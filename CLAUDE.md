# Poyetik

## Language: English only

**Everything in this repository is written in English**: code, identifiers, comments, CLI output, UI text, tests, documentation, roadmap tickets, commit messages, PR descriptions, CI and hook output. No exceptions.


## Guiding principle: maximum proof

We want **the maximum proof we can get**, everywhere, at all times. Every property we claim must be backed by an automated check that runs in CI and in the pre-push hook (which proves only the mutants of the changed code, and every mutant when a tag is pushed; see CI). In order of preference:

1. **Impossible by construction**: the type system, the compiler or the tooling makes the mistake unrepresentable or uncompilable (`no_std`, `forbid(unsafe_code)`, newtypes, unions of literals, banned methods, no casts).
2. **Formally checked**: model checking or proofs where it is feasible (Kani, Miri).
3. **Exhaustively tested**: 100% line and branch coverage, no surviving mutant, property tests, fuzzing, cross-target conformance.
4. **Reviewed**: only for what none of the above can reach, and documented as such.

When in doubt, choose the stronger guarantee, even if it costs more work. A shortcut that weakens a guarantee is never acceptable.

## Goal

A visual audio patching environment (boxes connected by cables), with a Rust engine (WebAssembly on the web, native elsewhere). The full patcher is a desktop application, without limits; a lighter version, with limits, runs in the browser.

A finished patch can be exported natively, user interface included, to: web, macOS, Windows, Linux, iOS, Android, plugins (VST3, CLAP, AU…), and embedded audio boards (microcontrollers, and single-board computers running Linux), without a user interface or with their own controls.

Core promise: **the engine produces exactly the same samples, bit for bit, on every target**. A strict, public testing policy proves it.

## Audio DSP: the objective

**State-of-the-art audio quality, measured, on every target.** Every box sounds as good as the best professional implementations of the same process, and proves it with numbers in its tests; bit-exact determinism is never traded for it, nor the reverse.

**Before any engine or box change, read `spec/engine-design.md`** (the decisions, and the step that implements each) **and `spec/measurements.md`** (the measurement definitions, and how thresholds are derived). A change that contradicts the spec changes the spec first, with the maintainer's decision.

- **Quality is measured, not claimed**: every box, and every engine component that touches the signal (the resampler, parameter smoothing, the output-stage limiter, latency compensation, hot-swap crossfades, event timing), has objective measurements with thresholds (spectrum, aliasing level, THD, SNR, frequency response, behavior under parameter changes), compared with high-precision references (double precision or arbitrary precision). Each threshold is derived from first principles, with its derivation next to it, as `spec/measurements.md` defines; an engine component's measurements land with the step that builds it (`spec/engine-design.md`).
- **Known pitfalls are handled by design**: aliasing (band-limited synthesis, oversampled non-linearities), zipper noise (smoothed parameters, sample-accurate events), unstable filters under modulation (topologies such as TPT / zero-delay feedback), subnormal numbers (a deterministic strategy, flushed in software at defined points, since WebAssembly cannot set a hardware flush mode, though a browser may run its audio thread under one: `spec/limitations.md`), DC offset, numerical precision of phases and coefficients.
- **Real time is a hard constraint**: no allocation or release of memory, lock, I/O or unbounded work in `process`, nor anywhere on the browser's audio thread. Two known exceptions, tracked by #12 steps 21 and 30: a processor and its WebAssembly instance belong to the audio thread, so constructing the engine processor compiles the module, instantiates it and builds the plan there, once, before it renders (measured; to be bounded by step 30, as `spec/engine-design.md` decides); and the playground's oscilloscope runs the tap processor, which copies and posts every render quantum while it plays (until step 21). Four messages of the engine processor on the audio thread are exceptions too, each bounded by what causes it and held by a test of `bindings/audio-wasm`'s `processors.test.ts`: the `replaced` message, at most one per `REPLACED_REPORT_SECONDS` of audio ("tells the first replacement at once, then more at most once per REPLACED_REPORT_SECONDS"); a refusal, one message per refused command, the engine's (`refused`, "tells a refused command back as bytes, and renders on") or the processor's, for a command it cannot read (`malformed`, "tells a malformed command back as its own kind, apart from the engine's refusals, and renders on with the settings it had"), the processor's also throwing and catching its `CommandError` in JavaScript and posting its detail, one per message received, the engine's refusal also allocating and releasing its explanation in the module (counted exactly at the C interface by `audio-wasm`'s `follows_the_protocol`, for each kind of refusal as derived per character by `refusal_operations`, and none for an accepted command by `assert_accepted_without_the_heap`) and its `OutputError` in JavaScript, until roadmap #24 step 130; the live commands of the limiter (`setLimiter`, `setProtected`), one message received per command, none sent back on success ("applies the commands of the main thread, telling nothing on success") but the next; and the `lookaheadApplied` message, at most one per accepted `setLimiter` command, none for one that keeps the lookahead asked for, when the lookahead it asked for takes effect, at once or at the limiter's rest ("tells a lookahead set at rest applied after the quantum that takes it, then nothing more", "tells a lookahead set while it limits nothing while pending, and applied when set back"), the processor reading whether one is pending once per accepted `setLimiter` command and, per quantum, only while one is.
- **Cost is measured**: benchmarks per box in CI with regression thresholds; an approximation replaces an exact function only when measurements prove it is both faster and within threshold.
- **Engine design decisions come first**: messages, event scheduling, feedback, polyphony, multichannel, rates, parallelism, hot swap, latency and state are decided and recorded (in `spec/engine-design.md`) before the code that depends on them.

## CI

**One command runs every check: `cargo xtask check`** (Rust formatting, lints, tests, portability builds, 100% coverage gate, mutation testing, Miri, conformance, supply chain, then every TypeScript package: the shared policy itself, each rule proven to reject what it forbids, the oracle, the engine in the browser, the playground, the roadmap, the WebAssembly build tool, the visual library's module and the page module; and the GPU renderer's own Cargo workspace, checked as the root). It has two modes, which differ only in mutation testing, in whether a failure stops the run, and in the order of the steps (`Mode` in xtask; `cargo xtask list [--full]` lists the steps of each): the default check runs the full check's steps cheapest first (`cheapest_first`), an order that changes no outcome; `--full` keeps its order. Every step and the check say their elapsed time (`run_steps_then`). A third command mutates one target:
- **`cargo xtask check`** (the default, for development; the `.githooks/pre-push` hook runs it through `cargo xtask pre-push`, which first refuses uncommitted changes and a pushed commit other than the one checked out, `pre_push_gate`, and runs `--full` instead when a tag is pushed, since a release requires it): Rust mutants only in the lines changed since the merge base (`MUTATION_BASES`; no base, the check fails), uncommitted changes and new Rust files included, a file git hides from its diffs refused (`hidden`), no change, no mutant (`rust_mutants_of_changes`); widened to every mutant of a source whose unit tests changed (the source declaring the `*_tests.rs` file changed; a crate with a changed test file no source declares is tested whole: `declaring_sources`), and of a crate whose integration tests or declared test data changed (test code lives only in `tests/` and declared `*_tests.rs` files: `test_code_gate`, and `loaded_files_gate` over the files rustc itself read; test data are `RustCrate::test_data`, the only files outside its crate a crate's tests may read: `test_data_gate`, where a path computed at run time is review only), to every crate a change of a shared input reaches, and to every Rust mutant when what every test depends on changed or a change cannot be narrowed, said with the reason (`widening`, whose `Widening` holds the table, and `reach`); in the parallel jobs of `--full`, with the unviable-mutant gate refusing every unreviewed unviable mutant it generated, then every stale review (`unviable_reviews_gate`); TypeScript mutants through Stryker's incremental mode (`STRYKER_INCREMENTAL`), which reruns the mutants whose code or covering tests changed and reuses the earlier results of the others, so its report and the TypeScript gates still cover every mutant. It proves that the changed code has no surviving mutant under the tests as they are now. It does **not** prove what only the full check sees: a Rust mutant outside the changed lines that a change elsewhere (a test weakened, a unit test of another source among them, a callee changed) now lets survive, and a TypeScript result reused although something Stryker does not track changed (a test helper or fixture, a configuration, a dependency, the WebAssembly module). **A green default check does not imply a green full check.**
- **`cargo xtask check --full`**: every mutant (cargo-mutants in parallel jobs, `mutation_jobs`, as in the default mode; Stryker's `--force`, which also rewrites its incremental file), and the unviable-mutant gate refuses stale reviews after its complete run. It runs every step whatever fails, then reports every failure at once (one stdout line per failed step, one `error:` line counting them), while the default check stops at the first failure; within a step, every gate runs whatever another found, and the step reports each failure (xtask's `all_of`; one gate follows another only where it reads what that one proves, a precondition stated where they are chained). `.github/workflows/quality.yml` runs exactly this, split into parallel jobs: one per part of the full check (`cargo xtask list --full --parts`; `cargo xtask check --full --part <part>`: the Rust checks, the Rust coverage, Miri, the gates, each TypeScript package, and each mutation shard of the Rust mutants, cargo-mutants' `--shard`), then, once every part has passed, a final job that reviews the unviable mutants of every shard together, stale reviews included. The parts gate proves that the parts run every check step of the full check once (only preparation repeats), and the workflow gate requires the workflow to be exactly the one xtask defines (`workflow_text`: its matrix lists exactly those parts, every job holds the `[ci]` condition), up to its comments, its blank lines and the commit hashes of its actions with their tag comments. It is **required** before a release (a tag), at the end of a review block, before its merge (its pull request's CI run), before closing a roadmap ticket, for a deep review (except a review block's, which comes before it, see Working in blocks), and whenever a change can weaken tests or code it does not touch (test helpers, fixtures, configurations, dependencies, the engine under the TypeScript packages); a green CI run counts.
- **`cargo xtask mutants <target>`**, for development: every mutant of one target, a crate by its name (`cargo mutants --package`), a Rust file of a crate (`--file`), a TypeScript package by its directory (Stryker on the whole package, which also rewrites its incremental file) or one of its sources (Stryker's `--mutate`), or `--changed <revision>`, the Rust lines changed since the merge base of `HEAD` with that revision (any revision git resolves: a commit, a branch, a tag), new Rust files included, the root's lines never widened (a change in the GPU workspace, which the root's cargo-mutants does not see, mutates that whole workspace) and with no proof record (`rust_mutants_of_changed_lines`, measured in `crates/xtask/README.md`, where the default check may widen to a whole source or crate; it says the merge base, its short hash and subject, and how many mutants it will test before testing them; a revision git does not resolve is refused, named, and so is `--changed` without one, proposing the branch's upstream: the base is never chosen silently, since the upstream's default of the default check mutated, on a branch not pushed or one branched from another, the work of others), then the gate on that report, as for a partial run (no stale review; no mutant at all is accepted, except for a whole package). It proves that target only, and never replaces a check.

Every build cargo-mutants makes, in both modes, in every part and in `cargo xtask mutants`, differs from every other build of the checks only by dropping debug information and capping lints (`MUTANTS_ARGS`), neither of which changes the code generated (reviewed: `MUTANT_BUILD_CONFIG`'s doc holds the comparison and the review); on Linux, cargo-mutants also runs the test programs cargo builds (doc tests apart, which rustdoc runs) under a 4 GiB address-space limit (`MUTANT_TEST_RUNNER`), which changes no build. Each choice made for the check's speed beyond what the default check leaves to the full check (above) is recorded with its measurement and its argument that it changes no outcome in `crates/xtask/README.md`, or, where the maintainer traded a proof of the default check for speed (the full check, which every change passes before `main`, keeping it), with that decision.

The default check also keeps a **mutation proof record** (`ProofRecord`): when its Rust mutation testing and the unviable gate pass on a clean tree (`unclean`: the cleanliness the pre-push hook requires, nothing changed while it ran), it records what it proved, in git's common directory, shared by every worktree. A later default check of the same base and host skips every crate whose inputs (its files, those of every crate of the workspace it depends on, its declared test data) are byte-identical to the recorded commit; every other crate is mutated exactly as without a record, from the changes since the base widened by the same function (`reach`), so **a record never changes what the default check proves**; each crate skipped that the check would otherwise have tested is named. A record is ignored, with one line saying why, when it cannot be read or when anything it is keyed on changed (`usable_proof`, `proven_crates`; `ProofRecord` and `ProofTools` name each input); only a missing record is passed over in silence. Review only: the shell xtask's tests run, which no record can name (`ProofRecord`). The record is optional: when the environment refuses it, the step says `not recorded: <reason>` and succeeds (`record_mutation_proof`). `cargo xtask check --full` and CI never read nor write a record; the pre-push hook benefits locally only.

So a green full check locally differs from a CI run only by platform (the limits of its runner, below); a green default check means only that the changes are proven. **CI runs on demand**, since the full check is long and commits are frequent: on a push only when the last commit's message holds `[ci]` alone on a line (Claude adds that line when the maintainer asks for CI; the commit-msg hook and the history gate refuse the marker anywhere else, since GitHub's condition can only search the whole message), on every pull request, and by hand (Run workflow on GitHub). A run can check only some parts, to debug one on CI without the whole matrix: a push whose marker names them, `[ci gates bindings-audio-wasm]` alone on a line (known parts, each once, in the order of `cargo xtask list --full --parts`, the final one apart: the one form the hooks accept), or a run by hand given them; `cargo xtask ci-parts` reads them for the workflow's first job, and such a run has no final job, so it is never a full check. The repository allows rebase merges only (a maintainer setting on GitHub), so that no merge commit enters `main`; the history gate accepts the one merge GitHub writes to run a pull request (`Merge <commit> into <commit>`) only as the commit checked out, never anywhere else in the history.

Working while the check runs: when it is useful and harms nothing, development may continue in a separate git worktree (`git worktree add`, its own branch) while `cargo xtask check` validates a finished commit in the main one, since the check (mutation testing above all, the full check most) takes a long time. It is an option, not a habit: skip it when the next work depends on the result, or when the extra load would disturb the check (load-sensitive browser tests). The validated commit is not done, and the work built on it is not pushed, until that check is green; a failure is fixed by a new commit, validated again.

What CI runs on, and so proves, is limited by its runner: an x86_64 Linux machine; each green run proves what this section says CI proves, for the commit it ran on. Native conformance (the same hashes as WebAssembly) is proven in CI on x86_64 Linux only; on aarch64 (macOS on Apple silicon) it is proven by the pre-push check of a Mac, and only cross-compiled in CI; the native shell (`audio-cli`) and the floating-point mode it uses (`fpenv`, test support of either library too), whose code differs by architecture, are linted (Clippy, which type-checks) and their libraries built (code generated and inline assembly assembled, nothing linked) for both architectures on every machine (xtask's `NATIVE_TARGETS`), so CI compiles and assembles their aarch64 code and a Mac their x86_64 code, which only the other runs. "WebKit" in the browser tests is Playwright's WebKit (WebKitGTK on Linux), not Safari, and "mobile WebKit" is the same engine at an iPhone's size and user agent, not iOS Safari. The runner has no sound card: every job that runs a part of the check (the `check` job's matrix; the final job plays nothing) starts an audio server with a null sink as its default output (xtask's `AUDIO_SINK`), through which Firefox plays live, while Chromium runs with its audio output disabled; so in CI, live playback is proven to reach an audio output, never a device, and a local check uses the machine's own output, unchanged. A macOS job (#20 step 1) and checks on real phones (#18 step 5) are planned; until then, a claim that needs aarch64 or Safari rests on the pre-push check of a Mac.

Every new check is added to `xtask` (`check_steps`), never directly to the hook or the workflow. The hook is enabled through `core.hooksPath`, set automatically by `pnpm install` at the root. **The hooks are never bypassed by default.** Two exceptions, decided by the maintainer, where Claude may skip the pre-push check (`git push --no-verify`) and says so in its report: when the maintainer explicitly asks for it for a given push; and, without asking, when a full CI run will check the pushed commits before anything relies on them (a push to a pull request's branch, whose CI run is the full check, or a push to `main` followed by a full run on `main` that Claude starts, by hand or with `[ci]`), since the repository is public and its CI free, so that a local check that would only repeat it, for hours when a change widens the mutation testing to whole crates, is not run; never for a tag, whose push runs the full check. The commits pushed that way are not validated until a later `cargo xtask check --full`, local or a CI run, is green (after the push, the default check finds no change and mutates nothing); a CI run validates them on x86_64 only, so before such a push Claude runs on the Mac what differs by architecture, `cargo test -p fpenv -p audio-cli` and the native conformance (`cargo run --package audio-cli --locked -- check conformance`), and the rest of aarch64 rests on the next default check of a Mac. The commit-msg hook is never bypassed (`git commit --no-verify` stays forbidden).

### Working in blocks
- **Large tickets are done in small review blocks** of two to four steps: each block is a branch with one commit per logical change. Every step of the block gets targeted checks chosen for what it touched, proportionate to it (the static gates, `cargo xtask check --gates`, every time: the gates of either check that read the tree and what tools say of it, their tool runs included (`Action::ToolGate`: rustdoc, cargo-deny, the frozen JavaScript install, `pnpm audit`), derived from their steps (`gates_steps`), which no other targeted check runs, the network needed; tests, Clippy and formatting of the touched crates and packages, the tests of every crate and package that depends on a changed one, since a dependent's own fakes or uses may break where the changed one's tests pass, mutation testing of the changed lines (cargo-mutants' `--in-diff`), a whole file's mutants only when its logic changed in depth, browser tests when the engine under them changed; listed in the step's report; the long suites run once, in the pull request's CI) and a light targeted review (blocking problems fixed, the rest added to the hardening card), and its roadmap step is ticked on the branch (`main`'s board may lag until the merge).
- At the end of a block, in this order: (1) the default `cargo xtask check` on the branch; (2) a **deep review** of the branch's diff against `main` (no pull request yet), scoped by the spec decisions and roadmap steps of the block, the maintainer deciding on every finding; (3) the decided fixes, with targeted checks; (4) the **pull request**, whose CI run (the full check) runs once on the final state and must be green: it is the block's `--full`; (5) the version commit and the **rebase merge** into `main` (no merge commit).
- For #12, the blocks end at steps 8, 12, 15, 18, 22, 27, 31, 34 and 38 (their titles carry the end of the block). How many review passes a block takes is decided with the maintainer from what the last pass found. A block's last step is ticked by the last commit of its fixes, before the pull request, not with its targeted checks, since its title claims the review.
- Small changes outside a block (docs, roadmap, a fix) may go to `main` directly, with their version number and the usual checks.

## Command-line tools

Every command-line tool of the repository (`audio-cli`, `visual-cli`, `cargo xtask`, the oracle, the roadmap CLI, the WebAssembly build commands, and every one to come) follows one contract, tested on the real entry point:
- exit code 0 on success, 1 when the work failed, 2 for a usage error;
- every error is one line on stderr, `error: ...`, naming the file or the command involved; never a stack trace;
- a usage error says what is wrong and where the usage is, `error: <reason> (see: <command>)`, `<command>` the exact command that prints the usage as the tool is run (`cargo xtask help`, `cargo run -p visual-cli -- help`, `pnpm roadmap help`): `cargo xtask check` requires every hint to open in that one form and to start with a command a user runs (`runnable_hints_gate`: `cargo xtask`, `cargo run`, `cargo update`, `pnpm`, `git` or `node`), and each tool's tests run the exact command its hints name; only that command prints the usage, on stdout;
- a closed stdout (`| head`) is never an error and never changes the exit code, for the commands a tool starts too as long as stderr stays open (`cargo xtask` writes their output to its stderr);
- a tool with several problems to report prints them on stdout, one per line, and one `error:` summary on stderr (for `cargo xtask`, the problems of the commands it runs come with their output, on its stderr, but `cargo xtask bless`, which replays `audio-cli bless`'s result lines, then its error output, on its stdout);
- untrusted text quoted in an error (a box name, a field of a document) is escaped and bounded, so that it can neither drive the terminal nor forge a second line.

## Portability

**Each library's core is fully portable: no platform-specific code, ever.** `audio-core` and `visual-core` (and every crate they will be split into) are `no_std`, have no OS, clock, thread, file, network or JS access, and build for every target. Everything platform-specific (audio and video I/O, files, permissions, UI hosting) belongs to the thin shells around it (`bindings/`, native players, plugin wrappers, Tauri apps).

This is proven, not assumed: `cargo xtask check` builds the core and the boxes of each library (`PORTABILITY_PACKAGES`: the audio library's and the visual library's crates, their shells apart, tied to their roles by a test, and the coordinating layer above both; every `no_std` crate is among them or is listed with why it is not, `no_std_portability_gate`) for macOS (ARM), Linux (x86), WebAssembly and a bare-metal ARM microcontroller with no OS at all. Their tests run on x86_64 and aarch64 hosts only; `audio-core`'s also build there only, since its host differential uses `fpenv` (#24 step 159).

## Technologies and dependencies

- **As few as possible.** Every dependency (library or tool) is a liability: prefer the standard library, then a tool or library already used in the project, then a new one.
- **Modern, mainstream and well maintained.** Only widely used projects with active maintenance and a healthy community. Nothing obscure, experimental or abandoned.
- **Every dependency is justified** in `dependencies.txt`, the dependency register: every direct dependency of a crate or a package with its reason (what it is for, why it is needed), which `cargo xtask check` requires to match the manifests exactly. Adding one means adding its line first. The local `doc/architecture.md` keeps only the strategic reasons (why this one rather than another, what it commits the project to).
- Versions are locked (`Cargo.lock`, `pnpm-lock.yaml`) and the toolchains are pinned. A dependency whose code computes output samples, images or hashes, or the values they are computed from, is **bit-defining**: its line in `dependencies.txt` gives a reason starting `bit-defining: `, every normal or build dependency of the audio library and of the visual library is one, as are the case readers of both command-line tools (`audio-cli`, `visual-cli`), and each is pinned to one exact version (`=X.Y.Z`), its updates following `spec/engine-design.md` decision 29 (checked by the pin gate for the libraries' direct dependencies and for those of a crate holding `CrateRole::CaseReader`, `visual-cli` so far (`audio-cli`'s role is roadmap #24 step 101), and for the pin of every dependency marked so; the code they reach in turn is fixed by `Cargo.lock`, which every check builds with, and proven by the render hash vectors, conformance and the fingerprints, a change of it in the lock file being an update too). Every lock file is tied to the others: the versions a new lock file (Cargo or pnpm) shares with another are held equal by a gate of `cargo xtask check` from the day it lands, as `shared_versions_gate` holds the GPU workspace's `Cargo.lock` to the root's.
- **The audio library stands alone** (the crates of xtask's `RUST_CRATES` holding `CrateRole::Library`, `spec/engine-design.md` decision 32): its crates depend, within the project, only on each other and on the time crate (`spec/engine-design.md` decision 17; planned, #37), and their tests also on its test crates (the crates holding `CrateRole::LibraryTests`: `audio-testkit`, the fingerprint battery, the counting allocator and the floating-point mode `fpenv`, which depend only on the library and on each other, so that nothing the library or its tests reach, however indirectly, is outside them); never on the native shell, xtask, the apps, the tooling or the layer above it, which uses it only through its public interface (checked). **The visual library stands alone the same way** (the crates holding `CrateRole::VisualLibrary`, `spec/visual-design.md` section 1): within the project, only on its own crates and the time crate, its tests also on its test crates (the crates holding `CrateRole::VisualLibraryTests`: `visual-testkit`, the counting allocator and `fpenv`), held to the same rule (checked by the same gate, which holds its tool, `visual-cli`, to the same dependencies; the pin gate requires every normal or build dependency of either library to be bit-defining and pinned).
- **No architecture choice costs performance** (`spec/engine-design.md` decision 33): libraries are crates of one program (natively one binary, in the browser one WebAssembly module per thread, never one module per library side by side, externals apart, roadmap #34 step 6 and #35 step 3), their interfaces take blocks and borrowed slices with no dynamic dispatch on hot paths: a plan calls the built-in boxes directly (`audio_boxes::BuiltIn`), and only a box type loaded at run time through its virtual table, once per box per block, never per sample, none in build mode (measured, dated in `spec/benchmarks.md`: fewer instructions per box per block for slightly dearer plan loading, the real-time path coming first), and a box or the engine costs the same directly and through an interface, held by the benchmarks (`spec/benchmarks.md`): within the counts' tolerance today, exactly or within a per-call allowance written for each interface once its comparison lands (roadmap #12 step 13, #32 step 8).

## Strict typing and linting policy

Non-negotiable, and **enforced by tooling, not by goodwill**: CI and the pre-push hook reject any violation (the hook's mutation testing covers only the changed code, every mutant when a tag is pushed; see CI). No shortcut may weaken the whole.

### Principle: parse at the boundaries, trust types inside
- External data (JSON, CLI arguments, files, network, FFI) enters as `unknown` (TS) or raw bytes (Rust) and is **validated once, at the boundary**, by functions that *prove* the type (TS type guards, Rust constructors returning `Result`).
- Every limit a specification states (a size, a range, a count) is enforced at the earliest point, before the input is held whole, by a type of fixed width where one fits (never a pointer-wide type, whose range differs between targets), and is tested at the limit and one past it. Every reader of one format accepts and rejects the same documents, checked on a shared corpus.
- Internal code only accepts proven types and **never re-checks** what the type system already guarantees. Invalid states must be unrepresentable (unions of literals, newtypes, private fields with checked constructors).
- If a value cannot be typed precisely, fix the types. Never silence the checker.

### TypeScript
- `tsconfig`: the strictest settings (`strict`, `noUncheckedIndexedAccess`, `exactOptionalPropertyTypes`, `noPropertyAccessFromIndexSignature`, `verbatimModuleSyntax`, `isolatedModules`, `erasableSyntaxOnly`, `useUnknownInCatchVariables`…), shared by every package through `@poyetik/config` (`tooling/config`); the roadmap extends Astro `strictest` with the same extras.
- ESLint: one configuration for every package, `@poyetik/config/eslint`; a package only adds what its framework needs (React hooks rules).
- ESLint: `strictTypeChecked` + `stylisticTypeChecked` with zero warnings, plus:
  - **no type assertions** (`as T`, `<T>x`), except `as const`, and no non-null assertions (`!`);
  - **no `any`**, explicit or implicit;
  - **no `@ts-ignore`, `@ts-expect-error`, `@ts-nocheck`**;
  - **no inline `eslint-disable`** comments: a rule is either respected or changed in the config, for everyone, with a reason;
  - strict boolean conditions (no truthiness on strings, numbers or nullable values), exhaustive `switch`, explicit types on exported functions, no `enum`, `readonly` where possible, type-only imports;
  - **no formatter given no locale** (or `undefined`, or `[]`), which follows the machine's locale, one no test run varies: the formatters `LOCALE_SYNTAX` lists (`@poyetik/config`'s `eslint.ts`, whose policy fixture holds each form), a read of the locale itself staying allowed;
  - a type parameter of an exported function is inferred from a required argument, or its signature is split into overloads, so that no caller names a type its value does not have (`loadPatch`; no lint catches it: review, and a type fixture per function, until #24 step 150).
- Tests follow exactly the same rules: no casts to reach "impossible" states. If a state is impossible by type, it needs no test and no runtime check.

### Rust
- Pinned toolchain (`rust-toolchain.toml`), edition 2024, `rustfmt --check`.
- Workspace-level lints, inherited by every crate, all as errors:
  - no `unsafe` code anywhere (`#![forbid(unsafe_code)]`) except the minimal, audited files of xtask's `UNSAFE_FILES`, the only ones lifting the lint: every crate root and module forbids it, but the roots of their crates, which stay under the workspace's `deny`, and the unit tests an unsafe file declares, which stay under its lifting (`unsafe_gate`), so that the compiler refuses any other lifting; and since rustc does not lint code expanded from another crate's macro, no Rust file but those and the unit tests they declare holds the keyword `unsafe`, nor any file `global_asm!` or `naked_asm!` (`unsafe_gate`, in tokens; neither workspace holds a procedural macro or a build script, `untested_targets_gate`, so only `macro_rules!` macros and third-party macros expand into it, the latter left to the dependency review); every library root forbids unsafe code in its doc tests, which are crates of their own (`#![doc(test(attr(forbid(unsafe_code))))]`, what they load being review only); every crate inherits the workspace lints, and `.cargo/config.toml` holds no build flag. The constant's doc names each with why it lifts the lint: the C interfaces of the WebAssembly modules (each a minimal C interface with the same guard against WebAssembly atomics) and the counting allocator `alloc-counter` (test-only, every call delegated unchanged to the system allocator), which proves that boxes never allocate while processing, all checked by Miri; and the floating-point control register of `fpenv` (native only, `x86_64` and aarch64), which sets the CPU's default floating-point mode around native engine calls (`spec/engine-design.md`, decision 11). Inline assembly, which Miri cannot run (`ASSEMBLY_FILES`; `unsafe_gate` keeps each of its `unsafe` blocks to one assembly call and lets no other code of its crate run unsafe under its lifting): it is proven by its crate's tests (`lib_tests.rs`, whose module doc lists them; 100% coverage and no surviving mutant) on the architecture that runs them, `x86_64` in CI and aarch64 only by the pre-push check of the maintainer's Mac until the macOS job (#20 step 1), and by the review written in the file (`word.rs`: the instructions, the reserved bits, and Rust's floating-point rule, which its writes and the crate's tests under forced modes break on purpose, with why);
  - `missing_docs`, `unused_results`, `unreachable_pub`, `rust_2018_idioms`;
  - Clippy `all`, `pedantic`, `nursery` and `cargo` groups, plus selected `restriction` lints: no `unwrap`/`expect`/`panic!`/`todo!`/`unimplemented!`, no `as` numeric casts (use `From`/`TryFrom`), no indexing that can panic, no equality on raw floats (`float_cmp`: the ban targets `f32` and `f64`; exact equality of the engine's sample types is allowed by design, the same IEEE equality on every target, and reviewed, `spec/engine-design.md` decision 10), no `dbg!`/`print!` in library code, no struct mixing public and private fields (`partial_pub_fields`: a type that keeps an invariant keeps all its fields private), no lint suppressions (`#[allow]`) without an explicit, reviewed `reason`.
- Determinism rules as Clippy `disallowed_methods` / `disallowed_types` (`f32::sin`, `mul_add`, `Instant::now`, `HashMap` with random state…).
- Supply chain, by `cargo xtask check`, whose configuration is xtask's (`supply_chain_gate`: a crate's advisory ignored, a crate skipped, a release age shortened or an exclusion from it is a change of xtask; an npm advisory ignored is the traced exception below): licenses allowed only as listed (Rust: `deny.toml`; JavaScript: xtask's `SHIPPED_LICENSES` for what the apps ship, plus `TOOLING_EXTRA_LICENSES` for development tooling), no known vulnerabilities (`cargo-deny`, `pnpm audit`; an advisory `pnpm audit` ignores is a traced exception of the maintainer, listed under `pnpm-workspace.yaml`'s `auditConfig` with its package, its reason and the roadmap step that removes it, in the one form xtask's `AUDIT_CONFIG` documents, the key absent when none is, and refused in a package an app ships, `shipped_exceptions_gate`), no duplicate crate (`cargo-deny`), no unexpected direct dependency (`dependencies.txt`).
- Coverage 100% lines, functions and branches (`cargo-llvm-cov`; branch coverage needs the nightly xtask pins (`NIGHTLY_TOOLCHAIN`), used only for it, Miri and the float-method audit, which reads its `rust-src`), reached by **each crate's own unit tests**: `cargo xtask check` measures each crate of `RUST_CRATES` alone (`--lib`), so a path exercised only from another crate or an integration test is not covered (a fixture crate proves the gate refuses it). The gate reads llvm-cov's summary, which counts each generic function by its best instantiation, never their union: a line or a branch counts as covered only when one instantiation runs it (both ways of a branch in that same instantiation), so a branch on a constant of the instantiation (`if D::NARROWS`) is never covered, and is written as a run-time test of that constant (free, the constant being known where it is compiled; `given_as` in `audio-core`'s output stage, generic over the sample type alone, the constant passed to it as a flag), while a path taken in one precision only, or by one caller's type only, still counts when that instantiation takes it (roadmap #24 step 87). The one exception is a binary's `main.rs`, which unit tests cannot reach: it is measured by its crate's tests. No target or manifest setting may leave a test unbuilt or unrun: a target turns its unit tests off only if its root declares no module, so that no test can hide in it, and no library turns its doc tests off (`untested_targets_gate`, whose doc lists every setting it refuses; the `harness` key is refused by the bypass gate unless reviewed in `proof-bypasses.txt`). Code no test can reach is removed by construction, not tested around.
- **A `compile_fail` doc test proves its error code**: it names the code it fails with (`compile_fail_codes_gate`), which is part of its proof, since a block failing for another reason (a name renamed, a path moved) would prove nothing. Rustdoc checks the code only on a nightly compiler, so `cargo xtask check` runs the doc tests again on the pinned one with `RUSTC_BOOTSTRAP` limited to the workspace's crates, in a target directory of their own, after proving on a fixture that a wrong code fails (`doc_tests_command`); the preflight refuses the variable from the environment, so that no other build sees it.
- **No surviving mutant** (`cargo-mutants --cap-lints=true`, so that mutants are never skipped because of lints), and Miri on any `unsafe` but inline assembly, which it cannot run (the control-register file above, proven by tests and audit instead).
- **Every unviable mutant (one that does not compile) must be reviewed.** Confirm that the type system or `no_std` really makes that wrong implementation impossible, and that no legitimate variant of it escapes the tests; then record it with its reason in `mutants-unviable.txt` (every function a reason names, such as the test that kills the viable variant, is checked to exist in test code). `cargo xtask check` fails on any unreviewed unviable mutant it generated, and on any stale entry (the default check against cargo-mutants' `--list` of the workspace, the full check against its complete run), so the list always matches reality.

## Documentation, versioning and commits

Enforced by `cargo xtask check` and the git hooks, like everything else.

### Documentation
- **Every item is documented**, public or private: Rust `missing_docs` + Clippy `missing_docs_in_private_items`; TypeScript JSDoc on every named item, exported or not: functions, classes and their members, types, module-level constants (`eslint-plugin-jsdoc`, `publicOnly: false`).
- Docs explain **why and what**, not only how: purpose, invariants, units, errors (`# Errors` sections in Rust), panics (there must be none).
- `cargo doc` runs with the rustdoc lints as errors: no broken or private links, no invalid code blocks, crate-level docs required.
- `README.md` and each part's `README.md` explain what it is and how to run and check it (checked: every TypeScript package has a README, every part is named in the README of its folder, every folder in the root README); `GLOSSARY.md` holds the words of the project, one word per concept, and `cargo xtask check` refuses in the prose of the repository (Markdown, the comments and string literals of Rust and TypeScript, and the string values of the JSON files under `spec/` and `conformance/`; the released sections of `CHANGELOG.md` apart, which stay as `main` holds them, `released_sections_gate`) the synonyms it replaces, as listed in `vocabulary.txt` with the contexts where each is allowed; the local `doc/architecture.md` holds the architecture, the strategic reasons of the dependencies and the decisions log. Every architecture decision adds a line to that log.

### Versioning and changelog
- **One version for the whole project**, following [Semantic Versioning](https://semver.org): the workspace `version` in `Cargo.toml` and the `version` of every `package.json` must match (checked).
- **Every notable change adds an entry under `## [Unreleased]` in `CHANGELOG.md`**, in the same commit ([Keep a Changelog](https://keepachangelog.com) sections: Added, Changed, Deprecated, Removed, Fixed, Security). `[Unreleased]` describes the change from the last release, never the history of the branch: an entry for a state added and changed again before the release is rewritten, not appended to (a fix of what the last release did not have, a review's fix included, rewrites that feature's Added entry and never adds a Fixed one) (`duplicate_entries_gate` refuses two entries that open alike or cite mostly the same items, a heuristic whose doc states what it misses), and nothing is listed as removed or changed that the last release did not have; each Breaking entry names the public signatures it changes against the last version, whose version commit is the merge base with `main` (`git show <commit>:<file>`): at least one name it cites is a word of that commit's tree (xtask's `breaking_names_gate`, a word test that cannot tell a name's sense), and a commit adding a Breaking entry carries `!` (`breaking_bang_gate`, from `BREAKING_SINCE` on, which counts the Breaking lines a commit adds and removes: a commit that merges two entries and adds a break at once is outside it, kept out by one logical change per commit); both gates read the one form `- **Breaking`, and an entry of `[Unreleased]` that opens with "breaking" in another form (`- **BREAKING:**`, `- Breaking:`) or marks itself breaking at its end (`(breaking)`, a last word "breaking") is refused (`breaking_spellings_gate`; one saying so inside a sentence, "a breaking change", is read by no gate until #24 step 168), as is every line of `[Unreleased]` that is not blank, a `### <kind>` heading, a `- ` entry or a line indented below one (`unreleased_shape_gate`), so that no entry escapes the gates under another bullet. The changelog format is checked: `# Changelog`, `## [Unreleased]` first, then `## [X.Y.Z] - YYYY-MM-DD` in strictly decreasing order, never newer than the project version, and no link-reference footer (the oldest released section runs to the end of the file, kept as released: `released_sections_gate`).
- **Every push to `main` carries a new version number** (decided 2026-11-09), chosen exactly by Semantic Versioning: while the version is `0.x`, the minor version for new features or breaking changes, the patch version for fixes only; from `1.0.0` on, a breaking change bumps the major version. The push's last commit is its version commit: it moves the `[Unreleased]` entries under a new `## [X.Y.Z] - date` heading and sets the version everywhere the version gate checks. A version is not a release: no tag and no GitHub release for it.
- **A release is a tag `vX.Y.Z`** on a version commit, made only when the maintainer decides, on `main` after the rebase merge (which rewrites the branch's commits, so a tag made on the branch would name a commit `main` never holds). It requires a green `cargo xtask check --full` (the pre-push hook runs it when a tag is pushed; a green CI run counts) and a deep review.

### Commits
- **[Conventional Commits](https://www.conventionalcommits.org)**, in English: `type(scope)!: summary`, with type one of `feat`, `fix`, `docs`, `test`, `refactor`, `perf`, `build`, `ci`, `chore`, `style`, `revert`; optional scope, one name per part (xtask's `commit_scopes`: a crate by its name, a package by its folder or the crate sharing it, `audio-wasm`, or one of `COMMIT_SCOPE_EXTRAS` such as `spec`; held to that list from `SCOPES_SINCE` on, a commit of `main` like every pin of the history gate, `history_pins`); `!` when the commit breaks a public signature of the last version (its version commit, the merge base with `main`), its body saying what breaks, and never for an item added since that version, which changes freely until it is released; header of at most 72 characters, no trailing period, a blank line before the body.
- Checked by the `.githooks/commit-msg` hook (`cargo xtask commit-msg`). One logical change per commit; never commit a red `cargo xtask check`.
- A promise in a commit body ("to be measured", "later") is kept in the same series or filed as a roadmap step in that commit, cited `#N step M`; an applied review fix closes every place and every direction its finding names, each with its test, or files the rest as a step.
- A commit that changes rendered bits blesses the references it changes in the same commit (`cargo xtask bless --case-changed <case>`, or `--live-changed` for the live limiter vector's hashes, its body saying why), never in a later one, so that no commit of the history leaves conformance red.
- A commit message cites a deep review's finding in its qualified form, "finding B04-1 of the fourth deep review of block 2", the first time it cites that review, then the later findings of the same review by their short ids (B04-2); never a short id of a review it has not qualified (a bare `D12` reads as decision 12 of `spec/`), and it cites a commit of a branch by its subject, never by its hash, which the rebase merge rewrites (review; the history gate's check of both is #24 step 147).

## Testing policy

Non-negotiable. A change that does not meet these rules is not done.

### Principles
- **No code without tests.** For the engine, the test is written first and must fail before the implementation.
- **Every bug fix starts with a regression test** that reproduces the bug and fails.
- **Tests are deterministic**: no system clock, no `sleep`, no network, no unseeded randomness, no dependency on execution order. A flaky test is a bug to fix, never something to re-run until it passes. The one exception to the clock: the wall-time benchmarks of `spec/benchmarks.md`, asserted only as upper bounds with a derived margin, in the end-to-end tests, read through the bench page's timing module. Enforced by tooling: the shared ESLint policy refuses the clock reads it lists (`@poyetik/config`'s `eslint.ts`) outside its reviewed `CLOCK_READERS` (that module, and the roadmap command's entry point, which stamps today's date); it refuses a sleep: Playwright's `waitForTimeout` everywhere, and in test code (`TEST_FILES`) the timers `setTimeout` and `setInterval`, bare or through the global object, outside its reviewed `TIMED_WAITS` (the playground's readings of the audio clock, spaced by the page's timers); a clock reached another way (an alias, `Reflect.construct`, a computed or spread form, `performance.timeOrigin`, an event's `timeStamp`) is beyond a syntax rule and left to review; and Clippy's `disallowed-methods` refuses `Instant::now` and `SystemTime::now`, but in xtask's `SystemRunner::clock` (a reviewed `expect` with its reason): the elapsed time the checks print, which decides nothing, and whose one test asserts only that the clock advances across the start of a process.
- **Never work around a test**:
  - do not delete it, disable it (`#[ignore]`, `.skip`) or weaken it;
  - do not lower a threshold or widen a tolerance;
  - do not update a reference hash to make CI pass.
  If a test looks wrong, stop and discuss it. A test that pins a maintainer's decision says so in its doc, with the decision's date; changing what it expects changes that decision, which only the maintainer does.
- **CI is the source of truth.** A single local command reproduces CI exactly: `cargo xtask check --full`.

### Scope: the whole project
Maximum testing applies to **all code, in every language**: Rust engine, patch model, WASM/worklet glue, web editor (TS), native shells (Swift, Kotlin), plugin wrappers, build service, AI assistant, tooling scripts. Nothing is "too simple to test".

### Measured requirements (all code)
- **Coverage: 100% of lines and branches** (`cargo-llvm-cov` for Rust, the equivalent tool for each other language). CI fails below that.
- **Mutation testing: no surviving mutant** (`cargo-mutants` for Rust, Stryker for TS, the equivalent tool elsewhere). A truly equivalent mutant is disabled by a `// Stryker disable next-line <Mutator>: <reason>` comment and listed with its justification in `mutants-equivalent.txt`; `cargo xtask check` fails on any disable comment not listed, any stale entry, and any broader disable. That list is public and reviewed. Every TypeScript mutant must be killed (or time out); one with another status (a runtime error included) fails the check, unless it is ignored exactly where a listed disable comment says so. Any other bypass of a proof (a skipped mutant, an ignored or focused test, a coverage exclusion, a mutation-tool configuration or a Stryker setting that hides mutants) is refused by `cargo xtask check` unless it is reviewed in `proof-bypasses.txt`; so is every TypeScript source of a package, tests apart, that its coverage does not measure or Stryker does not mutate (the scope gate: a package's coverage `include` and Stryker `mutate` select the same sources, and every other source is reviewed there). Stryker always runs `stryker.config.json` (named on its command line; a package script may run it only as `stryker run stryker.config.json`), and every source it should mutate that has statements must appear in its report, or be reviewed there too. That register holds only tool configurations, entry points and browser shells that wire measured code, the Astro templates Stryker cannot mutate (#15 step 2), and sources of constants Stryker has no mutator for; prefer moving code under the proofs to adding a line.
- **Test order in mutant runs follows the measurements**, in every Rust mutation run of every Cargo workspace (the root's and the GPU renderer's, each with its own slow group in its `.config/nextest.toml`, checked by `nextest_configs_gate`): each mutant's tests stop at their first failure, so the slow tests run last and a mutant a fast test catches stops in seconds. Stryker keeps no order: it runs only the tests that cover each mutant (`coverageAnalysis: "perTest"`), which leaves little for an order to gain (reasoned, not measured: a mutant's run holds only the tests that reach it). When a mutation run ends with a suggestion to move tests to or from the slow group, Claude analyzes it before adopting anything, and never adopts it as is: is the gain significant, does the suggestion look plausible (many tests suddenly slower, or slower by a similar factor, point to a loaded machine, not to slow tests: compare with earlier runs and the machine's load at the time, and measure again rather than adopt), is a slow test a sign of a test to speed up rather than reorder; only then does it adjust the order, in its own commit; the order never changes what a run proves, only how long it takes.
- **Strict static analysis**: `clippy -D warnings`, `rustfmt --check`, TypeScript `strict` with no `any`, ESLint with zero warnings, no exceptions.
- **Supply chain**: `cargo-deny`, `pnpm audit` (its exceptions traced, see Strict typing and linting policy) and xtask's license gate (licenses, vulnerabilities), locked dependencies, every direct dependency reviewed, and every third-party build script and procedural macro either Cargo workspace builds reviewed at its exact version in `build-time-code.txt` (`build_time_gate`: a new one, or a new version, is refused until reviewed). The provenance of npm packages is not checked yet (#24 step 30).

### Behavior tests
- **Reference renders**: every box has test patches rendered offline (patch + events + seed → samples + hash).
- **Cross-target conformance**: the same corpus produces **the same hashes natively and in WASM**, in CI (on x86_64 Linux; on aarch64 by the pre-push check of a Mac).
- **The corpus alone kills every mutant of the rendering code**: `cargo xtask check` mutates the code that writes image bytes with the visual corpus's check as the only test, and fails on a survivor not reviewed in `mutants-corpus-exempt.txt` (one that cannot change an image byte, with its reason) and on a stale review, since the targets that only replay the corpus see nothing it does not reach.
- **A reference hash only changes through a dedicated command**, and the commit explains why. Never silently.
- **Property tests** (`proptest`), at minimum:
  - the same render however it is split into host buffers;
  - two identical renders give the same result;
  - never NaN or infinity in the output.
- **Real-time safety**: no allocation or release of memory in `process`, measured from the first call on a fresh instance, checked automatically by the counting allocator (`alloc-counter`, re-exported by `audio-testkit`), installed in the tests of every crate that processes audio: each box (box laws), every plan (plan laws over random patches), the WASM engine and its C interface. On the browser's audio thread, no copies or messages per render quantum: `pnpm test:allocation` (`bindings/audio-wasm`) drives the engine processor from the first quantum of a fresh instance and counts V8's garbage collections, with every tier and with the interpreter alone, in a young generation of 1 MB (calibrated by a control: one object per 128-frame quantum causes a collection), and finds none for quanta that are whole engine blocks (Web Audio's 128 frames, with an engine block of at most 128 frames; the suite loads the 64-frame module only, until roadmap #24 step 121). Known deviations, each pinned by a test or ticket: the construction of the engine processor (see the real-time constraint above); the first quantum creates one view of the module memory per patch channel, kept for the next blocks, which the count cannot see (counted by a unit test); a quantum that is not a whole number of blocks allocates a view of the part of a block it copies (`subarray`), at least until V8 optimizes it (the optimized tiers are not measured), so with the modules of 256, 512 and 1024 frames every 128-frame quantum allocates a view per channel (#24 step 121); the tap processor copies every render quantum (capture, and the playground's oscilloscope until roadmap #12 step 21); SpiderMonkey and JavaScriptCore are not measured yet (#12 step 21).
- **Never test only at the default**: every dimension of the environment the code receives is tested across its domain, never at a single value: sample rate (8 kHz to 384 kHz, including 44.1 kHz), how the host splits time (host buffer sizes, including sizes that are not a multiple of the block, random splits), duration, channel count (including 0 and 1), parameter values crossed with rates, special values (0, -0, subnormal, NaN, infinities, Nyquist), patch sizes, browsers and platforms, the pointer width (32 and 64 bits: where the test host cannot vary it, code that depends on it is tested through a pure function of the width, given both as literals, as `audio-core`'s `fits`), screen sizes and densities, locale and time zone. Test values deliberately differ from defaults, so that a hard-coded default cannot pass. The shared values come from one test matrix, never retyped. A dimension is covered only when the tests iterate every value of the matrix, in each crate's own tests, and their result depends on it, checked against an independent reference rather than the code against itself (a plan hard-coding 48 kHz must fail). Code that imitates another program's lookup (a loader's search path, a tool's configuration) is tested at the edge values that program documents, not only at regular ones: an empty variable, a symbolic link, a dangling one, a link to a directory (the Vulkan preflight's `holds_a_manifest` and `vulkan_driver_dirs`); `std::fs::DirEntry::file_type` and `std::fs::DirEntry::metadata`, which follow no link, are banned (`clippy.toml`).
- **A gate accepts only the forms it parses**: any other spelling of the same thing (a conditional attribute, a dotted key, a comment around it, a combined form) is refused with a message naming the one form, never read as absent; its tests hold a fixture of each other spelling the language allows.
- **Invariants are tested at the edges of their domain**: every documented invariant and numeric claim is checked at the extremes of every parameter and sample rate and their combinations (zero, negative, Nyquist and above, subnormal, largest accepted sizes), and over long runs (drift, overflow). Every tolerance has a derivation or a measured distribution, written next to it; never a guess. A derivation states its preconditions and holds per regime, each regime tested and each precondition checked by a test reading the real constants; a test reference is exact where it can be (phases reduced in integers), and its own error stays inside the bound.
- **Objective DSP measurements**: every box and every engine component that touches the signal has measured audio quality in its tests, with derived thresholds (spectrum, aliasing level, THD, SNR, frequency response, parameter changes without zipper noise; for engine components, what `spec/engine-design.md` lists for each), compared with high-precision references, through `audio_testkit::measure` and the oracle's independent measurements (`spec/measurements.md`). State-of-the-art DSP is a requirement, not a goal.
- **Fuzzing**: patch parsing, the command layer, then native-vs-WASM differential fuzzing.
- **`unsafe` code**: forbidden by default. If truly required, it is isolated, its every `SAFETY` comment stating the rule of the interface it relies on (an address valid until the next call), never the list of today's writers, which a new one makes false, checked with Miri (or, for inline assembly, which Miri cannot run, by tests on each architecture it supports and a written audit) and, for critical parts, proven with Kani.

### Every other aspect
- **Commands and patch model**: every command is tested (success, rejection, undo/redo round trip), with property tests over random command sequences (full undo = initial state, identical serialization round trip).
- **Format compatibility**: every version of the patch format keeps test files. Old patches always load and migrate, checked in CI.
- **Web interfaces (playground, editor)**: the local `doc/interface-testing.md` is the required test strategy, layer by layer (scene, camera and animations, interactions, renderer, accessibility layer, components, end-to-end, visual regression, performance). It is mandatory, heavy on purpose, and applies from the first line of every interface change. In short:
  - unit and component tests;
  - end-to-end tests (Playwright) on **Chrome, Firefox and WebKit**;
  - visual regression via screenshots;
  - accessibility (axe);
  - the sound produced in the browser is captured (`OfflineAudioContext`) and compared to the native hash.
- **Performance**: engine and editor benchmarks (CPU per box, latency, load time, memory) tracked in CI. A regression beyond the set threshold fails CI.
- **Exported artifacts**: each target runs in test mode, its render is compared to the reference hash, and plugins pass the official validators (`pluginval`, `clap-validator`, `auval`, the VST3 validator).
- **Native shells**: Swift/Kotlin unit tests, plus lifecycle tests (interruptions, background, device changes, denied permissions) on simulators and reference devices.
- **Security**: CSP verified, no API key ever sent to the server (checked by tests), fuzzing of everything that reads external input (patches, media, network messages, MCP).
- **AI assistant**: an evaluation suite (requests → valid patch + expected render metrics), with a success rate tracked per model. A drop fails CI.
- **Reproducible builds**: two builds of the same commit produce identical artifacts, checked in CI.

### Rules the reviews taught
Each rule below comes from a class of defects a deep review found. Where a tool enforces it, the tool is named and is the reference; the others are checked by review.

- **Hermetic tests.** A test that runs an external tool runs it in a temporary directory, with no inherited configuration pointing outside it: git's local variables (`GIT_DIR`, `GIT_INDEX_FILE` … which a hook inherits, from a linked worktree too) are removed (`hermetic_git` in xtask's tests; xtask clears `LOCAL_GIT_VARIABLES` for every command it starts), and nothing reads the machine's or the user's configuration (git's system and global configuration, attributes and ignore files: every recipe of xtask's tests, the hooks' included, sets `HERMETIC_GIT`, whose effect a test shows on a user file it would read; every file of code in any crate or package that starts git itself names every variable of `HERMETIC_GIT` and `LOCAL_GIT_VARIABLES`, a copy of both lists where it cannot use xtask's, which `hermetic_git_gate` checks, a program named through a variable apart). No test writes outside its temporary directory, and a test removes that directory when it returns or unwinds, a failing test or a panicking mutant included: a guard removes it when dropped (`Scratch`, one per test target, each with its own test), never a final statement (a test process killed at a timeout or aborted leaves it, for the next test of the same name and process id to remove), and Clippy's `disallowed-methods` refuses `std::env::temp_dir` anywhere but in that guard's constructor. The code under test runs its own external tools with the test's isolation, through an environment its runner takes from the test, never the machine's configuration.
- **Fakes reproduce absence.** A fake of an event source can also withhold the event (a clock that runs only while running, a message never sent, a promise never settled), throw and reject, so that the tests cover the conditions under which the real event never comes. Every await of an external event is raced against the end of the object that waits; an in-flight promise is stored on the object whose lifetime it belongs to, and cleared when it fails. A fake of a host object is built on the platform's real base class where there is one (`EventTarget`), so that its event model is the host's by construction; the object that owns a resource follows its end from the moment it creates it, before its first await.
- **Every promise of a doc comment is attacked.** A behavior a doc comment promises ("never", "once", "already validated", "releases …") has a test that tries to break it, at its edges; a precondition it states (`must`, `only if`) is a type or a checked error, never prose only. A guarantee names the conditions it holds under, with a test on each side of each; an invariant a type's doc states is checked by every public constructor of the type, or the constructor is not public. A guarantee a type fixture states (a type that offers no way to do something) is also held, and tested, at the boundary below it (the engine refuses it, through each interface), or the fixture says it is the typed API's only.
- **An invariant holds at every public operation, and a stream's properties at its start.** An invariant a type keeps is checked, or made unrepresentable, by every public operation that pairs it with other data (a count of channels with the blocks it applies to), not only by its constructors; a field carrying an invariant is never handed out as `&mut`, only changed through operations that keep it (`OutputStage` owns its blocks and changes its limiter through `set_limiter` and `set_protected`); a component holding a stream's state (a limiter's delay, history and frame) never leaves the object of its stream, neither as `&mut` nor by a copy (`TruePeakLimiter` is not `Clone`). A property of a stream (its format, its length, its rate) is fixed when the stream is built, a type parameter or a field of what renders it, never given per call, and no method of the stream gives it in another (`Renderer<S, I, D, N>`, `Renderer::lasting`, `AsComputed`).
- **Numbers in comments are proven.** A number stated in a comment or a doc (a bound, a count, a size, a duration) is either the constant itself, named, or computed by a test from the exported constants; never retyped. A comment that justifies code by a measurement points to the dated record in `spec/` and states both what the choice gains and what it costs; a measured count is a record, never a constant of a comment. A figure a spec or a doc derives from a constant or a record (a deviation, a product, a count of runs) is written as a test derives it from that source, with its rounding named, and the test reads the text and refuses it stating another (`states_the_runs_figures_as_the_constants_give_them`). A measured figure quoted in prose (a count, a size, a cost a pixel) carries the date or the commit it was measured at, or a test recomputes it from its source; prose never says a figure is what a file gives unless a test reads both.
- **Tests never learn their answer from the code under test.** Expected values and fake keys are fixed facts written as literals or computed by an independent reference, never read from the module being tested; nor is a value bounded by a function that starts from it (a search starting at an estimate is never below it, so `exact <= estimate` cannot fail): the bound is checked against an independent count, and the commit names a cheat the old test passed and the new one refuses (`straight_start`). A mutant is equivalent only when no test anywhere can kill it, and is then reviewed (`mutants-equivalent.txt`).
- **A test's work is bounded without the code under test.** Every loop bound, run length, buffer size and iteration count of a test is a literal, a value of the test matrix, or computed by an independent reference. A value the code under test computes (a latency, a step, a channel count, a state it converges to) sizes or ends a test's work only after the same test has asserted it against such an independent value or bound, before any work it sizes; a loop that waits for the code to progress or converge has a cap computed the same way. A mutant can then fail a test, never make it run longer or allocate more than its correct version: one test sized by a corrupted value costs the whole test binary's time under mutation testing, whatever the other tests catch at once, so an assertion of the value in another test does not count. A time limit per test under mutation testing, which would end such a test whatever sized it, is roadmap #24 step 144.
- **A test's cost is recorded.** A commit that adds more than a few seconds of CPU to the tests of a crate or a package, in any build the checks make (debug, instrumented for coverage, Miri), dates the cost in `crates/xtask/README.md` in the same commit, since every mutant of the crate pays it again; a time compared across CI runs names each job's CPU model and compares only jobs on the same model, or normalizes by a control the change did not touch, since the runners' models differ from run to run; a proof that reaches no code of its crate (a proof of a specification's arithmetic over its domain) lives outside that crate's unit tests, in its integration tests or a test crate's, so that its mutants do not pay it (decided 2026-11-17).
- **An emulation first proves it took effect.** A test that emulates an environment (a time zone, a locale, a muted device, a blocked request, a policy) asserts that the emulation is in force before asserting anything that depends on it; a check that asserts an absence has a positive control that shows it would see a presence.
- **The tooling changes for a reason.** A change to the checks or their tools answers one of: a real incident (a gate missed a real mistake or refused a right change), a plausible honest mistake a review found, a measured speed gain that loses no proof (or only one of the default check's, by the maintainer's decision, the full check keeping it), a simplification (code or a rule removed), a new part of the project to cover, an upgrade of an external tool. A check made in advance is added when the failure it catches is plausible for an honest change, costly if it happens (bits, a release, data, a proof silently weakened), and the check is cheap; never against a deliberately crafted failure that cannot change what the engine computes.
- **A gate guards against honest mistakes.** Its scope is what an honest change can bring while it pursues its goal: the forms the tree uses, those a tool, an editor or a machine's configuration writes, and those a plausible edit would write. A form only an author's deliberate evasion would write, and which cannot change what the engine computes at run time, is outside its scope: the gate's doc says so in one sentence, and no code refuses or follows it. The engine's run-time guarantees (bits, laws, real time) keep every form in scope, however unlikely.
- **Every gate is proven to refuse.** A gate of `cargo xtask check` has a test with a fixture it must refuse, for every kind of problem it reports (the policy fixtures of `@poyetik/config` for the lint rules). A gate that parses text accepts only the canonical shape and refuses, never skips, what it does not recognize within its scope; every exemption names the exact form it allows; external identifiers are normalized before they are compared; a gate fed by git is tested against the output of real git. A gate's message never claims more than it checks. A guarantee that a lint is never lifted is a `forbid` the gate reads as tokens of a real leading inner attribute of the file, which the compiler enforces against every name of the lint, never a refused word; a word rule only covers what the compiler does not lint (the keyword `unsafe` in code expanded from another crate's macro), and says so; a gate over the repository's Rust sources reads the tokens of a real tokenizer (`RustSource`, the file's start rustc strips refused), never characters or lines; a gate that reads the structure of TypeScript code (its elements, attributes, calls, arguments) reads the syntax tree of the TypeScript compiler (`ts.createSourceFile`, as the playground's accessibility gate does), never regular expressions over its text, which an arrow's `>`, a comment or a nested brace defeats; a rule that tells files apart by their names (test code, test data) has a gate that keeps the names true. A gate about what the compiler loads or resolves (files, modules, paths, lint levels) reads the compiler's own record, for every configuration the check builds (each target, the fused math layer, tests or not: `loaded_files_commands`); a configuration no build of the check makes (a `cfg` only Miri, the coverage, the release profile or rustdoc sets, a feature) is refused where it is written, unless reviewed (the bypass gate), so the loaded-files gate is the guard of what is loaded, no word rule imitating it, and what a doc test loads is review only. A gate or proof fed by a tool sees exactly what the tool acts on: the tool's configuration and environment are pinned or refused, never left to the machine. A pattern with alternatives has a fixture for each alternative in each form it matches, and a test of a message asserts it as the user reads it, after every layer that adds to it.
- **A reused result is keyed on all its inputs.** A check may reuse an earlier result only when every input of that result (code, tests, test data, dependencies, configuration, rules, tools, host) is unchanged, as found by a tool (where the tool cannot see an input, the rule that keeps it seen is stated as reviewed, as the test data gate's run-time paths are); its soundness statement names each input, and each has a test showing that its change voids the reuse (the mutation proof record above; Stryker's incremental mode keeps the gaps the default check states).
- **No mutant may crash the test runner.** An error a framework reports globally (React on the window, an unhandled rejection) is caught by the test that triggers it, so that a mutant fails that test instead of crashing the runner: Stryker counts a crash as a runtime error, which xtask's mutation gate refuses.
- **One source per fact.** A fact shared by code, hints, manifests, tests or docs has one source; every other place derives from it, or a gate compares every copy (xtask's `PACKAGES`, `RUST_CRATES`, `TOOLS`; the test matrix). A README names the source of a list instead of copying it. This file states each rule, its guarantee and its limits, and names the item whose doc is the source of its mechanism; it never copies field lists, accepted forms, format numbers or measurements. Conversely, one name per meaning: a constant or function is reused only for the meaning it was made for. A helper that must be copied into each test target carries its test in each copy. Across crates, the crate owning a layout or a table exports it, and another crate's code and tests read the export, never a copy of its private constants (`visual_core::display_bucket_floors`). A text file read by several crates, workspaces or languages has its exact layout written in `spec/`, which its writer and every reader cite (the display corpus, `spec/visual-design.md` section 9); a test derives its constants from the code's (`SUBPIXELS`), never retypes them.
- **Validators accept exactly what they document.** A validator is tested with truncated, padded and out-of-range forms of what it accepts; a function that produces evidence (a hash, a report, a verdict) refuses malformed input instead of normalizing it, and takes every fact it records from its caller, never from a default. An option that relaxes a refusal is tested crossed with every other input the refusal depends on.
- **One kind of input, one classifier.** Inputs of one kind that several parts receive (the WebAssembly bytes the square and the sound download) are told apart by one shared function, so that one failure never takes one cause in one part and another elsewhere; a cache of such an input is dropped when the input fails, so that the retry a remedy names can succeed.
- **Errors keep their cause across boundaries.** An error crosses a boundary (a message port, the C interface, a process) as one of a closed set of kinds that keeps its cause, and is rendered in words at the edge; an error from an external command carries its exit status and its own error line. A cleanup (a `finally`, a close) never replaces the error that caused it, and every promise is handled on every path, a failing one included.
- **A public `# Errors` names every error.** A public function's `# Errors` names every error its private `_with` twin and its callees return, a memory refusal included (`View::setup`), and an error value preset for a request that never answers is named by the doc of the variant it uses and of every function that returns it (`GpuError::Refused`).
- **Build properties are asserted at build time.** A design that depends on a property of the build asserts it where the compiler sees it (`compile_error!` against WebAssembly atomics in `audio-wasm`'s FFI). A fallback value is written only where the absence it covers is legitimate.
- **Scripts are tested functions.** Every script is a tested `main(io)` (or the equivalent), with a thin entry point that only wires the real process; the scope gate refuses an unmeasured source unless it is reviewed in `proof-bypasses.txt`. A file only a command-line tool writes can be changed in every field through that tool, and is read back only exactly as the tool writes it, an emptied file refused, the error naming the command that rewrites it; each such file is in the table of `spec/README.md`, "Files only a tool writes", with the test proving its check's reader and the one refusing it emptied (a Rust test there must exist, `spec_names_gate`).
- **Accessibility is audited in every state.** The axe audit runs on every state and rendering branch of a page, enumerated from the type of its states (a `Record` over the state kinds, so that a new state does not compile without one); every style that carries accessibility meaning (focus ring, contrast, hidden text) has an end-to-end assertion on its computed value; a layout law (no sideways scrolling at the narrowest width, nothing clipped) holds in a state showing the widest content each region can hold (a detail without a space, the longest label), not only the content the usual states happen to show; semantics a browser heuristic may drop are explicit in the markup.
- **Documentation follows the code.** `GLOSSARY.md` changes in the same commit as the public name it describes (its synonyms are refused by the vocabulary gate, `vocabulary.txt`); a change that makes an `[Unreleased]` statement false updates it; every command a README gives is one CI runs; `# Errors` and `@throws` name the errors that pass through from callees; a format implemented twice is specified in `spec/` with shared test vectors, the spec listing every input it refuses and the vectors holding at least one per refusal with the expected reason as a literal, each suite reading exactly the keys of the vectors file; a roadmap ticket is cited by its number, checked with `pnpm roadmap show` at each review. A doc describes the state, never its history (no "before", "no longer"), but a dated record of a measurement; a "not yet" names the roadmap step that ends it.
- **What CI cannot run is stated.** A property proven only on the maintainer's machine, or only on one platform, says so where it is claimed (see CI above); a platform CI cannot run has a written test protocol, and the gap is listed among the known deviations.
- **A law comes with the cheat it catches.** A new law, guarantee or gate is added with a counterexample it must refuse (a box that cheats, an input that breaks the claim), shown accepted before the law and refused after it, kept as a regression fixture.
- **A hint is a command.** A message that tells the user what to run names the exact command, in the runnable form `(see: <command>)` the hints gate reads (a remedy in prose, "restore it from git", is no hint, and the prose a fix replaces is retired in `retired-patterns.txt`), and a test follows it in that state and shows it succeeds (`audio-cli`'s hints are the variants of `Hint`, whose test does not compile without a state that gives each). The one exception is a system package (git, util-linux), whose install command depends on the system: its hint names the package (xtask's `TOOLS`), decided 2026-11-17. A command that runs another tool's command passes its options on unparsed and maps the child's usage exit to its own usage exit; it keeps no second table of them.
- **Evidence runs the shipped path.** The laws, fingerprints and equivalence tests run the type and the code path that ship, or a test proves both paths equal bit for bit at every input the evidence uses; a claim of identical bits compares bits, and a type carrying evidence of bits has a bitwise equality or none. A law bounding a quantity the code fixes exactly asserts the exact value, or a bound whose slack is smaller than the regression it guards against, and says which.
- **Measuring nothing fails where the gate exists.** On the machine a measurement gate exists for, a measurement that measured nothing (a capability missing, such as a GPU's clock, a period or a time of 0, a non-finite or saturated value) fails the gate, never passes it or counts as a value; only a machine the gate does not hold skips it, saying so (`visual-gpu check` on a held GPU without a clock, `clock_period`).
- **An absence a source marks is refused in every form the source documents.** A reader of values an external source writes (a GPU's timestamps, an operating system's answer, a device's counter) treats as absent every value the source documents as no value or as an error (0 for a timestamp never written, all ones for Metal's `MTLCounterErrorValue`, a reversed or equal pair), each with a fixture, never only the form first met (`pass_ticks`).
- **A cost bound holds at the special values.** A bound a doc or the spec states on the cost or the steps of an algorithm ("one or two products", "at most n comparisons") is tested over the special values (infinities, not a number, zeros of both signs, subnormals, the largest values) as well as the typical grid; a loop only special values reach is a finding, removed by construction rather than tested around (`straight8`).
- **A limit is tested where it is enforced.** A test of a limit (a dispatch size, a buffer size, a count) runs where the limit is enforced, a device opened at the limit itself, so that code ignoring the limit fails, never only where more is allowed; an assertion a passing sibling test already makes true (a clock present where every test runs on one) is removed, its case tested through its own environment (`encodes_in_rows_of_workgroups_at_any_dispatch_limit`).
- **A fix covers its siblings.** A fix repairs every instance of the structure it repairs (each parallel path, each copy), and its test iterates them. A pattern a fix retires (a weakened assertion, an old wording) is added to `retired-patterns.txt` in the same commit, and `cargo xtask check` refuses it in its scope, every tracked text file searched (the list, the gate's tests and the changelog's released sections apart), across the lines code, a comment or a string a formatter splits wraps it on, through the one reader of logical text (`retired_patterns_gate`, `logical_text`). A retired pattern covers the whole tree; it is narrowed to paths only when its reason says why the rest of the tree may keep it (`; kept elsewhere: <why>`, which the gate requires of every narrowed entry), and each sibling of another wording (a help text in another crate) is retired with it.
- **A used instance is tested as well as a fresh one.** An object that reuses its buffers or states from one life to the next (a path taken up again, a ring rewritten in part) is tested from a used instance as well as a fresh one, and a law compares it with fresh instances over random sequences of its operations (`renders_from_each_rest_as_limiters_always_at_its_lookaheads`). A state rebuilt or carried over is compared from below as well as from above with an instance that always ran (both sides of the law, never one), and the law's control counts the cases of the regime it was written for, so that it cannot pass by never reaching it. A measurement taken on fresh resources (a buffer just created, zeroed) justifies no claim on reused ones; a resource reused from one pass to the next is reset by construction before each use (`run_pass` clears its timestamps before resolving them).
- **A kept state is compared by its values.** A test that a refusal keeps the state it had compares that state's values (bits, bytes, hashes, placements) before and after, never their lengths nor an answer that does not read the state; the refused input differs from the kept state in every field it carries, so that a refusal taking any of them shows. An error is asserted itself, `new X(message)`, never by its class alone, and a predicate over elements asserts the failing elements empty, never `every` as true (both refused by the shared ESLint policy).
- **A configured bound compares exactly.** The comparison of a value with a bound a library or a file configures (a tolerance, a threshold) is exact over everything its reader accepts: the reader refuses what the comparison cannot hold exactly (a fraction, a product beyond 2⁵³), or the comparison runs in integers. A law that reports a missing value names only what is missing, never the values it could not compare for want of it.
- **A sweep asserts what the sweep changes.** A test that loops over a dimension to show the code follows it asserts bits, or values computed by an exact formula, that differ from one value of the dimension to the next, never only a total the swept values cannot change (an area, a count); a loop checking an invariant across values (the area wherever the square is) says so in its name, beside a test that follows the dimension.
- **A number in prose names its proof.** Every bound, cost or failure behavior a spec, a doc comment or the changelog states names the derivation, test or benchmark that establishes it, or says it is not established yet; the largest value a search found is evidence for a bound, not the bound.
- **A rounding budget follows the code's steps.** A bound on the rounding of computed code lists each rounding step it bounds with the precision that step runs in, per format or precision, citing where the code or the spec fixes it (a precision, an order of summation); it is pinned by values computed apart from that list of steps, never by its own expression, and a model of the code that feeds it runs in the same precisions.
- **A stored value passes a flush point, and a tolerance is computed from its formula.** Every value a control path or other state machine stores (a release stage, a share, an applied reduction) passes one point where it is kept or set to zero, never left subnormal: a flush point of decision 11, or a threshold above the subnormal numbers (the limiter's `math::kept`); a value derived only from such values (a running sum, the limiter's Hann sums) is proven zero or normal instead, its proof naming each operation (`spec/measurements.md`, "The true-peak limiter", step 7); so that the state is the same on a host that flushes subnormal numbers as on one that keeps them (decision 11; held by `differs_on_no_host_through_a_release_tail`, which compares the whole state across hosts frame by frame). A tolerance a derivation gives is computed in its test from the derived formula and the real constants (the limiter's `hann_sums_bounds`), never a constant typed beside the derivation.
- **A changed decision changes everywhere.** When a decision of `spec/` changes, the same commit searches every versioned file for its old wording (READMEs, doc comments, this file, the roadmap, the glossary) and updates each restatement, and adds its `[Unreleased]` line.
- **"Checked" names its checker.** A claim that something is checked names the gate or test that checks it, and claims exactly what that gate covers. A gate over text reads it as it is written, wrapped, through one reader of logical text (the `logical_text` module of xtask): a sentence, a term or a citation is read whole across the lines of its paragraph or comment block, a string across the lines a formatter splits it on (a Rust `\` and the next line's indentation, a TypeScript `+`), and code as one line up to a blank line, never one line at a time; every refusal fixture of every such gate is refused in every rewrap of it too (the rewrap law over the table of text gates, `text_gates`, `rewraps`). A doc never restates what a typed list holds, neither its count nor a copy of its entries (a register, a constant array, a table of modules or paths): it names the list, or a family of paths by a pattern (`crates/visual-*/`), so that an entry added later cannot leave it stale (`module_table_gate` holds the packages' module tables, `list_counts_gate` refuses a sentence that names such a list, a constant array of strings or a register at the root, and writes its current count, in the files of its filter, `citation_sources`, the released changelog apart).
- **A gate's inputs are one named list, held to what exists.** The files a gate reads are a filter of one table of kinds (`SOURCE_KINDS`: what of a file is prose, whether it is code, whether Stryker mutates it, or why no gate of code reads it), and every tracked file is of a kind it names (`source_kinds_gate`); a list a step derives from the code (the files it mutates, the inputs that run it) is asserted against that code or against every source of the crates it covers (`corpus_sources_gate`, the corpus inputs test); every file of reviewed exceptions passes the names and reasons gates of the unviable reviews.
- **Neutralize and ban by family.** A list of settings a tool is run with to neutralize a user's configuration, or of variables the preflight refuses, is read against the tool's own families of settings (each command's colors and formats, not only the global switch), and its test reads every command it claims in its plainest form; a banned method bans each sibling with the same flaw (`DirEntry::file_type` and `DirEntry::metadata`).
- **A mechanism that only some versions have names its version.** Code relying on a tool's mechanism that older versions ignore or lack (git 2.31's `GIT_CONFIG_COUNT`) names the version beside it, and the preflight refuses an older one, or the roadmap step that will is cited there.
- **Twin readers are tested as twins.** Two implementations reading the same format (a Rust reader and the oracle's) each have a seeded random-input test, and a differential test between them, or a roadmap step that records when it comes.
- **A bound that depends on the machine is measured where it runs, or observed.** A bound on a time or on anything else the machine decides (a GPU's time, a repaint interval, a clock's step, an adapter's behavior) is derived from distributions measured in every condition its check runs in (idle and under the load of a concurrent check, each machine and browser), recorded with their dates and conditions, and computed in its test; where the test can see the quantity itself (the repaints it recorded, the clock samples it read), it asserts against what it observed in the same run, never against a constant measured once on one machine.
- **One cause per absence.** A value absent for one reason only may be `undefined` (`None`); one absent for several (not yet, refused, lost, unmeasured) is a discriminated union naming each cause, so that callers and messages tell them apart; a missing measurement is never a value (0, a default).
- **A function over unknown values is total.** A function that takes an `unknown` (a caught error, a message, a parsed value) terminates and never throws on any value, proven by a property test over arbitrary values, cycles, throwing getters and deep nesting included.
- **An identity claim names its last proven point.** A claim of identity (the same bits, bytes or images on every target) names the last point a test proves it at (the module's output, a canvas's bytes); what may change them after that point (a browser's resampling, a display's color management) is recorded in `spec/limitations.md`.
- **Tests prove presence.** A test proves a state by asserting it exactly (its exact name, text, attribute or value), never by the absence of the state before it, nor by a pattern several states would match (a regular expression alternation, an inequality to the old value).
- **A claim about a third party cites its source and its gaps.** A claim of how a service, a browser, a platform or a tool behaves (what Dependabot groups, which browser has a WebGPU adapter on Linux) cites the third party's documentation or a recorded run (its date and where it ran), and says which cases it has not observed; a table of such behaviors written before any run says it is unmeasured, and the first run writes what it saw and its date.
- **A decision lands with its log row.** A commit that carries a maintainer's decision writes its row in the decisions log of the local design notes (`doc/architecture.md`, through the manager session, which commits them) in the same pass, and marks every row it amends or supersedes; a part renamed, added or split updates the architecture sections of those notes (the crates, the workspaces, the audited files) in the same pass.

### Deep review
`/deep-review` (`.claude/skills/deep-review/`) runs an exhaustive multi-agent review along every quality axis (seventeen, scientific rigor and edge cases included), verifies each finding adversarially, then analyzes each one (admissibility, options, trade-offs) before anything is applied. Run it at the end of each review block, on the branch after its green default check (the green `--full`, the pull request's CI, comes after the review's fixes, before the merge; see Working in blocks), and before closing a roadmap ticket and before every release, each of these two with a green `cargo xtask check --full` first; a version that is not a release needs none. No finding is applied without the maintainer's decision and a fresh analysis at the moment of applying it. Every review also turns the classes of defects it reveals into lessons: each finding's analysis names its class, and its fix adds what covers the class, not only the case found (a law, a property test over generated inputs, an exhaustive sweep, a gate, a lint, a type), otherwise a rule in this file, worded to apply beyond the case that revealed it. No finding is left without a disposition: fixed, or deferred as a roadmap step in the same pass.

### Transparency
Results are meant to be published for every release: coverage, mutants, per-target conformance hashes, known deviations.

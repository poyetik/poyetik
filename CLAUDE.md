# Poyetik

## Language: English only

**Everything in this repository is written in English**: code, identifiers, comments, CLI output, UI text, tests, documentation, roadmap tickets, commit messages, PR descriptions, CI and hook output. No exceptions.


## Guiding principle: maximum proof

We want **the maximum proof we can get**, everywhere, at all times. Every property we claim must be backed by an automated check that runs in CI and in the pre-push hook (which proves only the mutants of the changed code, and every mutant when a tag is pushed; see CI). In order of preference:

1. **Impossible by construction**: the type system, the compiler or the tooling makes the mistake unrepresentable or uncompilable (`no_std`, `forbid(unsafe_code)`, newtypes, unions of literals, banned methods, no casts).
2. **Formally checked**: model checking or proofs where it is feasible (Kani, Miri).
3. **Exhaustively tested**: 100% line and branch coverage, no surviving mutant, property tests, fuzzing, cross-target conformance.
4. **Reviewed**: only for what none of the above can reach, and documented as such.

When in doubt, choose the stronger guarantee, even if it costs more work. A shortcut that weakens a guarantee is never acceptable.

## Goal

A visual audio patching environment (boxes connected by cables) running in the browser, with a Rust engine (WebAssembly on the web, native elsewhere).

A finished patch can be exported natively, user interface included, to: web, macOS, Windows, Linux, iOS, Android, plugins (VST3, CLAP, AU…), and embedded audio boards (microcontrollers, and single-board computers running Linux), without a user interface or with their own controls.

Core promise: **the engine produces exactly the same samples, bit for bit, on every target**. A strict, public testing policy proves it.

## Audio DSP: the objective

**State-of-the-art audio quality, measured, on every target.** Every box sounds as good as the best professional implementations of the same process, and proves it with numbers in its tests; bit-exact determinism is never traded for it, nor the reverse.

**Before any engine or box change, read `spec/engine-design.md`** (the decisions, and the step that implements each) **and `spec/measurements.md`** (the measurement definitions, and how thresholds are derived). A change that contradicts the spec changes the spec first, with the maintainer's decision.

- **Quality is measured, not claimed**: every box, and every engine component that touches the signal (the resampler, parameter smoothing, the output-stage limiter, latency compensation, hot-swap crossfades, event timing), has objective measurements with thresholds (spectrum, aliasing level, THD, SNR, frequency response, behavior under parameter changes), compared with high-precision references (double precision or arbitrary precision). Each threshold is derived from first principles, with its derivation next to it, as `spec/measurements.md` defines; an engine component's measurements land with the step that builds it (`spec/engine-design.md`).
- **Known pitfalls are handled by design**: aliasing (band-limited synthesis, oversampled non-linearities), zipper noise (smoothed parameters, sample-accurate events), unstable filters under modulation (topologies such as TPT / zero-delay feedback), subnormal numbers (a deterministic strategy, since WebAssembly has no hardware flush-to-zero), DC offset, numerical precision of phases and coefficients.
- **Real time is a hard constraint**: no allocation or release of memory, lock, I/O or unbounded work in `process`, nor anywhere on the browser's audio thread. Two known exceptions, tracked by roadmap #12: a processor and its WebAssembly instance belong to the audio thread, so constructing the engine processor compiles the module, instantiates it and builds the plan there, once, before it renders (to be bounded and measured by steps 3 and 30, as `spec/engine-design.md` decides); and the playground's oscilloscope runs the tap processor, which copies and posts every render quantum while it plays (until step 21).
- **Cost is measured**: benchmarks per box in CI with regression thresholds; an approximation replaces an exact function only when measurements prove it is both faster and within threshold.
- **Engine design decisions come first**: messages, event scheduling, feedback, polyphony, multichannel, rates, parallelism, hot swap, latency and state are decided and recorded (in `spec/engine-design.md`) before the code that depends on them.

## CI

**One command runs every check: `cargo xtask check`** (Rust formatting, lints, tests, portability builds, 100% coverage gate, mutation testing, Miri, conformance, supply chain, then every TypeScript package: the shared policy itself, each rule proven to reject what it forbids, the oracle, the engine in the browser, the playground and the roadmap). It has two modes, which differ only in mutation testing, in whether a failure stops the run, and in the order of the steps (`Mode` in xtask; `cargo xtask list [--full]` lists the steps of each): the default check runs the full check's steps cheapest first (`cheapest_first`), an order that changes no outcome; `--full` keeps its order. Every step and the check say their elapsed time (`run_steps_then`). A third command mutates one target:
- **`cargo xtask check`** (the default, for development; the `.githooks/pre-push` hook runs it through `cargo xtask pre-push`, which first refuses uncommitted changes and a pushed commit other than the one checked out, `pre_push_gate`, and runs `--full` instead when a tag is pushed, since a release requires it): Rust mutants only in the lines changed since the merge base (`MUTATION_BASES`; no base, the check fails), uncommitted changes and new Rust files included, a file git hides from its diffs refused (`hidden`), no change, no mutant (`rust_mutants_of_changes`); widened to every mutant of a crate whose test code or declared test data changed (test code lives only in `tests/` and declared `*_tests.rs` files: `test_code_gate`, and `loaded_files_gate` over the files rustc itself read; test data are `RustCrate::test_data`, the only files outside its crate a crate's tests may read: `test_data_gate`, where a path computed at run time is review only), to every crate a change of a shared input reaches, and to every Rust mutant when what every test depends on changed or a change cannot be narrowed, said with the reason (`widening`, whose `Widening` holds the table, and `reach`); in the parallel jobs of `--full`, with the unviable-mutant gate refusing every unreviewed unviable mutant it generated, then every stale review (`unviable_reviews_gate`); TypeScript mutants through Stryker's incremental mode (`STRYKER_INCREMENTAL`), which reruns the mutants whose code or covering tests changed and reuses the earlier results of the others, so its report and the TypeScript gates still cover every mutant. It proves that the changed code has no surviving mutant under the tests as they are now. It does **not** prove what only the full check sees: a Rust mutant outside the changed lines that a change elsewhere (a test weakened, a callee changed) now lets survive, and a TypeScript result reused although something Stryker does not track changed (a test helper or fixture, a configuration, a dependency, the WebAssembly module). **A green default check does not imply a green full check.**
- **`cargo xtask check --full`**: every mutant (cargo-mutants in parallel jobs, `mutation_jobs`, as in the default mode; Stryker's `--force`, which also rewrites its incremental file), and the unviable-mutant gate refuses stale reviews after its complete run. It runs every step whatever fails, then reports every failure at once (one stdout line per failed step, one `error:` line counting them), while the default check stops at the first failure. `.github/workflows/quality.yml` runs exactly this, split into parallel jobs: one per part of the full check (`cargo xtask list --full --parts`; `cargo xtask check --full --part <part>`: the Rust checks, the Rust coverage, Miri, the gates, each TypeScript package, and each mutation shard of the Rust mutants, cargo-mutants' `--shard`), then, once every part has passed, a final job that reviews the unviable mutants of every shard together, stale reviews included. The parts gate proves that the parts run every check step of the full check once (only preparation repeats), and the workflow gate requires the workflow to be exactly the one xtask defines (`workflow_text`: its matrix lists exactly those parts, every job holds the `[ci]` condition), up to its comments, its blank lines and the commit hashes of its actions with their tag comments. It is **required** before a release (a tag), at the end of a review block, before its merge (its pull request's CI run), before closing a roadmap ticket, for a deep review (except a review block's, which comes before it, see Working in blocks), and whenever a change can weaken tests or code it does not touch (test helpers, fixtures, configurations, dependencies, the engine under the TypeScript packages); a green CI run counts.
- **`cargo xtask mutants <target>`**, for development: every mutant of one target, a crate by its name (`cargo mutants --package`), a Rust file of a crate (`--file`), a TypeScript package by its directory (Stryker on the whole package, which also rewrites its incremental file) or one of its sources (Stryker's `--mutate`), then the gate on that report, as for a partial run (no stale review; no mutant at all is accepted, except for a whole package). It proves that target only, and never replaces a check.

Every build cargo-mutants makes, in both modes, in every part and in `cargo xtask mutants`, differs from every other build of the checks only by dropping debug information and capping lints (`MUTANTS_ARGS`), neither of which changes the code generated (reviewed: `MUTANT_BUILD_CONFIG`'s doc holds the comparison and the review). Each choice made for the check's speed beyond what the default check leaves to the full check (above) is recorded with its measurement and its argument that it changes no outcome in `crates/xtask/README.md`.

The default check also keeps a **mutation proof record** (`ProofRecord`): when its Rust mutation testing and the unviable gate pass on a clean tree (`unclean`: the cleanliness the pre-push hook requires, nothing changed while it ran), it records what it proved, in git's common directory, shared by every worktree. A later default check of the same base and host skips every crate whose inputs (its files, those of every crate of the workspace it depends on, its declared test data) are byte-identical to the recorded commit; every other crate is mutated exactly as without a record, from the changes since the base widened by the same function (`reach`), so **a record never changes what the default check proves**; each crate skipped that the check would otherwise have tested is named. A record is ignored, with one line saying why, when it cannot be read or when anything it is keyed on changed (`usable_proof`, `proven_crates`; `ProofRecord` and `ProofTools` name each input); only a missing record is passed over in silence. Review only: the shell xtask's tests run, which no record can name (`ProofRecord`). The record is optional: when the environment refuses it, the step says `not recorded: <reason>` and succeeds (`record_mutation_proof`). `cargo xtask check --full` and CI never read nor write a record; the pre-push hook benefits locally only.

So a green full check locally differs from a CI run only by platform (the limits of its runner, below); a green default check means only that the changes are proven. **CI runs on demand**, since the full check is long and commits are frequent: on a push only when the last commit's message holds `[ci]` alone on a line (Claude adds that line when the maintainer asks for CI; the commit-msg hook and the history gate refuse the marker anywhere else, since GitHub's condition can only search the whole message), on every pull request, and by hand (Run workflow on GitHub). The repository allows rebase merges only (a maintainer setting on GitHub), so that no merge commit enters `main`; the history gate accepts the one merge GitHub writes to run a pull request (`Merge <commit> into <commit>`) only as the commit checked out, never anywhere else in the history.

Working while the check runs: when it is useful and harms nothing, development may continue in a separate git worktree (`git worktree add`, its own branch) while `cargo xtask check` validates a finished commit in the main one, since the check (mutation testing above all, the full check most) takes a long time. It is an option, not a habit: skip it when the next work depends on the result, or when the extra load would disturb the check (load-sensitive browser tests). The validated commit is not done, and the work built on it is not pushed, until that check is green; a failure is fixed by a new commit, validated again.

What CI runs on, and so proves, is limited by its runner: an x86_64 Linux machine; each green run proves what this section says CI proves, for the commit it ran on. Native conformance (the same hashes as WebAssembly) is proven in CI on x86_64 Linux only; on aarch64 (macOS on Apple silicon) it is proven by the pre-push check of a Mac, and only cross-compiled in CI; the native shell (`engine-cli`) and the library's floating-point mode it uses (`engine-fpenv`), whose code differs by architecture, are linted (Clippy, which type-checks) and their libraries built (code generated and inline assembly assembled, nothing linked) for both architectures on every machine (xtask's `NATIVE_TARGETS`), so CI compiles and assembles their aarch64 code and a Mac their x86_64 code, which only the other runs. "WebKit" in the browser tests is Playwright's WebKit (WebKitGTK on Linux), not Safari, and "mobile WebKit" is the same engine at an iPhone's size and user agent, not iOS Safari. The runner has no sound card: every job that runs a part of the check (the `check` job's matrix; the final job plays nothing) starts an audio server with a null sink as its default output (xtask's `AUDIO_SINK`), through which Firefox plays live, while Chromium runs with its audio output disabled; so in CI, live playback is proven to reach an audio output, never a device, and a local check uses the machine's own output, unchanged. A macOS job (roadmap #20) and checks on real phones (roadmap #18) are planned; until then, a claim that needs aarch64 or Safari rests on the pre-push check of a Mac.

Every new check is added to `xtask` (`check_steps`), never directly to the hook or the workflow. The hook is enabled through `core.hooksPath`, set automatically by `pnpm install` at the root. **The hooks are never bypassed by default.** One exception, decided by the maintainer: when the maintainer explicitly asks for it for a given push, Claude may skip the pre-push check (`git push --no-verify`) and says so; the commits pushed that way are not validated until a later `cargo xtask check --full`, local or a CI run, is green (after the push, the default check finds no change and mutates nothing). The commit-msg hook is never bypassed (`git commit --no-verify` stays forbidden).

### Working in blocks
- **Large tickets are done in review blocks**: each block is a branch with one commit per logical change. Every step of the block gets targeted checks chosen for what it touched (tests, Clippy and formatting of the touched crates and packages, the tests of every crate and package that depends on a changed one, since a dependent's own fakes or uses may break where the changed one's tests pass, `cargo xtask mutants` on the changed files, browser tests when the engine under them changed; listed in the step's report) and a light targeted review (blocking problems fixed, the rest added to the hardening card), and its roadmap step is ticked on the branch (`main`'s board may lag until the merge).
- At the end of a block, in this order: (1) the default `cargo xtask check` on the branch; (2) a **deep review** of the branch's diff against `main` (no pull request yet), scoped by the spec decisions and roadmap steps of the block, the maintainer deciding on every finding; (3) the decided fixes, with targeted checks; (4) the **pull request**, whose CI run (the full check) runs once on the final state and must be green: it is the block's `--full`; (5) the version commit and the **rebase merge** into `main` (no merge commit).
- For roadmap #12, the blocks end at steps 8, 18, 31 and 38 (their titles carry the end of the block). A block's last step is ticked by the last commit of its fixes, before the pull request, not with its targeted checks, since its title claims the review.
- Small changes outside a block (docs, roadmap, a fix) may go to `main` directly, with their version number and the usual checks.

## Command-line tools

Every command-line tool of the repository (`engine-cli`, `cargo xtask`, the oracle, the roadmap CLI, and every one to come) follows one contract, tested on the real entry point:
- exit code 0 on success, 1 when the work failed, 2 for a usage error;
- every error is one line on stderr, `error: ...`, naming the file or the command involved; never a stack trace;
- a usage error says what is wrong and where the usage is, `error: <reason> (see: <tool> help)`; only `<tool> help` prints the usage, on stdout;
- a closed stdout (`| head`) is never an error and never changes the exit code, for the commands a tool starts too as long as stderr stays open (`cargo xtask` writes their output to its stderr);
- a tool with several problems to report prints them on stdout, one per line, and one `error:` summary on stderr (for `cargo xtask`, the problems of the commands it runs come with their output, on its stderr, but `cargo xtask bless`, which replays `engine-cli bless`'s result lines, then its error output, on its stdout);
- untrusted text quoted in an error (a box name, a field of a document) is escaped and bounded, so that it can neither drive the terminal nor forge a second line.

## Portability

**The engine core is fully portable: no platform-specific code, ever.** `engine-core` (and every crate it will be split into) is `no_std`, has no OS, clock, thread, file, network or JS access, and builds for every target. Everything platform-specific (audio I/O, files, permissions, UI hosting) belongs to the thin shells around it (`bindings/`, native players, plugin wrappers, Tauri apps).

This is proven, not assumed: `cargo xtask check` builds the core and the boxes (`engine-objects`) for macOS (ARM), Linux (x86), WebAssembly and a bare-metal ARM microcontroller with no OS at all.

## Technologies and dependencies

- **As few as possible.** Every dependency (library or tool) is a liability: prefer the standard library, then a tool or library already used in the project, then a new one.
- **Modern, mainstream and well maintained.** Only widely used projects with active maintenance and a healthy community. Nothing obscure, experimental or abandoned.
- **Every dependency is justified** in `dependencies.txt`, the dependency register: every direct dependency of a crate or a package with its reason (what it is for, why it is needed), which `cargo xtask check` requires to match the manifests exactly. Adding one means adding its line first. The local `doc/architecture.md` keeps only the strategic reasons (why this one rather than another, what it commits the project to).
- Versions are locked (`Cargo.lock`, `pnpm-lock.yaml`) and the toolchains are pinned. A dependency whose code computes output samples or hashes, or the values they are computed from, is **bit-defining**: its line in `dependencies.txt` gives a reason starting `bit-defining: `, every normal or build dependency of the audio library is one, and each is pinned to one exact version (`=X.Y.Z`), its updates following `spec/engine-design.md` decision 29 (checked for the direct dependencies; the code they reach in turn is fixed by `Cargo.lock`, which every check builds with, and proven by the render hash vectors, conformance and the fingerprints, a change of it in the lock file being an update too).
- **The audio library stands alone** (the crates of xtask's `RUST_CRATES` holding `CrateRole::Library`, `spec/engine-design.md` decision 32): its crates depend, within the project, only on each other, and their tests also on `engine-testkit`; never on the native shell, xtask, the apps, the tooling or the layer above it, which uses it only through its public interface (checked).
- **No architecture choice costs performance** (`spec/engine-design.md` decision 33): libraries are crates of one program and one WebAssembly module, their interfaces take blocks and borrowed slices with no dynamic dispatch on hot paths: a plan calls the built-in boxes directly (`engine_objects::BuiltIn`), and only a box type loaded at run time through its virtual table, once per box per block, never per sample, none in build mode (measured, dated in `spec/benchmarks.md`: fewer instructions per box per block for slightly dearer plan loading, the real-time path coming first), and a box or the engine costs the same directly and through an interface, held by the benchmarks (`spec/benchmarks.md`): within the counts' tolerance today, exactly or within a per-call allowance written for each interface once its comparison lands (roadmap #12 step 13, #32 step 8).

## Strict typing and linting policy

Non-negotiable, and **enforced by tooling, not by goodwill**: CI and the pre-push hook reject any violation (the hook's mutation testing covers only the changed code, every mutant when a tag is pushed; see CI). No shortcut may weaken the whole.

### Principle: parse at the boundaries, trust types inside
- External data (JSON, CLI arguments, files, network, FFI) enters as `unknown` (TS) or raw bytes (Rust) and is **validated once, at the boundary**, by functions that *prove* the type (TS type guards, Rust constructors returning `Result`).
- Every limit a specification states (a size, a range, a count) is enforced at the earliest point, before the input is held whole, by a type of fixed width where one fits (never a pointer-wide type, whose range differs between targets), and is tested at the limit and one past it. Every reader of one format accepts and rejects the same documents, checked on a shared corpus.
- Internal code only accepts proven types and **never re-checks** what the type system already guarantees. Invalid states must be unrepresentable (unions of literals, newtypes, private fields with checked constructors).
- If a value cannot be typed precisely, fix the types. Never silence the checker.

### TypeScript
- `tsconfig`: the strictest settings (`strict`, `noUncheckedIndexedAccess`, `exactOptionalPropertyTypes`, `noPropertyAccessFromIndexSignature`, `verbatimModuleSyntax`, `isolatedModules`, `erasableSyntaxOnly`, `useUnknownInCatchVariables`…), shared by every package through `@poyetik/config` (`tooling/config`); the roadmap extends Astro `strictest` with the same extras.
- ESLint: one configuration for every package, `@poyetik/config/eslint`; a package only adds what its framework needs (React hooks rules).
- ESLint: `strictTypeChecked` + `stylisticTypeChecked` with zero warnings, plus:
  - **no type assertions** (`as T`, `<T>x`), except `as const`, and no non-null assertions (`!`);
  - **no `any`**, explicit or implicit;
  - **no `@ts-ignore`, `@ts-expect-error`, `@ts-nocheck`**;
  - **no inline `eslint-disable`** comments: a rule is either respected or changed in the config, for everyone, with a reason;
  - strict boolean conditions (no truthiness on strings, numbers or nullable values), exhaustive `switch`, explicit types on exported functions, no `enum`, `readonly` where possible, type-only imports.
- Tests follow exactly the same rules: no casts to reach "impossible" states. If a state is impossible by type, it needs no test and no runtime check.

### Rust
- Pinned toolchain (`rust-toolchain.toml`), edition 2024, `rustfmt --check`.
- Workspace-level lints, inherited by every crate, all as errors:
  - no `unsafe` code anywhere (`#![forbid(unsafe_code)]`) except the three minimal, audited files of xtask's `UNSAFE_FILES`, the only ones lifting the lint: every crate root and module forbids it, but the roots of their crates, which stay under the workspace's `deny`, and the unit tests an unsafe file declares, which stay under its lifting (`unsafe_gate`), so that the compiler refuses any other lifting; and since rustc does not lint code expanded from another crate's macro, no Rust file but those and the unit tests they declare holds the keyword `unsafe`, nor any file `global_asm!` or `naked_asm!` (`unsafe_gate`, in tokens; the workspace holds no procedural macro or build script, `untested_targets_gate`, so only `macro_rules!` macros and third-party macros expand into it, the latter left to the dependency review); every library root forbids unsafe code in its doc tests, which are crates of their own (`#![doc(test(attr(forbid(unsafe_code))))]`, what they load being review only); every crate inherits the workspace lints, and `.cargo/config.toml` holds no build flag. They are the FFI module of `engine-wasm`, and the counting allocator `engine-alloc-counter` (test-only, every call delegated unchanged to the system allocator), which proves that boxes never allocate while processing, both checked by Miri; and the control-register file of `engine-fpenv` (native only, `x86_64` and aarch64), which sets the processor's default floating-point mode around native engine calls (`spec/engine-design.md`, decision 11). That third file is inline assembly, which Miri cannot run (`ASSEMBLY_FILES`; `unsafe_gate` keeps each of its `unsafe` blocks to one assembly call and lets no other code of its crate run unsafe under its lifting): it is proven by its crate's tests (`lib_tests.rs`, whose module doc lists them; 100% coverage and no surviving mutant) on the architecture that runs them, `x86_64` in CI and aarch64 only by the pre-push check of the maintainer's Mac until the macOS job (roadmap #20), and by the review written in the file (`word.rs`: the instructions, the reserved bits, and Rust's floating-point rule, which its writes and the crate's tests under forced modes break on purpose, with why);
  - `missing_docs`, `unused_results`, `unreachable_pub`, `rust_2018_idioms`;
  - Clippy `all`, `pedantic`, `nursery` and `cargo` groups, plus selected `restriction` lints: no `unwrap`/`expect`/`panic!`/`todo!`/`unimplemented!`, no `as` numeric casts (use `From`/`TryFrom`), no indexing that can panic, no equality on raw floats (`float_cmp`: the ban targets `f32` and `f64`; exact equality of the engine's sample types is allowed by design, the same IEEE equality on every target, and reviewed, `spec/engine-design.md` decision 10), no `dbg!`/`print!` in library code, no struct mixing public and private fields (`partial_pub_fields`: a type that keeps an invariant keeps all its fields private), no lint suppressions (`#[allow]`) without an explicit, reviewed `reason`.
- Determinism rules as Clippy `disallowed_methods` / `disallowed_types` (`f32::sin`, `mul_add`, `Instant::now`, `HashMap` with random state…).
- Supply chain, by `cargo xtask check`, whose configuration is xtask's (`supply_chain_gate`: an advisory ignored, a crate skipped, a release age shortened or an exclusion from it is a change of xtask): licenses allowed only as listed (Rust: `deny.toml`; JavaScript: xtask's `SHIPPED_LICENSES` for what the apps ship, plus `TOOLING_EXTRA_LICENSES` for development tooling), no known vulnerabilities (`cargo-deny`, `pnpm audit`), no duplicate crate (`cargo-deny`), no unexpected direct dependency (`dependencies.txt`).
- Coverage 100% lines, functions and branches (`cargo-llvm-cov`; branch coverage needs a pinned nightly, `nightly-2026-11-01`, used only for it, Miri and the float-method audit, which reads its `rust-src`), reached by **each crate's own unit tests**: `cargo xtask check` measures each crate of `RUST_CRATES` alone (`--lib`), so a path exercised only from another crate or an integration test is not covered (a fixture crate proves the gate refuses it). The gate reads llvm-cov's summary, which merges the instantiations of a generic function: a branch counts as covered when any instantiation takes it, so a path taken in one precision only, or by one caller's type only, is not seen (roadmap #24 step 87). The one exception is a binary's `main.rs`, which unit tests cannot reach: it is measured by its crate's tests. No target or manifest setting may leave a test unbuilt or unrun: a target turns its unit tests off only if its root declares no module, so that no test can hide in it, and no library turns its doc tests off (`untested_targets_gate`, whose doc lists every setting it refuses; the `harness` key is refused by the bypass gate unless reviewed in `proof-bypasses.txt`). Code no test can reach is removed by construction, not tested around.
- **No surviving mutant** (`cargo-mutants --cap-lints=true`, so that mutants are never skipped because of lints), and Miri on any `unsafe` but inline assembly, which it cannot run (the control-register file above, proven by tests and audit instead).
- **Every unviable mutant (one that does not compile) must be reviewed.** Confirm that the type system or `no_std` really makes that wrong implementation impossible, and that no legitimate variant of it escapes the tests; then record it with its reason in `mutants-unviable.txt` (every function a reason names, such as the test that kills the viable variant, is checked to exist in test code). `cargo xtask check` fails on any unreviewed unviable mutant it generated, and on any stale entry (the default check against cargo-mutants' `--list` of the workspace, the full check against its complete run), so the list always matches reality.

## Documentation, versioning and commits

Enforced by `cargo xtask check` and the git hooks, like everything else.

### Documentation
- **Every item is documented**, public or private: Rust `missing_docs` + Clippy `missing_docs_in_private_items`; TypeScript JSDoc on every named item, exported or not: functions, classes and their members, types, module-level constants (`eslint-plugin-jsdoc`, `publicOnly: false`).
- Docs explain **why and what**, not only how: purpose, invariants, units, errors (`# Errors` sections in Rust), panics (there must be none).
- `cargo doc` runs with the rustdoc lints as errors: no broken or private links, no invalid code blocks, crate-level docs required.
- `README.md` and each part's `README.md` explain what it is and how to run and check it (checked: every TypeScript package has a README, every part is named in the README of its folder, every folder in the root README); `GLOSSARY.md` holds the words of the project, one word per concept, and `cargo xtask check` refuses in the prose of the repository (Markdown, the comments and string literals of Rust and TypeScript, and the string values of the JSON files under `spec/` and `conformance/`; the released sections of `CHANGELOG.md` apart, which stay as `main` holds them, `released_sections_gate`) the synonyms it replaces, as listed in `vocabulary.txt` with the contexts where each is allowed; the local `doc/architecture.md` holds the architecture, the strategic reasons of the dependencies and the decisions log. Every architecture decision adds a line to that log.

### Versioning and changelog
- **One version for the whole project**, following [Semantic Versioning](https://semver.org): the workspace `version` in `Cargo.toml` and the `version` of every `package.json` must match (checked).
- **Every notable change adds an entry under `## [Unreleased]` in `CHANGELOG.md`**, in the same commit ([Keep a Changelog](https://keepachangelog.com) sections: Added, Changed, Deprecated, Removed, Fixed, Security). `[Unreleased]` describes the change from the last release, never the history of the branch: an entry for a state added and changed again before the release is rewritten, not appended to, and nothing is listed as removed or changed that the last release did not have; each Breaking entry names the public signatures it changes against the last tag (`git show <tag>:<file>`). The changelog format is checked: `# Changelog`, `## [Unreleased]` first, then `## [X.Y.Z] - YYYY-MM-DD` in strictly decreasing order, never newer than the project version.
- **Every push to `main` carries a new version number** (decided 2026-11-09), chosen exactly by Semantic Versioning: while the version is `0.x`, the minor version for new features or breaking changes, the patch version for fixes only; from `1.0.0` on, a breaking change bumps the major version. The push's last commit is its version commit: it moves the `[Unreleased]` entries under a new `## [X.Y.Z] - date` heading and sets the version everywhere the version gate checks. A version is not a release: no tag and no GitHub release for it.
- **A release is a tag `vX.Y.Z`** on a version commit, made only when the maintainer decides. It requires a green `cargo xtask check --full` (the pre-push hook runs it when a tag is pushed; a green CI run counts) and a deep review.

### Commits
- **[Conventional Commits](https://www.conventionalcommits.org)**, in English: `type(scope)!: summary`, with type one of `feat`, `fix`, `docs`, `test`, `refactor`, `perf`, `build`, `ci`, `chore`, `style`, `revert`; optional scope, one name per part (xtask's `commit_scopes`: a crate by its name, a package by its folder or the crate sharing it, `engine-wasm`, or one of `COMMIT_SCOPE_EXTRAS` such as `spec`; held to that list from `SCOPES_SINCE` on); `!` for breaking changes; header of at most 72 characters, no trailing period, a blank line before the body.
- Checked by the `.githooks/commit-msg` hook (`cargo xtask commit-msg`). One logical change per commit; never commit a red `cargo xtask check`.

## Testing policy

Non-negotiable. A change that does not meet these rules is not done.

### Principles
- **No code without tests.** For the engine, the test is written first and must fail before the implementation.
- **Every bug fix starts with a regression test** that reproduces the bug and fails.
- **Tests are deterministic**: no system clock, no `sleep`, no network, no unseeded randomness, no dependency on execution order. A flaky test is a bug to fix, never something to re-run until it passes. The one exception to the clock: the wall-time benchmarks of `spec/benchmarks.md`, asserted only as upper bounds with a derived margin, in the end-to-end tests, read through the bench page's timing module. Enforced by tooling: the shared ESLint policy refuses the clock reads it lists (`@poyetik/config`'s `eslint.ts`) outside its reviewed `CLOCK_READERS` (that module, and the roadmap command's entry point, which stamps today's date); a clock reached another way (an alias, `Reflect.construct`, a computed or spread form, `performance.timeOrigin`, an event's `timeStamp`) is beyond a syntax rule and left to review; and Clippy's `disallowed-methods` refuses `Instant::now` and `SystemTime::now`, but in xtask's `SystemRunner::clock` (a reviewed `expect` with its reason): the elapsed time the checks print, which decides nothing, and whose one test asserts only that the clock advances across the start of a process.
- **Never work around a test**:
  - do not delete it, disable it (`#[ignore]`, `.skip`) or weaken it;
  - do not lower a threshold or widen a tolerance;
  - do not update a reference hash to make CI pass.
  If a test looks wrong, stop and discuss it.
- **CI is the source of truth.** A single local command reproduces CI exactly: `cargo xtask check --full`.

### Scope: the whole project
Maximum testing applies to **all code, in every language**: Rust engine, patch model, WASM/worklet glue, web editor (TS), native shells (Swift, Kotlin), plugin wrappers, build service, AI assistant, tooling scripts. Nothing is "too simple to test".

### Measured requirements (all code)
- **Coverage: 100% of lines and branches** (`cargo-llvm-cov` for Rust, the equivalent tool for each other language). CI fails below that.
- **Mutation testing: no surviving mutant** (`cargo-mutants` for Rust, Stryker for TS, the equivalent tool elsewhere). A truly equivalent mutant is disabled by a `// Stryker disable next-line <Mutator>: <reason>` comment and listed with its justification in `mutants-equivalent.txt`; `cargo xtask check` fails on any disable comment not listed, any stale entry, and any broader disable. That list is public and reviewed. Every TypeScript mutant must be killed (or time out); one with another status (a runtime error included) fails the check, unless it is ignored exactly where a listed disable comment says so. Any other bypass of a proof (a skipped mutant, an ignored or focused test, a coverage exclusion, a mutation-tool configuration or a Stryker setting that hides mutants) is refused by `cargo xtask check` unless it is reviewed in `proof-bypasses.txt`; so is every TypeScript source of a package, tests apart, that its coverage does not measure or Stryker does not mutate (the scope gate: a package's coverage `include` and Stryker `mutate` select the same sources, and every other source is reviewed there). Stryker always runs `stryker.config.json` (named on its command line; a package script may run it only as `stryker run stryker.config.json`), and every source it should mutate that has statements must appear in its report, or be reviewed there too. That register holds only tool configurations, entry points and browser shells that wire measured code, the Astro templates Stryker cannot mutate (roadmap #15), and sources of constants Stryker has no mutator for; prefer moving code under the proofs to adding a line.
- **Strict static analysis**: `clippy -D warnings`, `rustfmt --check`, TypeScript `strict` with no `any`, ESLint with zero warnings, no exceptions.
- **Supply chain**: `cargo-deny`, `pnpm audit` and xtask's license gate (licenses, vulnerabilities), locked dependencies, every direct dependency reviewed. The provenance of npm packages is not checked yet.

### Behavior tests
- **Reference renders**: every box has test patches rendered offline (patch + events + seed → samples + hash).
- **Cross-target conformance**: the same corpus produces **the same hashes natively and in WASM**, in CI (on x86_64 Linux; on aarch64 by the pre-push check of a Mac).
- **A reference hash only changes through a dedicated command**, and the commit explains why. Never silently.
- **Property tests** (`proptest`), at minimum:
  - the same render however it is split into host buffers;
  - two identical renders give the same result;
  - never NaN or infinity in the output.
- **Real-time safety**: no allocation or release of memory in `process`, measured from the first call on a fresh instance, checked automatically by the counting allocator (`engine-alloc-counter`, re-exported by `engine-testkit`), installed in the tests of every crate that processes audio: each box (box laws), every plan (plan laws over random patches), the WASM engine and its C interface. On the browser's audio thread, no copies or messages per render quantum: `pnpm test:allocation` (`bindings/wasm`) drives the engine processor from the first quantum of a fresh instance and counts V8's garbage collections, with every tier and with the interpreter alone, in a young generation of 1 MB (calibrated by a control: one object per 128-frame quantum causes a collection), and finds none for quanta that are whole engine blocks (Web Audio's 128 frames included). Known deviations, each pinned by a test or ticket: the construction of the engine processor (see the real-time constraint above); the first quantum creates one view of the module memory per patch channel, kept for the next blocks, which the count cannot see (counted by a unit test); a quantum that is not a whole number of blocks allocates a view of the part of a block it copies (`subarray`), at least until V8 optimizes it (the optimized tiers are not measured); the tap processor copies every render quantum (capture, and the playground's oscilloscope until roadmap #12 step 21); SpiderMonkey and JavaScriptCore are not measured yet (roadmap #12).
- **Never test only at the default**: every dimension of the environment the code receives is tested across its domain, never at a single value: sample rate (8 kHz to 384 kHz, including 44.1 kHz), how the host splits time (host buffer sizes, including sizes that are not a multiple of the block, random splits), duration, channel count (including 0 and 1), parameter values crossed with rates, special values (0, -0, subnormal, NaN, infinities, Nyquist), patch sizes, browsers and platforms, screen sizes and densities, locale and time zone. Test values deliberately differ from defaults, so that a hard-coded default cannot pass. The shared values come from one test matrix, never retyped. A dimension is covered only when the tests iterate every value of the matrix, in each crate's own tests, and their result depends on it, checked against an independent reference rather than the code against itself (a plan hard-coding 48 kHz must fail).
- **Invariants are tested at the edges of their domain**: every documented invariant and numeric claim is checked at the extremes of every parameter and sample rate and their combinations (zero, negative, Nyquist and above, subnormal, largest accepted sizes), and over long runs (drift, overflow). Every tolerance has a derivation or a measured distribution, written next to it; never a guess. A derivation states its preconditions and holds per regime, each regime tested and each precondition checked by a test reading the real constants; a test reference is exact where it can be (phases reduced in integers), and its own error stays inside the bound.
- **Objective DSP measurements**: every box and every engine component that touches the signal has measured audio quality in its tests, with derived thresholds (spectrum, aliasing level, THD, SNR, frequency response, parameter changes without zipper noise; for engine components, what `spec/engine-design.md` lists for each), compared with high-precision references, through `engine_testkit::measure` and the oracle's independent measurements (`spec/measurements.md`). State-of-the-art DSP is a requirement, not a goal.
- **Fuzzing**: patch parsing, the command layer, then native-vs-WASM differential fuzzing.
- **`unsafe` code**: forbidden by default. If truly required, it is isolated, checked with Miri (or, for inline assembly, which Miri cannot run, by tests on each architecture it supports and a written audit) and, for critical parts, proven with Kani.

### Every other aspect
- **Commands and patch model**: every command is tested (success, rejection, undo/redo round trip), with property tests over random command sequences (full undo = initial state, identical serialization round trip).
- **Format compatibility**: every version of the patch format keeps test files. Old patches always load and migrate, checked in CI.
- **Web interfaces (playground, editor)**: the local `doc/interface-testing.md` is the required test strategy, layer by layer (scene, camera and animations, interactions, renderer, accessibility layer, components, end-to-end, visual regression, performance). It is mandatory, heavy on purpose, and applies from the first line of every interface change. In short:
  - unit and component tests;
  - end-to-end tests (Playwright) on **Chrome, Firefox and WebKit**;
  - visual regression via screenshots;
  - accessibility (axe);
  - the sound produced in the browser is captured (`OfflineAudioContext`) and compared to the native hash.
- **Performance**: engine and editor benchmarks (CPU per box, latency, load time, memory) tracked in CI. A regression beyond the set threshold fails CI.
- **Exported artifacts**: each target runs in test mode, its render is compared to the reference hash, and plugins pass the official validators (`pluginval`, `clap-validator`, `auval`, the VST3 validator).
- **Native shells**: Swift/Kotlin unit tests, plus lifecycle tests (interruptions, background, device changes, denied permissions) on simulators and reference devices.
- **Security**: CSP verified, no API key ever sent to the server (checked by tests), fuzzing of everything that reads external input (patches, media, network messages, MCP).
- **AI assistant**: an evaluation suite (requests → valid patch + expected render metrics), with a success rate tracked per model. A drop fails CI.
- **Reproducible builds**: two builds of the same commit produce identical artifacts, checked in CI.

### Rules the reviews taught
Each rule below comes from a class of defects a deep review found. Where a tool enforces it, the tool is named and is the reference; the others are checked by review.

- **Hermetic tests.** A test that runs an external tool runs it in a temporary directory, with no inherited configuration pointing outside it: git's local variables (`GIT_DIR`, `GIT_INDEX_FILE` … which a hook inherits, from a linked worktree too) are removed (`hermetic_git` in xtask's tests; xtask clears `LOCAL_GIT_VARIABLES` for every command it starts), and nothing reads the machine's or the user's configuration (git's system and global configuration, attributes and ignore files: every recipe of xtask's tests, the hooks' included, sets `HERMETIC_GIT`, whose effect a test shows on a user file it would read). No test writes outside its temporary directory, and a test removes that directory when it returns or unwinds, a failing test or a panicking mutant included: a guard removes it when dropped (`Scratch`, one per test target, each with its own test), never a final statement (a test process killed at a timeout or aborted leaves it, for the next test of the same name and process id to remove), and Clippy's `disallowed-methods` refuses `std::env::temp_dir` anywhere but in that guard's constructor. The code under test runs its own external tools with the test's isolation, through an environment its runner takes from the test, never the machine's configuration.
- **Fakes reproduce absence.** A fake of an event source can also withhold the event (a clock that runs only while running, a message never sent, a promise never settled), throw and reject, so that the tests cover the conditions under which the real event never comes. Every await of an external event is raced against the end of the object that waits; an in-flight promise is stored on the object whose lifetime it belongs to, and cleared when it fails. A fake of a host object is built on the platform's real base class where there is one (`EventTarget`), so that its event model is the host's by construction; the object that owns a resource follows its end from the moment it creates it, before its first await.
- **Every promise of a doc comment is attacked.** A behavior a doc comment promises ("never", "once", "already validated", "releases …") has a test that tries to break it, at its edges; a precondition it states (`must`, `only if`) is a type or a checked error, never prose only. A guarantee names the conditions it holds under, with a test on each side of each; an invariant a type's doc states is checked by every public constructor of the type, or the constructor is not public.
- **Numbers in comments are proven.** A number stated in a comment or a doc (a bound, a count, a size, a duration) is either the constant itself, named, or computed by a test from the exported constants; never retyped. A comment that justifies code by a measurement points to the dated record in `spec/` and states both what the choice gains and what it costs; a measured count is a record, never a constant of a comment.
- **Tests never learn their answer from the code under test.** Expected values and fake keys are fixed facts written as literals or computed by an independent reference, never read from the module being tested. A mutant is equivalent only when no test anywhere can kill it, and is then reviewed (`mutants-equivalent.txt`).
- **An emulation first proves it took effect.** A test that emulates an environment (a time zone, a locale, a muted device, a blocked request, a policy) asserts that the emulation is in force before asserting anything that depends on it; a check that asserts an absence has a positive control that shows it would see a presence.
- **A gate guards against honest mistakes.** Its scope is what an honest change can bring while it pursues its goal: the forms the tree uses, those a tool, an editor or a machine's configuration writes, and those a plausible edit would write. A form only an author's deliberate evasion would write, and which cannot change what the engine computes at run time, is outside its scope: the gate's doc says so in one sentence, and no code refuses or follows it. The engine's run-time guarantees (bits, laws, real time) keep every form in scope, however unlikely.
- **Every gate is proven to refuse.** A gate of `cargo xtask check` has a test with a fixture it must refuse, for every kind of problem it reports (the policy fixtures of `@poyetik/config` for the lint rules). A gate that parses text accepts only the canonical shape and refuses, never skips, what it does not recognize within its scope; every exemption names the exact form it allows; external identifiers are normalized before they are compared; a gate fed by git is tested against the output of real git. A gate's message never claims more than it checks. A guarantee that a lint is never lifted is a `forbid` the gate reads as tokens of a real leading inner attribute of the file, which the compiler enforces against every name of the lint, never a refused word; a word rule only covers what the compiler does not lint (the keyword `unsafe` in code expanded from another crate's macro), and says so; a gate over Rust sources reads the tokens of a real tokenizer (`RustSource`, the file's start rustc strips refused), never characters or lines; a rule that tells files apart by their names (test code, test data) has a gate that keeps the names true. A gate about what the compiler loads or resolves (files, modules, paths, lint levels) reads the compiler's own record, for every configuration the check builds (each target, the fused math layer, tests or not: `loaded_files_commands`); a configuration no build of the check makes (a `cfg` only Miri, the coverage, the release profile or rustdoc sets, a feature) is refused where it is written, unless reviewed (the bypass gate), so the loaded-files gate is the guard of what is loaded, no word rule imitating it, and what a doc test loads is review only. A gate or proof fed by a tool sees exactly what the tool acts on: the tool's configuration and environment are pinned or refused, never left to the machine. A pattern with alternatives has a fixture for each alternative in each form it matches, and a test of a message asserts it as the user reads it, after every layer that adds to it.
- **A reused result is keyed on all its inputs.** A check may reuse an earlier result only when every input of that result (code, tests, test data, dependencies, configuration, rules, tools, host) is unchanged, as found by a tool (where the tool cannot see an input, the rule that keeps it seen is stated as reviewed, as the test data gate's run-time paths are); its soundness statement names each input, and each has a test showing that its change voids the reuse (the mutation proof record above; Stryker's incremental mode keeps the gaps the default check states).
- **No mutant may crash the test runner.** An error a framework reports globally (React on the window, an unhandled rejection) is caught by the test that triggers it, so that a mutant fails that test instead of crashing the runner: Stryker counts a crash as a runtime error, which xtask's mutation gate refuses.
- **One source per fact.** A fact shared by code, hints, manifests, tests or docs has one source; every other place derives from it, or a gate compares every copy (xtask's `PACKAGES`, `RUST_CRATES`, `TOOLS`; the test matrix). A README names the source of a list instead of copying it. This file states each rule, its guarantee and its limits, and names the item whose doc is the source of its mechanism; it never copies field lists, accepted forms, format numbers or measurements. Conversely, one name per meaning: a constant or function is reused only for the meaning it was made for. A helper that must be copied into each test target carries its test in each copy.
- **Validators accept exactly what they document.** A validator is tested with truncated, padded and out-of-range forms of what it accepts; a function that produces evidence (a hash, a report, a verdict) refuses malformed input instead of normalizing it, and takes every fact it records from its caller, never from a default. An option that relaxes a refusal is tested crossed with every other input the refusal depends on.
- **Errors keep their cause across boundaries.** An error crosses a boundary (a message port, the C interface, a process) as one of a closed set of kinds that keeps its cause, and is rendered in words at the edge; an error from an external command carries its exit status and its own error line. A cleanup (a `finally`, a close) never replaces the error that caused it, and every promise is handled on every path, a failing one included.
- **Build properties are asserted at build time.** A design that depends on a property of the build asserts it where the compiler sees it (`compile_error!` against WebAssembly atomics in `engine-wasm`'s FFI). A fallback value is written only where the absence it covers is legitimate.
- **Scripts are tested functions.** Every script is a tested `main(io)` (or the equivalent), with a thin entry point that only wires the real process; the scope gate refuses an unmeasured source unless it is reviewed in `proof-bypasses.txt`. A file only a command-line tool writes can be changed in every field through that tool, and is read back only exactly as the tool writes it, the error naming the command that rewrites it.
- **Accessibility is audited in every state.** The axe audit runs on every state and rendering branch of a page, enumerated from the type of its states (a `Record` over the state kinds, so that a new state does not compile without one); every style that carries accessibility meaning (focus ring, contrast, hidden text) has an end-to-end assertion on its computed value; semantics a browser heuristic may drop are explicit in the markup.
- **Documentation follows the code.** `GLOSSARY.md` changes in the same commit as the public name it describes (its synonyms are refused by the vocabulary gate, `vocabulary.txt`); a change that makes an `[Unreleased]` statement false updates it; every command a README gives is one CI runs; `# Errors` and `@throws` name the errors that pass through from callees; a format implemented twice is specified in `spec/` with shared test vectors, the spec listing every input it refuses and the vectors holding at least one per refusal with the expected reason as a literal, each suite reading exactly the keys of the vectors file; a roadmap ticket is cited by its number, checked with `pnpm roadmap show` at each review. A doc describes the state, never its history (no "before", "no longer"), but a dated record of a measurement; a "not yet" names the roadmap step that ends it.
- **What CI cannot run is stated.** A property proven only on the maintainer's machine, or only on one platform, says so where it is claimed (see CI above); a platform CI cannot run has a written test protocol, and the gap is listed among the known deviations.
- **A hint is a command.** A message that tells the user what to run names the exact command, and a test follows it in that state and shows it succeeds (`engine-cli`'s hints are the variants of `Hint`, whose test does not compile without a state that gives each). A command that runs another tool's command passes its options on unparsed and maps the child's usage exit to its own usage exit; it keeps no second table of them.
- **Evidence runs the shipped path.** The laws, fingerprints and equivalence tests run the type and the code path that ship, or a test proves both paths equal bit for bit at every input the evidence uses; a claim of identical bits compares bits, and a type carrying evidence of bits has a bitwise equality or none. A law bounding a quantity the code fixes exactly asserts the exact value, or a bound whose slack is smaller than the regression it guards against, and says which.
- **A fix covers its siblings.** A fix repairs every instance of the structure it repairs (each parallel path, each copy), and its test iterates them.

### Deep review
`/deep-review` (`.claude/skills/deep-review/`) runs an exhaustive multi-agent review along every quality axis (seventeen, scientific rigor and edge cases included), verifies each finding adversarially, then analyzes each one (admissibility, options, trade-offs) before anything is applied. Run it at the end of each review block, on the branch after its green default check (the green `--full`, the pull request's CI, comes after the review's fixes, before the merge; see Working in blocks), and before closing a roadmap ticket and before every release, each of these two with a green `cargo xtask check --full` first; a version that is not a release needs none. No finding is applied without the maintainer's decision and a fresh analysis at the moment of applying it. Every review also turns the classes of defects it reveals into lessons: preferably a tool that prevents or detects them (a gate, a law, a lint, a type), otherwise a rule in this file, worded to apply beyond the case that revealed it. No finding is left without a disposition: fixed, or deferred as a roadmap step in the same pass.

### Transparency
Results are meant to be published for every release: coverage, mutants, per-target conformance hashes, known deviations.

# conformance

The **conformance corpus**: every target and every SDK must reproduce these render hashes exactly.

| Path | Contents |
|---|---|
| `cases/<name>.json` | Reference cases: a sample rate and a duration, from 1 to 2^29 (536,870,912) frames, and optionally the output stage of the render (`output`: its `mode`, `raw` or `protected`, its limiter's `lookahead` in milliseconds from 0.5 to 5, its maximum too, and its `detector`, `standard`, `precise` or `mastering`; raw when absent, never `null`; the limiter's other settings their defaults, `spec/engine-design.md` decision 12). A case's name is lowercase ASCII letters, digits, dots and hyphens, starting with a letter or a digit, so that a command naming it needs no quoting in any shell: the engine CLI and the oracle refuse any other `.json` file in `cases/` (and the engine CLI in `patches/`) |
| `patches/<name>.json` | The patch of each case, in the patch format. Every runner (native, Node, browsers) gives the engine the bytes of this file unchanged, never a parsed and rewritten copy |
| `invalid/cases/<name>.json` | Case files every reader must reject, one fault each (a duration of 0 frames or above 2^29, or not an integer; a sample rate below the engine's range, above 32 bits, or written as a string; an unknown field; a file above 64 KiB; an output stage that is `null`, of an unknown mode or detector, of a mode or detector not written as a string, of a lookahead out of its range, or with an unknown field): the shared rejection corpus, which the tests of the engine CLI and of the oracle each read whole through their size-limited file reading, refusing every file |
| `test-matrix.json` | The shared test matrix: the values each dimension of the environment is tested across (the precisions, by their widths in bits, among them), read by the Rust and TypeScript tests |
| `references.json` | The expected render hash of every case in each render format (`spec/render-hash.md`): `binary64`, `binary64-as-binary32` (what a browser's audio thread is given) and `binary32`, each rendered in the strict arithmetic mode |
| `algorithms.json` | What the references were blessed under (`spec/engine-design.md`, decision 29), as `cargo xtask bless` recorded it with them: the render hash version, the render rules version, the fingerprint of every box type at each algorithm version blessed (with the version of the battery that computed them), and the algorithm version of every box type each case uses. The check refuses a case whose box types are at other versions (a new version needs new references), another render hash or render rules version, and a fingerprint changed at a recorded version; a reference mismatch under the same versions means bits changed without a new version |
| `visual/cases/<name>.json` | Visual reference cases: an image rate, a size, the first image and the number of images, and the square's side and cycle. Every limit of a single value a reader takes is reached by one, valid on every reader, next to its invalid case one past it: the rates, the sides of an image (1 and 16384) and its pixels (`square-largest-image-at-50`, exactly 2²⁵, next to `image-above-the-pixel-limit`, 2²⁵ + 1), the count of images and the image indices. The limit of 2²⁸ pixels rendered in all is the one exception: a case reaching it would cost minutes of every check unoptimized (about 2 minutes at 430 ns a pixel, measured once on the maintainer's Mac, 2026-11-15), so only its invalid case one past it is in the corpus, and the tests of `visual-cli` and of the oracle check a case at it is accepted. `square-one-column-at-1000` does not move, on purpose (a one-pixel-wide image shows no horizontal motion, and its cycle is one image). A case name is lowercase ASCII letters, digits, dots and hyphens, starting with a letter or a digit, as for the engine's cases: a `.json` file whose name is not a case name is refused (the check fails), and any other file of the directory is ignored |
| `visual/invalid/cases/<name>.json` | Visual case files every reader must reject, one fault each (a count of images out of range, an index past 2⁶⁴ − 1, a rate not reduced or out of range, a width or height of 0 or 16385, a side or cycle out of range, an image above 2²⁵ pixels or a case rendering more than 2²⁸ in all, a number written with a fraction or an exponent, above 32 bits or as a string, an unknown or missing field, a field written twice, a negative zero, a case or square that is not a JSON object, a file above 64 KiB): the shared rejection corpus, read whole by the tests of `visual-cli` and of the oracle, each refusing every file for the reason it holds for it |
| `visual/references.json` | The expected image hash of every visual case; it changes only through `cargo run -p visual-cli -- bless conformance/visual`, and the commit says why |
| `visual/test-matrix.json` | The shared visual test matrix: the image rates, sizes and indices every visual box law is checked at, read by `visual-testkit` and by the tests of `@poyetik/visual-wasm`, which render every value of the square across it in WebAssembly |
| `expectations.json` | What every case must sound like, independently of any hash: for each channel, the ideal signal (`sine`), whose largest allowed distance is derived by the oracle (output rounding, phase accumulation, evaluation), never declared; or, for a case rendered through the true-peak limiter with the standard detector, the sine it limits (`limited`): silence over the limiter's latency, then a true peak and a THD+N within the bounds the oracle derives from BS.1770's table |

- `cargo run -p audio-cli -- check conformance` renders every case natively in every render format and compares the hashes; `cargo xtask check` runs it with `--spent <record>`, the spent record (`algorithms.json` as `main` holds it, at the merge base of xtask's `MAIN_BASES`), and also refuses a fingerprint other than that record holds at a version both hold, whatever wrote the record.
- **`references.json` and `algorithms.json` only change through `cargo xtask bless`**, and the commit must explain why the hashes or the versions changed. The check reads both only exactly as bless writes them (a hand edit or a repeated key is refused). Bless itself refuses, writing nothing (`spec/engine-design.md`, decision 29): a reference of an existing case that changed while its box types' versions, the render rules and the render hash stayed as recorded, or whose case the record does not hold; a box type or the render rules at a lower version than either record holds; a box type's fingerprint changed at a version spent on `main` (one the spent record holds: versions first blessed on the branch may be blessed again, pushed or not); a battery change but with `--battery-changed`, in a bless of its own (with another change on the branch, the battery change is blessed alone first, as the refusal's hint says); and a directory missing either file but with `--from-nothing`. A case whose own files changed on purpose is named with `cargo xtask bless --case-changed <name>` (repeatable), and the commit says why.
- `cargo run -p audio-cli -- render conformance/cases/<name>.json conformance/patches/<name>.json --wav <file.wav>` writes a case as a WAV file to listen to (`--format <format>` chooses the render format; binary64 by default, 64-bit float samples).
- `cargo run -p audio-cli -- export conformance target/conformance` writes the WAV file of every case in every render format, `<case>.<format>.wav` (64-bit float samples for `binary64`, 32-bit otherwise); the independent oracle (`tooling/oracle`) then rereads them, recomputes their hashes and checks `expectations.json` against the error bound of each format. `cargo xtask check` runs both.
- Every case needs its patch, a reference hash, its algorithm versions and expectations, and every patch its case: the engine CLI fails on anything missing, the oracle on a missing case file, reference, expectation or WAV file (it reads neither the patches nor `algorithms.json`).
- Size limits, checked while reading by the engine CLI and the oracle alike (never more than one byte past them, and only from a regular file): a case file holds at most 64 KiB, a patch file 16 MiB (the limit of the patch format), `references.json` 1 MiB, `expectations.json` 1 MiB, an exported WAV file 4 GiB + 7 bytes (what its 32-bit RIFF size can declare). The engine CLI reads the case, patch and references files, and `algorithms.json` and the spent record (`--spent`), at most 1 MiB each; the oracle reads the case, references, expectations and WAV files.
- `cargo run -p visual-cli -- check conformance/visual` renders every visual case natively and compares the image hashes; the tests of `bindings/visual-wasm` (`pnpm test` there, after `pnpm build`) do the same with the real WebAssembly module, so the two prove the same bits natively and in WebAssembly; `cargo xtask check` runs both.

# xtask

The project's automation: `cargo xtask check` and the commands of the git hooks (`cargo xtask help` lists every command). What each check proves, and what the default check does not, is in the crate's documentation (`cargo doc -p xtask`) and in the root `CLAUDE.md`, section CI.

## Measured choices of the check's speed

The default check is run before every push, so its time decides how often it runs. Every change made to shorten it, beyond what the default check is designed to leave to the full check (`CLAUDE.md`, section CI: what the default check does not prove), and every proof the maintainer moved from the default check to the full check for speed, is recorded here, one entry each: when, what was measured with its numbers, what was kept and why, what was rejected and why, and how to measure again. The order of the reasons is the project's: **no guarantee is traded for speed**, but where the maintainer decided it, said in its entry (each kept change carries its own argument that it changes no outcome, since comparing the outcomes of one run is only a smoke test: almost every mutant dies on the first failing test), and the development environment stays portable (nothing here depends on one operating system's setting or tool). `cargo xtask check --full`, which CI runs, keeps its strength. The engine's own measured choices are in `spec/benchmarks.md`, "Measured design choices".

**How it was measured.** On the maintainer's Mac (10 cores, 16 GB), a fixed slice of the Rust mutants, `--shard 3/20 --sharding=round-robin` of cargo-mutants with the check's own options, about 110 mutants, run on a clean clone, one heavy run at a time, the forms compared alternated (A, B, A, B); per mutant, the build and test phases from cargo-mutants' report; the peak memory of the compilers, linkers and cargo-mutants sampled every second. The machine was in use: single runs vary by about 10%. The numbers below are those runs', on 2026-11-10; to measure again, run the same slice with and without the change, at least twice each, alternated, and compare the outcomes mutant by mutant as well as the times.

- **Mutant builds without debug information** (`MUTANT_BUILD_CONFIG`, every cargo-mutants run). Measured with debug information (Cargo's default), with `debug = false` and with line tables only, on 111 mutants at 5 jobs, in the order A1 B1 L1 A2 B2 L2:

  | Run | Setting | Wall time | Job time | Mean build of an xtask mutant |
  |---|---|---|---|---|
  | A1 | default | 182 s | 724 s | 3.42 s |
  | B1 | `debug = false` | 145 s | 576 s | 2.75 s |
  | L1 | line tables only | 162 s | 624 s | 3.14 s |
  | A2 | default | 179 s | 697 s | 3.63 s |
  | B2 | `debug = false` | 171 s | 692 s | 2.97 s (a foreign load on the machine) |
  | L2 | line tables only | 164 s | 637 s | 3.27 s |

  The same outcome for every mutant in all six runs. Kept: `debug = false`, the fastest builds of xtask's mutants (about 60% of all mutants) in both pairs, about a tenth less job time. The argument that it changes no outcome: compared on every compiler command line of `cargo test --no-run -v`, it changes only the debug-information options and the hashes Cargo names outputs with, and no code reads a backtrace's file and line (reviewed). Rejected: line tables only, close but slower to build xtask; the default.
- **No unit-test build of a binary's `main.rs`** (`test = false` on the binaries of `audio-cli` and xtask, `untested_targets_gate`). Their test harness held no test (each root declares no module, and test code lives only in declared `*_tests.rs` files and `tests/`), so every build of a mutant of those crates compiled and linked one program for nothing. Not measured alone: the slice above holds too few of those builds to resolve one compile and one link each. Kept, with a gate that refuses `test = false` on a target whose root declares a module.
- **One integration test program for xtask** (the binary's tests and the hooks' tests, two modules of `tests/binary.rs`). One compile and one link less per mutant of xtask; nine tests before and after, each unchanged. Not measured alone, for the same reason.
- **Mutation jobs: half the machine's threads, unchanged** (`mutation_jobs`). Measured on 115 mutants without debug information, in the order 5, 3, 4, 6, 5 jobs: wall time 158, 155, 165, 149 and 174 s, job time 634, 376, 547, 737 and 702 s, peak memory 2.3, 2.6, 2.5, 4.8 and 2.5 GB; the same outcomes in all five. No knee: the wall time is flat within the noise of the two 5-job runs, while the job time doubles from 3 to 6 jobs (contention). Kept: half the threads, from `available_parallelism`, valid on every system. Rejected: memory as an input of the formula (the standard library has no portable reading of it, and a reading per system breaks portability; about 0.5 GB per job was measured, so half the threads fits any machine with 1 GB per thread). Three jobs gave the same wall time at half the load; deciding needs a larger slice (roadmap #24 step 32).
- **The default check runs its steps cheapest first** (`cheapest_first`): the gates, the Rust checks, coverage, Miri, the TypeScript packages, then the Rust mutation testing, so that a failing gate, lint or test is reported before the mutation testing, about eighty minutes earlier on a change of the whole branch. Not a measurement but an order: the argument is that each part of the full check runs alone in CI after only its own preparations, so no step depends on another part's. `--full` keeps its order.
- **Widening per crate** (`widening`, `lock_widened`, `manifest_widened`). A change of a shared input (a crate's manifest, a crate of shared test code, `Cargo.lock`, an entry of the root `Cargo.toml`'s `[workspace.dependencies]`) widens the mutation testing to the crates it reaches, where it widened to every Rust mutant. What a crate's builds read is held by the loaded-files gate (`loaded_files_gate`), from rustc's own record. The argument for the root manifest: an entry of its shared dependencies reaches a build only through a crate that declares it under its name (`<name>.workspace = true`, read from `cargo metadata`), what it resolves to is in the lock file, widened on its own, and a crate's mutants are tested by its own tests, built from the crates it depends on; a change confined to its lint tables (`[workspace.lints]` and `[workspace.lints.<tool>]`, headers written exactly so) widens to nothing; any other change of the manifest (profiles, patches, members, package fields, a key not understood), or a manifest not read soundly entry by entry (`shared_dependencies`), still widens to everything. The argument for the lint tables, measured on 2026-11-12 with the pinned toolchain (1.99.1) and cargo-mutants 27.1.0: cargo-mutants caps lints in every cargo command it runs, its baseline included (`--cap-lints`, `MUTANTS_ARGS`), and a capped build fails on no lint level, `forbid` included; `check-cfg` only declares the names the `unexpected_cfgs` lint expects and sets no `cfg`; rustdoc applies no manifest lint to doc tests nor to the library they test (a doc test and a library breaking denied lints passed `cargo test --doc`), so no `compile_fail` doc test can fail for a lint; no lint level changes the code generated: `cargo test -p audio-core --no-run` under the cap gave a byte-identical test program with five different lint tables, `check-cfg` extended among them; no test reads the root manifest; and a crate's own `[lints]` cannot change (each must be `workspace = true`, a gate). A bump of cargo-mutants or of rustdoc's handling of lints needs these measurements again (a toolchain change widens to everything anyway). Measured on 2026-11-12 with cargo-mutants' `--list`, xtask's selection applied to the real manifests: the workspace holds 2,734 Rust mutants, 1,625 of them xtask's. The changes since `main` change the root manifest's two shared dependencies (`libm`, `sha2`) and its lints: the default check selects 1,093, the nine crates building a crate that declares one, xtask and the counting allocator apart (`sha2` alone: 827), where it selected every mutant before the lint tables were left out (2,733 then).
- **xtask tested on its fixtures only**. Its tests read fixtures, never the repository's own files (every Rust source, `cargo metadata`), whose checks are the gates every check runs as steps, but two: its declared test data are the hooks it runs and the workflow, which the workflow gate's test compares line by line. So a change outside xtask, its hooks and the workflow does not reach its mutants: about 1,200 of the 2,214 Rust mutants of the branch's first default check (2026-11-10, before the workflow became test data). Not measured as time.
- **The mutation proof record** (`ProofRecord`). A default check that passed on a clean tree records what it proved; a later default check of the same base skips every crate whose inputs are byte-identical since. Without it, every default check of a block branch mutates the whole diff since the merge base, widened to every Rust mutant once the shared test crate changed: 1,888 mutants for any change (2026-11-09). Not a measurement of speed but of what is repeated; its soundness is argued on its type (a record never changes what the default check proves).
- **A memory limit on the mutants' test programs, on Linux** (`MUTANT_TEST_RUNNER`, `MUTANT_MEMORY_LIMIT`, every cargo-mutants run). Not a speed change but a lost run prevented: on 2026-11-16, CI's mutation shards 1 and 4 lost their 16 GB runner three times, probably to mutants that inflate a size (`replace / with * in limiter::frames`, those of `Binary64::rounded_count`) whose tests reserve gigabytes at several jobs at once. Cargo's test runner, given on the command line, runs each test program under `prlimit --as` (4 GiB of address space), never the compilers, so a mutant's runaway allocation fails and the mutant is caught. The argument that it changes no outcome: the unmutated baseline runs under the same limit, so a test that legitimately needs more fails the baseline and the whole run, and a mutant caught only by the limit behaves differently from the code. Measured on 2026-11-16: before the limit, CI run 43824460371 lost the runners of shards 1 and 4; under it, run 43932217703 ran both to their end on their runners (shard 4: 478 mutants in 67 minutes, 424 caught, 53 unviable, 1 timeout, the hanging mutant of the next entry), no runner lost.
- **A test timeout that scales with the jobs** (`mutant_timeout_args`). Not a speed change but a false failure removed: with a timeout derived from the tests run alone, a mutant caught by a fast test whose program still runs its slow tests to the end is reported as a timeout under parallel jobs (two of `audio-testkit`, about 30 s against 22 s allowed at 5 jobs, 2026-11-10); the timeout is multiplied by the jobs, and a hanging mutant is still stopped and fails the check. What a hanging mutant costs, measured on 2026-11-16 (CI run 43932217703, the fourth mutation shard): the multiplier applies to cargo-mutants' unmutated baseline, which runs the tests of the whole workspace, so the timeout was set to 2,582 s (43 minutes) for a mutant of `audio-core`, whose own tests took about 25 s then (61 s by 2026-11-17, the record below); that bounds how long the failing run takes, never its outcome.
- **A cost accepted for proof: the gates read Rust as tokens** (`RustSource`, proc-macro2's lexer). Measured on 2026-11-11 on the same Mac, the six gates that read Rust code (unsafe, test code, test data, untested targets, unviable names, math layer), each step's time as `cargo xtask check --full --part gates` prints it, three runs each, identical: 0.0, 0.2, 0.1, 0.0, 0.1 and 0.0 s with the hand-written word scanner, 0.5, 0.5, 0.4, 0.4, 0.4 and 0.1 s with the tokenizer, about 2 s more per check in xtask's debug build. Reading all 79 tracked Rust files of that day (87 on 2026-11-12; the visual crates came after these measurements, and the whole gates part took 44.5 s on 2026-11-15) once costs about 0.4 s in debug (0.2 s of it proc-macro2's lexing, the rest each token's line and text) and 0.07 s in release. Kept: the scanner was an imitation of rustc's lexing in which every review found a new hole (raw identifiers, nested comments, a shebang), and each step reads the files again, its result never reused across steps. Halved by reading a token's own source text only for a `#`, where a doc comment may start.
- **A cost accepted for proof: the loaded-files gate reads every configuration the check builds** (`loaded_files_commands`). Besides the host's `cargo check` and `cargo test --no-run`, it reads the fused test build's own units (`--no-run`, which the fused step then reuses), and checks (`cargo check`: type-checked, no code generated, nothing linked) the crates of both libraries for each portability target, the WebAssembly crates of both libraries, and the native shell and its floating-point mode, tests included, for both native architectures. Measured on 2026-11-11 on the same Mac, idle (load about 2): the six target checks in a fresh target directory took 5.2 (the first, which also checks the shared dependencies), 1.6, 1.5, 1.7, 2.5 and 2.0 s, 14.5 s in all, and the fused units 4.1 s, which the fused step would have spent anyway; once built, the nine commands take 0.43 s in all, 0.3 s more than the host's two. Kept: a module compiled only for one target or under the fused math layer (a WebAssembly-only module, an aarch64-only file) was otherwise read by no gate but the word rules, which the compiler's record is meant to back. Rejected: reusing the outputs of the portability, native and fused steps (about 0.6 s cold instead of 15 s), which needs a second reading of cargo's messages for uplifted build outputs and an exemption for Clippy's own configuration files, and couples the gate to the exact flags of three other steps; and a doc test build, whose crates rustdoc compiles apart and records in no dep-info file. These timings were taken on 2026-11-11, before the visual crates joined these commands, and not measured again since. To measure again: run the commands of `loaded_files_commands` in a fresh target directory, then again.
- **Measured, not made yet: proc-macro2 optimized in the development profile** (`[profile.dev.package.proc-macro2] opt-level = 3`). Measured on 2026-11-12 on the same Mac, five lexes of the 74 Rust files under `crates/` (as five gates), three runs each: 1.14 to 1.23 s in the development profile, 0.16 to 0.19 s with the override, about 1 s per check. Sound for one package: xtask alone builds proc-macro2, and the override keeps the profile's debug assertions and overflow checks, so no checked behavior changes (no heap-counting test runs it). Not made yet: a `[profile.*]` change of the root manifest widens every default check to every Rust mutant until the merge base holds it, so it is to be made alone (roadmap #24 step 32).
- **A unit test change widens to its own source only** (`declaring_sources`, 2026-11-14, the maintainer's decision). A change to a `*_tests.rs` file mutates every mutant of the source declaring it (`<module>.rs`, or another, as `math.rs` declares `reduction_tests.rs`), where it mutated every mutant of the crate: for xtask, about 1,700 mutants, 25 to 55 minutes on the maintainer's Mac, for one changed test. This one trades proof for speed, on purpose: a weakened unit test can let a mutant of another source survive, which the default check no longer runs; every change reaches `main` through the full check of its pull request, which mutates everything (`CLAUDE.md`, section CI, says so). Integration tests, declared test data, and a test file no source declares (deleted, or its declaration removed) still widen to the whole crate.
- **The visual corpus checked optimized** (`visual_conformance_step`, 2026-11-15). The native visual conformance step builds `visual-cli` with `--release`: its largest image, 2²⁵ pixels, takes about 15 s unoptimized and half a second optimized (measured once on the maintainer's Mac). Nothing is left unchecked: the arithmetic stays checked (the library denies `arithmetic_side_effects`), the bits are the same, and `visual-cli`'s own test checks the corpus unoptimized, that one case apart.
- **`cargo xtask mutants --changed <revision>`** (`rust_mutants_of_changed_lines`): the Rust lines changed since the merge base of `HEAD` with the revision named, never widened, for development between two default checks. Measured on 2026-11-14 on the change that added it: 28 mutants in 71 s, where the default check would have mutated every mutant of xtask. The revision is required since 2026-11-17 (the maintainer's decision): measured from the upstream by default, as the default check is, a package branch not pushed mutated 762 mutants, most of them the work of other packages, where its own were 16. Before testing, it lists the mutants with the same arguments (cargo-mutants' `--list`) to say how many it will test: measured on 2026-11-17 on 24 mutants of the workspace, 0.6 s.
- **Each TypeScript script its own step** (`Package::checks`, tied to each manifest's `check` script by `package_check_gate`): every script of a package's checks runs and says its time alone, where one step ran `pnpm run check` and said one time (50 s for the roadmap, 2 min 37 s for the engine package on 2026-11-10), so that the next speed work knows which script costs what. Not a speed change: the same scripts run, each started by pnpm directly (measured on 2026-11-14: about 0.2 s less per package than through `pnpm run check`, which starts pnpm twice). One difference: in `--full`, which runs every step whatever fails, a failed script no longer stops the package's later scripts, as `&&` did; the check fails either way, with more failures listed for one cause.
- **Measured, not made: coverage without rebuilding the workspace for each crate.** Each of the eleven library measurements empties the coverage build first (`Coverage::clean_command`), so that no object of an earlier measurement enters the report as a second, unrun copy of its code. Measured on 2026-11-14 on the same Mac, the eleven measurements in a row: 67 s with the emptying, 56 s with only the raw profiles removed (`cargo llvm-cov clean --profraw-only`, then `--no-clean`), 11 s saved. Not made: sound only with one build directory per crate (about 400 MB each, some 5 GB, with 12 GB free on that disk), and a stale object left by a removed crate or changed features would fail the gate falsely.
- **Measured, not made: skipping xtask's tests and coverage when nothing of xtask changed.** Measured on 2026-11-14: xtask's library coverage 9 s, its binary's 11 s, its tests about 2 s once built: about 20 s per check, for change detection in two more steps.

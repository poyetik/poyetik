## [Unreleased]

### Added

- The preflight of `cargo xtask` requires a Vulkan driver on Linux, which the GPU workspace's tests render on, and names the package to install (on Ubuntu, `mesa-vulkan-drivers`, whose lavapipe renders on the processor), instead of the tests failing one by one.
- The playground shows the visual library's square with the sound: a white square on black sweeping across 320×180 pixels every two seconds at 60 images a second, the image of the audio clock's frame at every repaint (`Player.frame`: the frame nearest to the clock's time times its rate, `frameAt`, exact below 2⁵¹ frames, about 186 years at 384 kHz; then the page module's `imageAt`), encoded for display by the module and put on the canvas as it is (`Square`); or drawn on the GPU through WebGPU when the browser has one (`gpuSquare`): the library's own shaders from the page module, the square placed exactly by the module, the encoded pixels copied into the canvas as they are, the same bytes; the page says which draws it. Chromium's end-to-end tests run its new headless mode with WebGPU enabled, so that the GPU path runs in every check (its headless shell shows and reads back nothing of a WebGPU canvas); WebKit draws on the machine's GPU, Firefox headless on the processor (no adapter); the canvas shows its images at their 16:9 (it took the oscilloscope's 3:1). It shows the first image between sessions, and only it, saying so, when the system asks for reduced motion; the canvas is an image named and described by a line saying what it shows, accessible in every state. The page module, 64 KB beside the engine's 390 KB (65 360 and 399 139 bytes), loads from the page once its canvas exists. `@poyetik/visual-wasm` and `@poyetik/web-page` are built to JavaScript with their types (`dist/`, `pnpm build`), what their exports name, as `@poyetik/audio-wasm` is. End-to-end tests compare the canvas with the module's images, byte for byte, in every browser.
- An image's display encoding, `visual_core::DisplayImage` (`spec/visual-design.md`, decision 9): 8-bit sRGB with straight alpha, four bytes a pixel, as a canvas's `ImageData` takes it; alpha rounded linearly, each color taken over alpha as an exact quotient (no division rounded: `t × alpha` against the color, exact in 64 bits, `straight8`) then encoded by the sRGB transfer function of IEC 61966-2-1, every code found by comparing with 255 thresholds proven in exact rational arithmetic (`SRGB8_THRESHOLDS`, `ALPHA8_THRESHOLDS`, `srgb8`, `alpha8`, `pixel8`), so the same bytes on every target, a GPU's included; the display image allocates all its memory when created, refuses one the machine cannot hold, and encodes without allocating; each code starts from a bucket of its value's 16 high bits (two tables of 1,664 bytes) and an opaque color is its own straight value, so that encoding costs 122.7 WebAssembly instructions a pixel where a binary search cost 522. The visual benchmarks measure it (`render and display` at every size, its law from 320×180, `spec/benchmarks.md`), and show the page's module drawing at exactly the visual module's cost, the worklet's module holding no drawing code.
- `@poyetik/web-page`: the page module built reproducibly into `dist/page.wasm`, and `PageModule`, which creates its own instance from a compiled module or its bytes, drives the visual interface as `@poyetik/visual-wasm` does (whose driver is now exported, `./driver`, for product modules) and answers which image the page shows at a frame of the audio clock (`imageAt`, exact, 64-bit frames as `BigInt`).
- The product's module for the page, `web-page` (`page.wasm`): the visual library's C interface and the coordinating layer's in one WebAssembly module, never two side by side (`spec/engine-design.md`, decision 33); its own interface, integers only, answers which image the page shows at a frame of the audio clock (`page_image_at`, `REFUSED` for an invalid rate), its file one more audited `unsafe` file under Miri.
- The coordinating layer's crate, `coordinator`, born with its first real task: `image_at`, the image a visual sequence shows at each frame of the audio clock, `⌊frame × image rate / sample rate⌋` exact in 128-bit integers, proven against the inequality that defines it at every rate of both test matrices and at any rate.
- The GPU's time benchmark, `visual-gpu check|bless|help`: the median time of rendering the square at 1280×720 by the GPU's own clock, checked within ±10% on a GPU whose time `spec/gpu-time-baseline.txt` holds, shown on any other (CI's software GPU), the smaller sizes shown; a step of every check, blessed by `cargo xtask bless-benchmarks` (`spec/benchmarks.md`, "Visual library").
- What an image costs the GPU, `visual-gpu`: exact counts the same on every GPU of the same limits (`render_cost`: bands, workgroups, bytes uploaded and read back, proportional to the pixels, held per size by its tests), and the GPU's own time by its clock (`timed_render`, timestamp queries around each pass, so the processor's load does not count; `None` on a GPU without one).
- The display encoding on the GPU: `GpuSquare::encode` encodes an image for display on the GPU, exactly the bytes of the CPU's (`DisplayImage::encode`) whatever the values (not a number, infinities, zeros of both signs, subnormals, negatives, above 1), proven on every threshold over alphas from the faintest to above 1, at random bits and on the square across the visual test matrix, in bands of any size. Its shader, `visual_core::DISPLAY_WGSL`, works in 32-bit integers only, reading every value as its bits: the color over alpha compared exactly through a 48-bit product of significands, so that neither a GPU's division, nor its flushing of subnormals, nor fast math can change a code; it reads the library's thresholds as bits (`DISPLAY_THRESHOLD_BITS`). The square's shader moves to its box, `visual_boxes::SQUARE_WGSL`: each shader is given with the library, for wgpu and for WebGPU alike. `DisplayImage::bytes_mut` hands a display image's bytes to such an encoder. naga parses and validates both shaders in the GPU workspace's tests, with WebGPU's core capabilities, before any pipeline is created; the loaded-files gate accepts a shader in a build only when it is one of those (`VALIDATED_SHADERS`), tracked, in its crate's `src/`.
- The visual library on the GPU, `visual-gpu`: the square rendered by one WGSL shader through wgpu (Metal, Vulkan, DirectX 12), bit for bit the CPU reference's image (the square placed by the CPU, its coverage computed in 32-bit integers), proven at every point of the visual test matrix, at random squares and in bands of any height; an image larger than the GPU's buffers is rendered band by band, and a lost or refusing device is an error, never a panic. A Cargo workspace of its own, which `cargo xtask check` checks as the root (formatting, lints, docs, tests, 100% coverage, every mutant, supply chain with wgpu's exceptions), CI rendering on a software GPU (lavapipe).
- The visual CPU reference proven under the floating-point modes a host may set (`visual-cli`, through the shared `fpenv`): every visual conformance case gives its reference hash under a flushing host, and the small ones under every host mode that lets float work run, every rounding direction included.
- A cost-benchmark harness any library's WebAssembly module can use (`@poyetik/wasm-build/bench`): named counts measured on the module as built (`countedInstance` over the shared instrumenter), compared with a baseline in the repository within a tolerance either way, laws the counts must obey, and one command, `check`, `bless` or `help`, following the command-line contract; the engine's benchmarks keep their own until they move to it (roadmap #24 step 155).
- `Square::placement` (visual-boxes): where the square is in an image, its edges in subpixel units exactly as it renders and traces them, 32-bit by construction (at most 2²⁶), for renderers other than the CPU reference; computed in 32 bits, the square renders with 8.4% fewer WebAssembly instructions, the same images.
- The visual library's cost benchmarks (`spec/benchmarks.md`, "Visual library"): the WebAssembly instructions of rendering one image of the square, and of rendering and hashing it, at four image sizes from 64×36 to 1280×720, and the module's size, compared with `spec/visual-benchmark-baseline.json` within 2% by `pnpm benchmarks:check` in every check and blessed by `cargo xtask bless-benchmarks`; their law: an image costs its pixels (within 2% per pixel of the largest size).
- No visual box may output a subnormal value or -0: the finite-values law refuses both (a box writes 0 instead), so that a target flushing subnormals to zero, as GPUs do, cannot change an image's bits or its hash (`spec/visual-design.md`, section 3).

### Changed

- Mutation testing runs each mutant's tests under cargo-nextest in the GPU renderer's Cargo workspace too, not only in the root's.
- Mutation testing runs the slow tests last in the GPU renderer's Cargo workspace too, not only in the root's.
- The doc-test pass of a mutation run runs the doc tests alone (`cargo test --doc`), its baseline included: every other test of the mutants it is given already ran under nextest, which missed them, so only a doc test can still catch one, and it no longer runs a crate's whole suite again for each.
- The conformance oracle builds each detector's interpolator when a case asks for it (`interpolatorOf`, in place of the `INTERPOLATORS` table built as its module loaded), the same coefficients: Stryker now runs only the tests that reach those mutants, under a short timeout, where it ran every test under its longest one.

### Removed

- **Breaking:** `visual_core::VisualError` gains `DisplaySizeMismatch`, for a display image given an image of another size, and its `OutOfMemory` names the bytes asked for (`bytes`: 16 a pixel for an image, `Image::PIXEL_BYTES`, 4 for its encoding for display, `DisplayImage::PIXEL_BYTES`), where its message counted 16 a pixel whatever was refused.
- **Breaking (visual-wasm interface, version 4, `0x5056_0004`):** the module exports `visual_display` and `visual_display_len`: an image rendered then encoded for display (8-bit sRGB, straight alpha), its bytes held beside the image by `visual_host::View` (`View::display`, `View::display_len`), allocated with it at setup and encoded without the heap. `VisualDriver.display(index)` returns them as a `Uint8ClampedArray` viewing the module memory, not a copy, valid until the next call, so that a page copies an image once only, into its canvas. For a GPU drawing the square itself, the module also exports `visual_placement` (the square's four edges in an image, exact, `View::placement`, `VisualDriver.placement`), `visual_shader_ptr` and `visual_shader_len` (the library's WGSL shaders, `visual_host::shader`, `VisualDriver.shader`) and `visual_thresholds` (the display shader's thresholds as bits, `VisualDriver.thresholds`). A module of version 3 is refused by the new JavaScript side, and the reverse.
- `VisualModule` (`@poyetik/visual-wasm`) creates the instance it drives, from a compiled module (`VisualModule.create`, as a worker receives one) or from its bytes (`VisualModule.instantiate`); its constructor is private, so two drivers of one instance cannot be written, and the run-time check refusing a second wrapper is gone (breaking).
- An image's creation can fail: `Image::try_new` replaces `Image::new` and refuses an image the machine cannot hold with its size named (`VisualError::OutOfMemory`), never an abort or a trap; `visual-cli` reports it in one `error:` line and the WebAssembly module refuses the setup and stays usable. `PreparedCase::hash` returns a `Result` (breaking).
- The image hash feeds SHA-256 by chunks of 4 KiB laid out on the stack, not one value at a time: the same bytes, so the same hashes, for 8.5% fewer WebAssembly instructions to render and hash an image (`spec/benchmarks.md`, "The image hash fed by chunks").

### Fixed

- The loaded-files gate accepts a shader in a build only when the GPU workspace's test validates it: it reads that test, now its own file (`crates/visual-gpu/tests/shaders.rs`), for each shader of `VALIDATED_SHADERS`, where the two lists were tied by nothing, so that a shader added to the gate's list alone passed unvalidated.
- The loaded-files gate reads the GPU workspace's builds too, its code's and its tests', and the doc tests of every workspace run with their error codes checked: the GPU renderer's builds went unchecked, so that a file its compiler loaded from outside its crate, or a `compile_fail` doc test of it, would have passed unseen.
- The GPU workspace's supply-chain policy drops the root's ban of libm's features, which wgpu's tree turns on, with nothing in its place: `cargo xtask check` now proves that this workspace builds the CPU reference its tests compare the GPU's images with (`visual-core`, `visual-boxes`) with exactly the root's dependencies, versions and features (`cpu_reference_gate`, from `cargo tree` in each workspace).
- The GPU workspace's manifest is held to the root's exactly, as CLAUDE.md says: it holds only its workspace, the root's package fields and lints (no lint added after them), its crate, its dependencies and the workspace's lints, in that order, where the gate only found the root's tables in it, so that a profile, a patch or a lint allowed after them passed.
- The package order gate holds each package's declared build outputs to its manifest: a package that exports files of its `dist/` must list it in its `outputs`, and one that lists it must export it, where the gate trusted the hand-typed list, so that a package newly built for others would have been read stale, as the 13 failures of the last full check were.
- `cargo xtask mutants --since <revision>` mutates the GPU workspace too: a change there runs every mutant of that workspace, after the root's changed lines, where the root's cargo-mutants, which does not see it, reported no mutant to run.
- A mutation run whose baseline log gives no test time says so (`test order: no suggestion, no test time read from …`), where it said nothing, as for a slow group as measured: a change of nextest's output would have silenced every suggestion unseen.
- The preflight of `cargo xtask` refuses nextest's own variables (`NEXTEST_*`): nextest, the test runner of every mutant run, read them from the environment, so that a `NEXTEST_RETRIES` set elsewhere would retry a flaky test until it passed, and another profile or output form would change what the test order is read from.
- Under nextest, a mutant whose tests run no test at all is missed, as under `cargo test`, never caught: nextest ends a run that finds no test with code 4, which cargo-mutants read as a failing test (`--no-tests=warn`, `MUTANT_NO_TESTS`).
- The doc-test pass of every mutation run counts a mutant caught only when its own report lists it caught (`caught.txt`), not when it merely succeeds: cargo-mutants also succeeds when its filters select no mutant, so a mutant whose name a new release words differently would have passed as caught without any test run.
- A failed CI run uploads the WebAssembly module of every package that builds one, the page module's included (`bindings/*/dist/*.wasm`), where it uploaded the two libraries' modules only.
- `cargo xtask check` checks each TypeScript package after the workspace packages it uses, and builds for it, in its part of CI too, every package whose build outputs it reads: the page module's checks read the visual library's `dist/`, and the playground's the page module's, which the checks ran after them, so that once their outputs were emptied before the checks both failed to build. A gate derives both from the manifests (`package_order_gate`): every `@poyetik/*` dependency checked earlier, and exactly the builds a package reads, directly or not, prepared before it (`Setup::Build`).
- `cargo xtask check`'s step checking that every unviable mutant review is current listed the root workspace's mutants only, so that every review of a GPU workspace's mutant (`crates/visual-gpu`) came out stale in the default check; it lists the GPU workspace's too (`gpu_mutants_list_command`), each path from the root.

## [0.7.0] - 2026-11-19

### Added

- The engine's output stage (`spec/engine-design.md`, decision 12): after the plan, before delivery and before any hash, every non-finite sample (NaN or infinite) is replaced by zero and reported, natively (`audio_core::OutputStage<S, D, N>`, computing in the render's sample type; `Renderer::replaced`, a `Replaced` with its `FirstReplaced`, read through `count` and `first`, its fields private so that a count and a first sample always agree, built only by a stage or by the checked `Replaced::new`) as in WebAssembly (`engine_replaced`, the address of four words: the count, the frame of the first in two, its channel; `WasmEngine.replacedCount`, `replaced()`, `replacedFirst()`; the types `Replaced` and `FirstReplaced` of `./web`), on the samples as they are given: a binary64 render given as binary32 is checked after its rounding too, which makes a finite sample beyond the largest binary32 value infinite. A render of a known length (`Renderer::lasting`; `audio-cli` renders each case so) reports only on the frames it delivers, not on what its last block computes past them or leaves in the limiter's delay, so that its report is the same at every engine block, as the engine-block law checks, and refuses to render past them (`CoreError::PastTheEnd`), where a replacement would go unreported; it renders what is left of them at once, sized by itself (`Renderer::render_rest`, offered only by the type of a render of a known length, `Renderer<S, I, D, N, Lasting>`, `audio_core::Length`, where a stream without an end, `Endless`, the default, has no rest to ask for), a length whose samples no value could hold on its target (`isize::MAX` bytes, far fewer frames on a 32-bit target such as WebAssembly's) refused when it is built (`CoreError::RenderTooLong`), a plan without output lasting any length on every target. The engine processor tells the main thread (a `replaced` message: at once, then at most once per `REPLACED_REPORT_SECONDS` of audio, one second), `createEngineNode`'s handlers receive it (`onReplaced`), and the playground says it (a fixed sentence naming a defect of a box as the cause, announced once per start in a live region; the growing count, its digits grouped, and the channel of the first (of the one sample, for a count of one), counted from 1 as it says, shown beside it, never announced; the report of the last start forgotten before the next one is shown); the count saturates at `MAX_REPLACED_COUNT` (2^32 - 1), after which no report follows, and the playground then says "at least", as it does once its session ended (stopped or failed), whose last reports may never have come, where it says "so far" while the session lasts. `audio-cli render` writes one `warning:` line on stderr, naming the case and its patch, the frame and the channel of the sample, the first of several (both counted from 0, as it says), and its cause, a box of the patch; `check`, `bless` and `export` refuse a conformance case that needed any replacement, a defect of a box (`check` even when its hash matches its reference), each refused render named on its own line (`export` writing the others), then one error. The plan laws generate non-finite samples and require none delivered.

- The true-peak limiter of the output stage (`spec/engine-design.md`, decision 12), a component of the core: `audio_core::TruePeakLimiter`, with its settings (`LimiterSettings`, each read back by `ceiling`, `lookahead`, `release` and `adaptivity`, a maximum lookahead and the lookahead under it checked in one place by `within_maximum`, which the limiter and `audio_host::Instance` share, and one setting changed by `with_lookahead`; `Setting`, its `range` and `checked`, the one check of a value against its range; `LimiterError`, a `core::error::Error`) and its peak detector (`Detector`, every one in `Detector::ALL`, from which the interfaces derive their codes and names (`name`), its `phases`, `taps` and `coefficients`; BS.1770's `TRUE_PEAK_TAPS`). It limits only inside an output stage (`OutputStage::limited`), which replaces every non-finite sample before it, since its detector needs finite ones: it has no public way to limit a block of its own, and is not `Clone`, nor is the stage, so that a limiter's state (its delay, its frame, the format of its ceiling) never leaves the stream it limits. It is built for up to `MAX_CHANNELS` channels, a count of fixed width (`u16`), more refused before anything is allocated (`LimiterError::TooManyChannels`, worded as the host settings word theirs: "too many limiter channels: 513 (at most 512)"). It estimates the true peak of each channel through its detector's interpolator and takes one gain for all the channels. The detector is fixed when the limiter is built, since it sets part of its latency (`Detector::delay`): `Precise` by default, a 4x interpolator of 32 taps per phase; `Standard`, BS.1770's own interpolator (`audio_core::TRUE_PEAK_FILTER`), the cheapest; `Mastering`, an 8x interpolator of 128 taps per phase; the windowed interpolators are computed in the math layer. An estimate beyond the format (a sum that overflowed) needs the whole signal taken away. It holds the largest reduction over its lookahead, at its maximum too, releases in two stages mixed by an adaptivity setting, and smooths the reduction with a Hann window as long as the lookahead, whose sums are accumulated exactly over each window as its reductions are released and swapped in once per window, so that no frame sums a window at once. Its control path (the needs, the release, the Hann sums, the gain) runs in binary64 in both precisions, a margin derived from the maximum lookahead added to every need above the ceiling, the gain of each frame is rounded toward zero in the sample type (`Sample::toward_zero`) and the ceiling in the format given, binary32 for a binary64 render given as binary32 (`host::Delivered::NARROWS`): every sample given is at or below the ceiling, with no slack, in every render format and at every finite level, a level above about 6.5·10^10 silenced at -1 dBTP, a maximum lookahead of 5 ms and 384 kHz, higher at lower rates and shorter maximum lookaheads, whatever the lookahead in force (3.1·10^13 at a maximum of 0.5 ms and 8 kHz, `spec/limitations.md`). Below the ceiling it changes no bit: its output is its input delayed by its latency. Its maximum lookahead and its detector, fixed when it is built, set that latency (`TruePeakLimiter::latency`). Its other settings and its mode change live, the ceiling held across each change (a lowered one from the maximum lookahead on, in frames after the change, within the latency, every sample at or below the old one until then), the ceiling, the release and the adaptivity from the next frame, and a new lookahead held pending while its input needs a reduction (a switchable stage's switched to raw too), the last one set counting (any number of sets between two frames acting as the last one alone, one set back to the lookahead in force dropping it), and taken at the limiter's next rest, a frame by which a count certifies its whole control state zero as in a limiter always at the new lookahead, from where it renders bit for bit what a limiter always at the new lookahead renders, with no click, pending until then (`TruePeakLimiter::pending_lookahead`, `OutputStage::pending_lookahead`, the lookahead asked for while it is pending): `K` frames, about 71 release time constants, after its last frame needing a reduction (about 7.1 s at the default release of 100 ms, 71 s at 1,000 ms; a release or an adaptivity of another pace set meanwhile counting again, but at rest, and sets between two frames acting as the last one alone), when every state of a limiter at any lookahead has decayed to zero, some time after the first frame where it is (14.6% later after a one-frame over of 0.1 dB, 2.5% later after a second 20 dB over, measured), never while its input needs a reduction, and on its next frame for a limiter whose input never needed one or one at rest; and no value the control path stores below 2^-100 is kept (a release stage, a share, the reduction a frame applies), far below every need, its Hann sums, derived from those, proven zero or normal, so that it computes no subnormal number, a host flushing them computes every value alike (derived; tested under the flushing mode of x86_64 in CI and of aarch64 on the maintainer's Mac), and a release ends at exactly zero: ceiling -20 to 0 dBTP (default -1), lookahead 0.5 to 5 ms (default 1.5), release 10 to 1000 ms (default 100), adaptivity 0 to 1; raw or protected by a crossfade that arrives exactly, raw giving its input delayed bit for bit. Each detector's under-read and the limited sine's true peak and distortion are derived from the coefficients and measured (`spec/measurements.md`, "The true-peak limiter").

- The output stage limits when it has a limiter (`OutputStage::limited`, `OutputStage::latency`), after replacing non-finite samples, in the computing precision: a binary64 render given as binary32 is limited before its rounding, then rounded and checked as given in one call (`OutputStage::apply_narrowing`). The stage owns its blocks, one per channel, generic over the format it gives and the engine block (`OutputStage<S, D, N>`: a binary64 stage gives `f64` or `f32`, its limiter's ceiling rounded toward zero in binary32 from its first block when it gives `f32`, and only a binary64 stage giving `f32` has `apply_narrowing`, which returns the blocks as given, while only a stage giving its samples as computed has `apply` and `blocks`, `AsComputed`, so that no stage hands out blocks in a format it does not give, where the rounding could leave a sample infinite and unreported): a raw stage is built for a channel count (`OutputStage::new`), a limited one for its limiter's (`TruePeakLimiter::channels`), and the plan writes into them (`OutputStage::apply` and `apply_narrowing` take the function that writes them, `apply` returning them, `OutputStage::blocks` reading them), so that every block it applies to is one it limits. Its limiter is read through `OutputStage::limiter` and changed only through the stage, live (`OutputStage::set_limiter`, `OutputStage::set_protected`, refusing with a `StageError`: `Raw` for a stage without a limiter, `Limiter` with the limiter's refusal, kept as its cause, `Locked` for a protected stage told to go raw); the limiter is built in a mode (`LimiterMode`, `TruePeakLimiter::mode`): protected from its first frame and never switched to raw, or switchable, raw first, and only its stage switches it. `Renderer::with_stage` renders through a stage at its first frame of as many channels as the plan has (`OutputStage::channels`): a stage of another count (`CoreError::StageChannels`) or that applied a block already (`CoreError::UsedStage`) is refused. `Renderer::latency` says by how much it delays every sample. `Renderer::new` stays raw. The safe engine is built with its output stage (`audio_host::Output`: `Output::Raw`, which has no limiter and so no limiter setting, or `Output::Protected` or `Output::Switchable`, each with its `LimiterStage`, non-exhaustive, built by `LimiterStage::new`: the maximum lookahead, the detector and the limiter's settings, `limiter`; its `OutputMode`, every one in `OutputMode::ALL` with its `name`) and reports and changes it live (`Engine::latency`, `Engine::replaced`, a `Replaced`, `Engine::set_limiter`, `Engine::set_protected`, `Engine::pending_lookahead`, the lookahead its limiter asked for while it is pending; `Instance::output`, `limiter`, `protect`, `latency`, `lookahead_pending`). The instance stores the stage every later load builds whole, with its limiter's settings, their lookahead checked against its maximum in the same call (`Instance::output`, a raw stage reading none of them), and changes the loaded engine's limiter live only, checked against that engine's maximum alone (`Instance::limiter`). The WebAssembly engine builds the stage its host sets before a load (`engine_output`: raw, or protected or switchable with the maximum lookahead and the detector, which fix the limiter's latency, and the limiter's settings). The host sets the loaded engine's limiter live (`engine_limiter`), switches its protection by a crossfade (`engine_protect`), a switchable stage only going raw (a protected one stays protected: its stage refuses it, and `Engine::set_protected` and `engine_protect` relay the refusal), reads the stage's latency (`engine_latency`), and whether a lookahead set live is pending (`engine_lookahead_pending`, 1 or 0, without the heap). The engine limits bit for bit like the native renderer through the same stage.

- The output stage from TypeScript: `WasmEngine.create` takes an output stage (`Output`, of a mode of `OUTPUT_MODES` (`OutputMode`): raw, without a limiter or its settings (`RawOutput`), or protected or switchable, with a maximum lookahead, a detector (`DETECTORS`, `Detector`) and `LimiterSettings` (`LimitedOutput`); `RAW_OUTPUT` by default, `PROTECTED_OUTPUT`, `DEFAULT_LIMITER`, `MAX_LOOKAHEAD`, the longest lookahead and so the largest maximum, and `MIN_LOOKAHEAD`, the shortest, each tested at the engine's end of its range, the processor's message of a lookahead applied read within them), reports its `latency` and whether a lookahead set live is pending (`lookaheadPending`, read without allocating, a module answering neither 1 nor 0 ending the engine), and changes it live (`setLimiter`, `setProtected`, which refuses to switch a protected stage to raw), the engine's refusals thrown as an `OutputError` with its explanation, read like every other call of a live engine (a module error or a trap there ending the engine). `loadPatch` and `LoadedPatch.load` take the output stage too, read once by the processors' own reader into a frozen copy (a field of the wrong type refused as a `TypeError`), which the main thread checks and the processors get (`LoadedPatch.output`, `LoadedPatch.latency`). The playground plays protected (decision 12), and says so on its page, with the limiter's ceiling.

- A build names its engine block at compile time by the variable `POYETIK_ENGINE_BLOCK` (`audio_core::NAMED_ENGINE_BLOCK`): one of `ENGINE_BLOCKS`, any other name not compiling. Starting twice or stopping during a start is safe. The sound fades in and out over 20 ms and the device is released only after the fade, on the audio clock: no click. A browser lacking a secure page, Web Audio, AudioWorklet or WebAssembly is told what is missing. The button keeps the keyboard focus across transitions (`aria-disabled` instead of `disabled`) and looks different while it stops the sound.
- **Breaking:** `LoadedPatch` (engine-wasm web API) is a class only `loadPatch` creates, with its own copies of the bytes: a patch the engine did not check cannot be passed to an engine node. `createEngineNode` takes an `onFailure` callback and returns `{ node, ready }`: the processor tells the main thread whether it loaded the patch, and reports a later failure (a trap) once, instead of falling silent unnoticed. `renderOffline` rejects instead of returning silence when the processor fails.
- **Breaking:** conformance expectations no longer declare a tolerance (`max_error`, refused if present). The oracle derives the largest allowed distance from the ideal sine, term by term (binary32 output rounding, binary64 phase accumulation over the case length, evaluation), and computes its reference with an exact phase reduction, so it stays exact however long the case (up to 2^29 frames). The bound went from a guessed 1e-6 to 2.98e-8 at 1 s; a phase computed in binary32 (1.7e-3) or a gain off by 5e-7 is rejected. The `osc~` tests use the same bound.
- **Breaking:** the patch of each conformance case is its own file, `conformance/patches/<name>.json`, and every runner (native CLI, Node tests, browser bench) passes its bytes to the engine unchanged. The runners used to rewrite the patch from a parsed copy, which could hide differences (a repeated parameter was silently merged; JavaScript writes `-0` as `0`). `engine-cli render` takes the case and the patch files. A case without its patch, or a patch without its case, is an error.
- The playground plays the same document as the sine-440 patch of the conformance corpus (compared after parsing by a test), whose render has a reference hash.
- **Breaking:** `Patch` is a validated type, built only by `Patch::new`: box ids are unique, cables are never repeated, and a patch holds at most 65,536 boxes and 262,144 cables. The cables into an inlet are summed in a fixed order (source id, then outlet), whatever the order of the document. The patch reader also refuses documents over 16 MiB and a parameter named twice in one box.
- **Breaking:** `Renderer::render` continues exactly where the previous call stopped (rendering `a` then `b` frames equals rendering `a + b`), and returns `CoreError::RenderTooLong` instead of failing when the samples cannot be held in memory.
- Execution order is computed with Kahn's algorithm, in O((N + E) log N) instead of O(N²·E): a patch of 16,000 boxes is ordered in milliseconds instead of seconds. The order is unchanged.
- Error messages name the faulty element once and say what is expected ("box 2 is declared twice", "invalid sample rate: 5 Hz (supported: 8000 to 384000 Hz)").
- The conformance CLI refuses a case whose patch has no audio output, instead of rendering nothing.
- The box laws (`engine-testkit`) run at every sample rate of a shared test matrix (8 kHz to 384 kHz, including 44.1 kHz), with special inputs (signed zeros, subnormals), a long run and parameters away from their default; a box that fails at any of them fails the laws. The matrix is also published as `conformance/test-matrix.json` for the TypeScript tests.

- `@poyetik/config/one-line`: `oneLine(text)`, the TypeScript twin of `engine_patch::safe_message` (the same escaped characters, the same `\u{..}` form, the same 1,000-character bound), for the TypeScript command-line tools; both are tested on the shared vectors of `spec/safe-message-vectors.json`.
- Oracle: a case, reference or expectation file that is not UTF-8 is refused with one `error:` line naming it, as the engine's own reader refuses it; a byte that is not UTF-8 used to be replaced and the file read anyway.
- engine-wasm: a malformed message from a processor (an engine message or a render quantum from a tap) is reported as "invalid message from the processor", no longer as "invalid processor options".
- engine-wasm: when the engine traps in the browser, the failure reported to the main thread now includes the trap itself ("RuntimeError: unreachable", "memory access out of bounds"), the only clue a module built with `panic = "abort"` gives.
- engine-wasm: `interleave` refuses channels of different lengths instead of padding or cutting them, and `renderHash` refuses a rate that is not a 32-bit unsigned integer (44100.5 was hashed as 44100, -1 as 4294967295), a channel count that is not a whole number, and samples that are not whole frames: a hash is a proof, never computed over something else than what was asked.
- engine-wasm: rendering on the audio thread no longer allocates before V8 optimizes it: whole blocks are copied at once through views of the module memory made once, and no field holds a boxed number. `pnpm test:allocation` now drives the real engine processor from a fresh instance, also with V8's interpreter alone, at every host buffer size of the matrix; CLAUDE.md states what it proves and the known deviations.
- engine-wasm: a block the module places outside its memory, or at an unaligned address, is a `ModuleError` and the engine stops, instead of being read as silence.
- **Breaking (engine-wasm web API):** the marker channel counts the frames the engine renders (1, 2, 3…) instead of holding 1.0, so a live capture or an offline render now fails when the capture started after the engine (it returned shifted frames), when the engine stopped before the end (it returned a silent tail as success, whatever the order of the messages), or when the channel holds no marker; the marker is read in place, no longer copied into a JavaScript array (136 MB for 10 s at 384 kHz). `createEngineNode(…, true)` returns a `MarkedEngineNode`, the only engine node `captureEngine(context, engine, frames)` accepts: it no longer takes the channel count. Both refuse more than `MAX_MARKED_FRAMES` frames, the most the marker counts exactly.
- engine-wasm: creating an engine node no longer uses `Promise.withResolvers`, which Safari before 17.4 and Firefox before 121 lack: they now reach the playground's explanation of what is missing instead of a `TypeError`. The shared lint configuration bans it.
- Playground: starting the player no longer uses `Promise.withResolvers`, which Safari before 17.4 and Firefox before 121 lack: those browsers now reach the explanation of what is missing instead of a `TypeError` (the shared lint configuration bans it).
- engine-wasm: `pnpm build:wasm` and `pnpm test:reproducible` follow the command-line contract: a failed or missing cargo is one `error:` line (exit code, signal, or why it could not run) instead of a Node stack trace, and the problems of a build that is not reproducible are listed on stdout under one `error:` line. Both are now tested, with 100% coverage and no surviving mutant, around thin entry points; `test:reproducible` prints the SHA-256 of the module, to compare builds across machines.
- engine-wasm: the test bench server refuses a port that is not a whole number from 1 to 65535 with one `error:` line and exit code 2, instead of a stack trace; its port parsing and content types are tested functions of `e2e/routes.ts`.
- engine-wasm test bench: a missing build, case or patch fails with the URL and the status (`GET /conformance/cases/x.json: 404`) instead of a JSON or WebAssembly error about an empty body.
- engine-wasm: the README's command to open the test bench works (`ENGINE_WASM_E2E_PORT=4392 pnpm bench`): it builds the bench page and starts the server, and it is the very command the end-to-end tests start.
- engine-wasm test bench: the Content Security Policy test could not fail on Firefox (it looked for console text Firefox words differently) and had no control. It now listens to the page's own violation reports and to console errors while rendering offline and capturing live, checks the declared policy, and proves enforcement with a blocked image. It found a real violation: Firefox's request for `/favicon.ico`, blocked by the policy; the bench now has its own icon, allowed by `img-src 'self'`.

### Security

- The oracle prints every verdict and error line safely, like `engine-cli`: what it quotes from the corpus (a case name or JSON key, a WAV chunk id, the JSON parser's excerpt of a file) has its control, bidirectional and line-separator characters escaped as `\u{..}` and is cut after 1,000 characters (`oneLine`). A crafted key or chunk id can no longer drive the terminal or split a `FAIL` verdict into two lines.
- The roadmap CLI prints every error as one safe line, like `engine-cli`: what it quotes (an argument, a field of `board.json`, the JSON parser's excerpt of the file) has its control, bidirectional and line-separator characters escaped as `\u{..}` and is cut after 1,000 characters (`oneLine`). `show $'1\nerror: forged'` can no longer forge a second error line, nor a board column holding ESC drive the terminal. A text of the board (title, card title, description, milestone, step) may no longer hold such a character, whether read from `board.json` or typed on the command line: it is refused, not escaped, since the page and the listings show it as it is.
- Playground: the build fails when the page lacks the element its Content Security Policy is inserted after, instead of silently building a page without a policy; the insertion is now in `csp.ts`, under coverage and mutation testing.
- `engine-cli` prints every error as one safe line: control, bidirectional and line-separator characters coming from a patch (a box or field name) are escaped as `\u{..}`, and the line is cut after 1,000 characters. A crafted patch can no longer drive the terminal or forge a second error line. Every line it prints on stdout is made safe the same way (each line passes through `engine_patch::safe_message`; only the usage of `engine-cli help` is printed as is): a case name, a box type quoted by `check`'s `FAILED` line, or a key or value of `references.json` could forge an `ok` line on stdout and drive the terminal, and a line had no length limit.
- **Breaking (engine-wasm interface, version 2, `0x5059_0002`):** the module exports `engine_max_patch_bytes`, the 16 MiB limit of the patch format, and `WasmEngine.create` refuses a longer patch with a `PatchError` ("patch too large: … bytes (at most …)", the engine's own words) before asking the module for memory: a huge patch grew the module memory, which is never given back, before the engine refused it. A module of version 1 is refused by the new JavaScript side, and the reverse.
- engine-wasm: the explanation of a rejected patch, which JavaScript receives as `PatchError.detail`, is made safe the same way: one line, control and bidirectional characters escaped, at most 1,000 characters. `engine_patch::safe_message` is the one function both use (`engine-cli` no longer exports `MAX_ERROR_CHARS`; the limit is `engine_patch::MAX_MESSAGE_CHARS`).
- The JavaScript supply chain is checked like the Rust one: `pnpm audit` runs in `cargo xtask check` (the five moderate advisories in development tooling, all in transitive dependencies of Stryker and ESLint, are fixed by pnpm overrides), and a license gate allows MIT, Apache-2.0, BSD-2/3-Clause, ISC and 0BSD for what the apps ship, a wider list for tooling, and one documented exception (sharp's image library, build time only).
- The playground, the roadmap and the engine test bench declare a Content Security Policy: everything from the site itself, no inline script or style, and only `'wasm-unsafe-eval'` where the engine runs. End-to-end tests check on every browser that the page declares it, breaks none of it, and that it is enforced (a blocked image as control). The roadmap's styles are no longer inlined. The roadmap's end-to-end tests serve on a free port too.
- The end-to-end test server serves only the bench, the built package and the conformance cases, patches and references, to this machine only: a path such as `/conformance//etc/hosts` read any file, and any host name was answered (DNS rebinding).

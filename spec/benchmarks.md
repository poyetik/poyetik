# Benchmarks

What the engine's cost benchmarks measure, how their thresholds are derived, what they cannot see, and how to add one (roadmap #12 step 3). They exist so that the cost of the engine's later decisions (`engine-design.md`, implementation order) is measured, not guessed. The visual library's are below ("Visual library"): the square's render, its hash, its display encoding and its placement counted in WebAssembly, with the module's size, and the GPU's render timed; one per visual box with #35 step 12 (`limitations.md`).

Two kinds of measurement, with opposite properties:

1. **Instruction counts** of the engine's WebAssembly module, for each box at representative settings, for the plan's own sums, for whole patches played, and for building plans of several sizes, with the size of the module itself: deterministic, identical on every machine, compared exactly with the baseline. `pnpm benchmarks:check` in `bindings/audio-wasm` (part of its `pnpm check`, so of `cargo xtask check`).
2. **Wall time** of constructing the engine processor, and of rendering each box in both precisions, in Chromium, Firefox and WebKit: noisy, asserted only as upper bounds with a wide margin. End-to-end tests of `bindings/audio-wasm` (`pnpm test:e2e`, part of the same check).

## Instruction counts

### How they are counted

The engine module of the default engine block, 64 frames (`bindings/audio-wasm/dist/engine.wasm`, a reproducible build; the modules of the other engine blocks, the playground's 128 frames included, are not counted yet: roadmap #24 step 113), is rewritten by the instrumenter (`@poyetik/wasm-build/instrument`, `tooling/wasm-build/src/instrument.ts`): before every straight-line run of each function, it adds the run's number of instructions to a mutable 64-bit global, exported as `instructions`. A run starts where a branch may land (the start of a function, after `block`, `loop`, `if`, `else`, `end`, and after `br`, `br_if`, `br_table`, `return`, `unreachable`), so whenever one of its instructions runs, all of them do. Calls do not end a run: execution comes back after them. Right before every bulk memory instruction (`memory.copy`, `memory.fill`, `memory.init`), it also adds the words that instruction moves, computed from the length it is given.

**What counts as one instruction:** every WebAssembly instruction executed, except the structure markers `block`, `loop`, `else` and `end`, which compute nothing; and every 8-byte word a bulk memory instruction moves, ceil(length / 8) on top of the instruction itself, since its work grows with its length (one copy of a 64-frame block of binary64 samples counts 1 + 64). A word is charged as one instruction, where a loop copying it would execute a few: the charge is a floor of the work, never zero, so a copy added to every block shows in the counts. The instructions the instrumentation adds are not counted. A bulk table instruction (`table.copy`, `table.fill`, `table.init`), whose work also grows with its operand, is refused, as the engine module holds none; growing the memory or a table counts as one, its work being the host's.

**Proofs.** Hand-assembled modules with counts worked out by hand (a loop of any number of passes, each arm of an `if`, a call, copies and fills of 0, 1, 7, 8, 9, 512 and 65,536 bytes, a fill in a loop, and a length of 2^32 - 1 bytes charged before the module traps); every understood instruction decoded with its immediates and compared byte for byte with the expected rewriting; every conformance case rendered by the instrumented module with its native reference hash, so the instrumentation changes no result; every instruction the instrumenter does not understand is refused, naming it and its byte, never skipped, so a new compiler feature (vector instructions, tail calls) fails the check until the instrumenter learns it.

**Why it is deterministic.** The count depends only on the bytes of the module and on what it is asked to do. The module is built reproducibly with the pinned toolchain, so the counts are meant to be the same on every machine building with the pinned toolchain, a developer's Mac and the CI runner (CI's first comparison: the pull request of #12 step 8), whatever the load of the machine: a baseline is shared by every machine, and a change of a count always comes from a change of the code, the compiler or the benchmark.

### What they do not see

A WebAssembly instruction count is a proxy for cost, not a time:

- **Native code**: each browser compiles the module to machine code with its own compilers and tiers; one WebAssembly instruction becomes zero, one or many machine instructions, differently in each engine. The native engine (`audio-cli`, plugins) is not measured at all.
- **Memory and caches**: a load that misses every cache counts as much as one that hits; the cost of memory bandwidth (decision 10's 64-bit samples) is invisible.
- **Vector width**: a vector instruction counts as one, however many lanes it computes (the module has no vector instructions today; the instrumenter refuses them until it is taught them).
- **Instruction cost**: a division, a square root and an addition each count as one; a bulk copy counts one per word it moves, the floor of what a loop would execute for it.

So a count catches what changes the work done (an algorithm, a loop, an approximation, a copy, a bulk copy by the words it moves); it does not rank two designs whose work differs in kind. The wall time of each box in each precision on each browser engine ("Rendering each box" below) measures what counts cannot: the real binary32/binary64 ratio decision 10 speaks of.

### What is measured

**Each box at representative settings and in both precisions** (`BOX_BENCHMARKS` in `benchmarks/suite.ts`; each entry of the baseline names its `precision`): the instructions of `BLOCKS` blocks of a patch holding the box, minus those of the same blocks of the same patch without it, each in a fresh instance, computed in that precision and given as binary32, as the browser's audio thread is given it (so a binary64 count includes rounding the box's share of the output to binary32). So a count is the box's `process` plus what the plan does for it each block (gathering its inputs, its outputs written straight into the bus slots the cables read), which is what a patch pays for it. The settings cover low and high sample rates and frequencies, a constant output, and an output fed or not; their names are in the baseline.

**The plan's sums, in both precisions** (`MIX_BENCHMARKS` in `benchmarks/suite.ts`, under `mixes` in the baseline, named `mixing <setting> in <precision>`): what the plan does per block to add up several terms in the reduction order (`engine-design.md`, decision 28), which no box benchmark sees. Each is the instructions of `BLOCKS` blocks of a patch summing several terms into one place, minus those of the same boxes summing one (which the plan feeds by a plain copy, decided when it is built: so each difference is the sum against a copy), each in a fresh instance, computed in that precision and given as binary32: n oscillators into one inlet of a `dac~` minus the same oscillators with only the first cable, for n = 2 (one addition), 3 (a partial tree), 16 (the full tree) and 17 (a lane holding two terms); and two `dac~` fed by one oscillator on the same channels minus one `dac~` (whose difference also holds the second box's own work, which its box benchmark counts).

**Whole patches, in both precisions** (`PATCH_BENCHMARKS` in `benchmarks/suite.ts`, under `patches` in the baseline, named `playing <setting> in <precision>`): the instructions of `BLOCKS` blocks of a patch, in a fresh instance, computed in that precision and given as binary32, nothing subtracted. Every box and mixing benchmark is a difference, so a cost every patch pays each block whatever its boxes (the engine's and the plan's own work outside the boxes) cancels from all of them; these two show it. The empty patch is the engine's fixed cost of a block: a per-block cost added for every patch shows there whole, against the smallest count of the suite. The heavy patch, 16 `dac~` each fed by 3 oscillators into its left inlet, the first also into its right (`summingPatch`: 16 sums of three terms into inlets, two output channels of 16 terms each, 64 boxes and 64 cables), shows a cost that grows with the patch (by its boxes, its cables or its sums) beyond the tolerance of the whole. A unit test proves both sides on a stand-in module whose blocks cost a fixed number of instructions more: the whole-patch counts rise by exactly that number per block, every difference stays the same.

**Building plans** (`PLAN_SIZES`, at `PLAN_RATE`): the instructions of loading a patch of n oscillators feeding the two inlets of one `dac~` in turn (n + 1 boxes, n cables), copying the patch into the module, parsing it and building its plan included: what the engine processor does when it is constructed (`engine-design.md`, decision 15).

**The size of the engine module** (`module_bytes` in the baseline, reported as `engine module: <n> bytes`): the bytes of `bindings/audio-wasm/dist/engine.wasm` as built, before instrumentation. What a page downloads and compiles before it plays, and what the engine processor compiles on the audio thread (decision 15): the deterministic proxy of load time, as instruction counts are of CPU time, deterministic for the same reason (the build is reproducible). It is compared with the same tolerance, either way; the absolute budget of the module and a committed digest of its bytes are #11 step 3's.

### The n log n law

`Plan::build` sorts the boxes in O((N + E) log N) (`audio-core`, `plan.rs`). The check asserts it on the counts: for each plan size and the next, the ratio of their counts must not exceed the ratio of n log2 n. A cost a·n log n + b·n + c with non-negative terms always passes (its ratio is at most that of n log n), so the law holds whatever the constant parts; a quadratic term fails as soon as it dominates, since a quadratic cost grows as the square of the ratio of sizes, more than n log n allows for any sizes above 2. The law holds only for plans of 2 oscillators or more (n log n is 0 at 1), each costing something, in increasing size: it reports a plan outside that as a problem, never passes it. Unit tests prove the law accepts n log n, linear and constant costs at its edge and refuses a quadratic cost and every plan outside its domain; `bless` refuses to write a baseline that breaks it.

Today's boxes have either no inlet (`osc~`) or no outlet (`dac~`), so the plans are bipartite; deeper topologies join the plan benchmarks with the first box that has both. The plan's per-block work on fan-in (several cables into one inlet, several output boxes on one channel) is measured by the mixing benchmarks above.

### Threshold: the tolerance

`tolerance_percent` of `benchmark-thresholds.json`, in both directions, for every count.

**Derivation.** The counts have no noise: a count differs from the baseline only when the code, the compiler or a benchmark changed. So the tolerance does not absorb noise; it decides which change needs a reviewed new baseline:

- **above**: a regression of a box, of the plan's sums, of plan building or of the module's size by more than the tolerance fails the check. A smaller drift (a refactoring of the plan's per-block work, a compiler upgrade reordering code) passes, so that unrelated work does not force a re-bless at every commit; drifts do not accumulate unseen, since the baseline only moves through a reviewed bless and each change is compared with it.
- **below**: a count that fell by more than the tolerance also fails, so that the baseline stays tight: an improvement is recorded by a bless, and a later regression is measured from it, not from the old count.

What the tolerance cannot see is a trade smaller than it on every benchmark: a change that costs a few instructions per block on light patches and saves a few per sum on heavy ones moves the heavy patch by a fraction of a percent. Such a trade is decided by a dated entry of "Measured design choices", measured at one and at many of the things it scales with (boxes, sums, channels), with its break-even; the check holds it only within the tolerance.

So the tolerance is positive and below 100 (the reader refuses any other): a count cannot fall by 100% or more, so a wider tolerance could never refuse a fall. The baseline's reader also refuses any key it does not name and an entry repeated (the comparison is by name, so a second entry would hide the first), and `measure` refuses two benchmarks of one name.

### Changing the baseline

Through `cargo xtask bless-benchmarks` (the process rule above), which builds the module, counts every benchmark and rewrites `benchmark-baseline.json` (refusing to when the n log n law fails). The commit that changes the baseline says why the counts changed, and names the commit that moved each count, or says in a dated entry that it is not located yet (a count moved by commits before the bless is located by building each, as "Where loading and the module rose between the engine-block bless and the slices bless" did). Lowering a count by a bless is always allowed; raising one needs the reason in that commit, with what the extra cost buys.

### The cost of each precision

`benchmark-baseline.json` gives every box in both precisions; what its counts show, binary32 against binary64 given as binary32 (the counts themselves are in the baseline, the one source):

- `osc~` computes its sine with `libm`'s binary32 sine in binary32, about a third fewer instructions than the binary64 sine; at 0 Hz both sines take their shortest path, and rounding the angle to binary32 makes binary32 the dearer.
- `dac~`'s binary64 count holds the per-sample rounding of its channels to binary32 for delivery, which binary32 does not pay (binary32 is delivered as it is); a patch pays it once per output sample, not per box. Which part of that rounding costs most is not measured yet: roadmap #12 step 22 breaks it down.
- What the counts cannot see (above): a binary64 sample is twice the memory and bandwidth of a binary32 one, a vector holds half as many (the module has no vector instructions yet), and an instruction of the binary64 sine counts as one of the binary32 sine whatever their latencies. The wall times of "Rendering each box" measure the real ratio on each browser engine.

### Same cost through every interface

No architecture choice may cost performance (`engine-design.md`, decision 33): the libraries are crates of one program, and of one WebAssembly module per thread in the browser (externals apart; the audio thread's built for its engine block), and an interface between them costs nothing measurable against calling the code directly: today the instruction counts hold it within the counts' tolerance; each comparison below, when it lands, is exact or within a per-call allowance derived and written for its interface, since the tolerance alone would let an interface cost up to the tolerance of a count. The instruction counts prove it, never an argument:

- **The box contract's ABI** (roadmap #12 step 13): every box benchmark is counted twice, the box called directly and through the ABI form, with the same patch, rate and precision; the count through the ABI is held to the direct count exactly, or within a per-call allowance derived and written for the ABI (its canonical NaNs, decision 25, are work per sample), as the renders are held to the same bits.
- **The public interface** (roadmap #32 step 8): the engine driven through its public interface (Rust, the C interface, TypeScript over the module) is counted against the same patches driven directly, exactly or within a per-call allowance written for each interface.
- **The precedent**: the sample newtypes `Binary64` and `Binary32` (decision 10) added no instruction measured when they replaced plain floats, and are held within the counts' tolerance since (roadmap #24 step 86 makes that comparison exact).
- **The plan's call of each box**: a built-in box type is called directly, through `audio_boxes::BuiltIn` (decision 33); only a box type loaded at run time goes through its virtual table, one indirect call per box per block. The direct call is fewer instructions per box per block for slightly dearer plan loading and a larger module, the price accepted for the faster real-time path; a box's state stays on the heap, the faster per block (both measured and dated in "Measured design choices" below, "How the plan calls its boxes").
- **A box's parameters**: a box is created with `audio_core::Params`, a borrowed slice passed by value (two words), which leaves plan loading as it was without the type; the plan creates each instance from its `ParamValues`, which carry the box type they were checked against (`Dispatch::create`), at no cost ("Measured design choices" below).

A benchmark through an interface that exceeds its direct count beyond its allowance fails the check like any other regression; the interface is changed, never the allowance nor the tolerance.

## Visual library

The visual library's module (`bindings/visual-wasm/dist/visual.wasm`) is counted by the same instrumenter and compared by the shared harness (`@poyetik/wasm-build/bench`, which the engine's benchmarks will use too, roadmap #24 step 165), with its own suite (`bindings/visual-wasm/benchmarks/suite.ts`) and baseline (`spec/visual-benchmark-baseline.json`), blessed by `cargo xtask bless-benchmarks` with the engine's and checked by `pnpm benchmarks:check` in every check.

**What is measured.** At four image sizes, each four times the pixels of the one before (64×36, 320×180, 640×360, 1280×720), in a fresh instance with the square set up (not counted): the instructions of rendering one image, of rendering it and encoding it for display (`visual_display`), and of rendering and hashing it, and of placing the square in it (`visual_placement`, what a page drawing the square on its GPU asks for every image); and the module's size in bytes. The square is the only visual box today; the suite measures each box that comes.

**The law: an image costs its pixels.** An image's cost is proportional to its pixels, plus what it costs once: for the render, and for the render and hash, the cost per pixel at every size must be within 2% of the largest size's (measured 2026-11-16: 88.19 instructions a pixel at 64×36 against 87.04 at 1280×720 for the render, 1373.82 against 1369.99 for the render and hash). A box whose cost grows faster than its pixels, or whose fixed cost swamps a small image, breaks it, and bless refuses to write. The placement's law: its count is the same at every size, the largest's (a few integer operations on the square's edges, whatever the pixels: 681 instructions at every size for image 7, and at 1×1 and 16 384×2048 too, measured 2026-11-20); a placement whose cost grows with the image breaks it. The page module's own per-repaint call, `page_image_at`, is counted with #35 step 3, which rewrites it. The display encoding's law holds from 320×180 on: its cost a pixel depends on the image (a value of 0 or 1 is encoded at once, an edge pixel's partial coverage through a bucket and a comparison or two), and the square's edges are a share of the pixels that falls as 1 / height (measured 2026-11-18: 215.8 instructions a pixel at 64×36, 209.9 at 320×180, 208.8 at 1280×720 for the render and display: 3.4%, then 0.5%, from the largest).

**Changing the baseline.** As the engine's ("Changing the baseline" above), for `spec/visual-benchmark-baseline.json` too: through `cargo xtask bless-benchmarks`, the commit saying why the counts changed and naming the commit that moved each count, or a dated entry below saying it is not located yet; lowering a count is always allowed, raising one needs the reason in that commit, with what the extra cost buys.

**Threshold.** As the engine's: 2% either way, a review trigger, not a noise margin. A whole percentage, which the harness requires (any other is refused before measuring), so that the comparison is exact: in integers, where products of counts above 2⁵³ would round as numbers.

**What they show already.** Hashing an image costs about 16 times rendering the square (1370 against 87 instructions a pixel, 16 bytes a pixel): SHA-256 itself, about 80 instructions a byte in WebAssembly (86 with the render), which has no instruction for it. The image hash checks conformance; a page drawing live images does not hash them. Its measured choices come under "Measured design choices" below.

**What they do not see.** The cost of a box other than the square, and the display encoding of a translucent pixel: the square is opaque, so only the encoding of opaque pixels is counted (roadmap #35 step 12).

**The split costs nothing at render** (#34 step 6; 2026-11-18). The page loads one module, `page.wasm`, holding the visual library and the coordinating layer; the audio worklet loads the engine's module alone. Drawing an image through the page module costs exactly the visual module's instructions (render, display, hash: equal to the instruction, `bindings/web-page/test/split.test.ts`); the page module is larger by the layer's interface only (655 bytes: 70,302 against 69,647, measured again 2026-11-19 once both held the display corpus's encoding), held under 1 KiB; the worklet's module exports nothing of the visual library and holds no shader (`apps/playground/test/split.test.ts`), so the split leaves the worklet's start-up as it was: its module is the one it loaded before.

**The GPU renderer** (`visual-gpu`; the maintainer's decision, 2026-11-17). A GPU's instructions cannot be counted as WebAssembly's are, and its time depends on the GPU, so its benchmarks are in two layers:

- **Exact counts, checked on every machine**: what rendering an image costs in transfers and work (`render_cost`: its bands, the workgroups dispatched, the bytes uploaded and read back), the same on every GPU whose buffers allow the same bands; its tests hold them per size at the bands every WebGPU device allows (128 MiB a band), proportional to the pixels: 16 bytes read back a pixel and 16 a band (its pass's two timestamps), 32 bytes uploaded a band. Encoding an image for display has its own (`encode_cost`): 16 bytes uploaded a pixel and 16 a band, 4 bytes read back a pixel and 16 a band, the workgroups of 64 dispatched in rows of at most the GPU's limit.
- **The GPU's own time, per named GPU**: the median of 15 measured renders after 15 to warm up, by the GPU's clock (timestamp queries around each pass, so that the CPU's work between passes does not count): a pass is measured only when the GPU wrote both its timestamps, neither Metal's error value (all ones), the end after the start, its time at least 1 ns once rounded (a driver's clock period no pass can be timed with (0, negative, not a number, infinite, at most 2⁻⁶⁵ ns or at least 2⁶⁴ ns) reads as no clock), each pass with a query set of its own, and the renders go on until 15 are, at most 45 (Metal leaves some unmeasured; at 1280×720 every run recorded measured its first 15); each median says how many renders it took, a size never measured is shown as unmeasured, never as 0, and a clock measuring fewer than 15 of 45 at 1280×720 fails the check and the bless; a GPU without a clock is answered at once, nothing rendered: `bless` fails, and so does `check` on a GPU the baseline holds, so that a clock lost to a wgpu or driver change never turns the gate off on the machine it exists for. At 1280×720 it is checked only on a GPU whose time `spec/gpu-time-baseline.txt` holds (read only exactly as `visual-gpu bless` writes it, at least one GPU's time, so that an emptied or edited file fails rather than checks nothing; the baseline is keyed by the GPU's name, so that another machine with a GPU of the same name is checked against it; a GPU runner of CI and a baseline keyed by the machine are roadmap #35 step 12's); on any other GPU, CI's software GPU included, `visual-gpu check` renders nothing and says the GPU has no baseline, so that its time is not checked. The baseline records, beside each GPU's time (the median of 5 runs, each its own GPU device opened afresh, measured as the one run of a check is), the system and the GPU's driver it was blessed on (`sw_vers -productVersion` on macOS, the kernel release elsewhere; the driver as wgpu names it, `-` on Metal, whose driver ships with macOS), and the check fails before rendering when either differs, naming the change, old → new. **The bound and the baseline hold for one machine and system only: an Apple M2 Pro, its GPU through Metal, on macOS 26.5.2, the bound measured 2026-11-20, the baseline blessed 2026-11-23.** On a change of the hardware, of macOS or the GPU's driver, or of the GPU code's intended cost, measure the runs again and bless again: about 60 runs of `cargo run --manifest-path crates/visual-gpu/Cargo.toml --locked --quiet -- check` idle and as many under a full `cargo xtask check`, on AC power, outside Low Power Mode, the idle ones in one session with nothing of the project running and no other heavy work; record every run, with its condition, as rows of `spec/gpu-time-runs.txt` (of one GPU, system and driver, its key line, held to the baseline's by a law test, so that the baseline holds one GPU until roadmap #35 step 12: another one starts the file anew, the former runs kept by git), and the idle runs' extremes in `IDLE` (`crates/visual-gpu/src/bench.rs`), whose law test derives the bound again from those rows, with the figures `crates/visual-gpu/src/bench_tests.rs` states; then `cargo xtask bless-benchmarks` (5 runs, on AC power, outside Low Power Mode), its 5 runs added to the record as `bless` rows of a new session and the check after it as `after-bless` (a law test holds the median of the newest bless recorded to the baseline), the reason in the commit. A change of macOS or of the driver fails the check by itself; a change of the GPU code's cost shows only as a time beyond the bound, and a change of the machine with a GPU of the same name not at all. Why 1280×720 and that bound: there the image's pixels dominate what a submission costs once (the median varied by 40% from run to run at 320×180); the bound is ±11%, decided on 2026-11-21 under this rule: every run recorded is in `spec/gpu-time-runs.txt`, and only those of the dedicated idle session derive the bound, 51 idle runs (one session, 88 125 to 94 708 ns; medians of 5 of them from 90 125 to 94 542 ns), 16 runs of another session being recorded as not idle, with why. A bless writes the median of 5 runs and a check compares one, so the bound is 1.5 times the largest deviation a check could have seen among them, one run from the median of any 5, rounded up to a whole percent (`bound_percent`, a law test computing it from the recorded runs, each compared as a check compares): 1.5 × 6.79% = 10.18%, rounded up to 11%, a margin of 1.62 over the worst comparison recorded. Load did not move the time: 61 of 62 runs under a full check's load (its Rust tests, its GPU steps, its Rust mutation testing) stayed from 2.45% below to 0.89% above the idle median of 93 709 ns, and the median of any 5 of the 62 is one an idle bless could have written (a law test holds it), so a bless under load is no farther than an idle one, though one of 62 runs read 17.07% above the idle median, beyond the bound, its cause unknown (no second heavy check ran): a time beyond the bound is therefore first run again with no other heavy work running, which its failure line says, and only then taken as a regression of the work or an unrecorded change of the machine. The display encoding's time at 1280×720 is shown beside the render's, never held to a baseline: it is not stable from run to run on that machine, single passes at about 250, 390 and 520 µs within one process, up to 5.9 ms, and a run's median at about 525 µs in most runs but 367 to 393 µs in some (5 of 142 runs recorded, the lowest 367 208 ns, the others from 509 333 ns; 2026-11-20 and 2026-11-23, on the same code path for `check` and `bless`), while the render's stays within its bound; its buffers, created for every image, are what roadmap #35 step 2's resources decision is to keep. The renderer creates its buffers and bind groups, and copies an image's values, for every image, where a live host keeps them from one image to the next (the playground's GPU drawing creates them once): its time includes that work, until the resources and GPU memory decision of roadmap #35 step 2. The sizes below 1280×720 are shown only, and may come back unmeasured, idle as under load (Metal writes no timestamp for many passes of a few microseconds: at 64×36 about 51% of the renders tried in the idle runs and 74% in the loaded ones, 12 of 51 and 42 of 62 of their runs unmeasured; at 320×180 and 640×360 at most 4%, every run measured; measured 2026-11-20 on an Apple M2 Pro; other GPUs are unmeasured, roadmap #35 step 12) (`visual-gpu check`, a step of every check; `cargo xtask bless-benchmarks` writes this machine's GPU's time, system and driver).

## Measured design choices

Every choice of the engine's code that a measurement decided, since the reduction order of roadmap #12 step 7, added on 2026-11-09, one entry each: when, the forms measured with their numbers, the form kept and why, the forms rejected and why, and how to measure again. The order of the reasons is the project's: performance on the real-time path first (instructions per block), then proof and robustness, then flexibility; plan loading and the module's size come after the per-block cost, and a rise of either is stated as the price of the form kept. The design decisions themselves, and why each exists, are in `engine-design.md`; what the checks' own speed choices measured is in `crates/xtask/README.md`.

**Units.** Unless an entry says otherwise, a count is the instructions of `BLOCKS` blocks (64), as the baseline gives it; "per block" divides it by 64; "loading" is the plan benchmarks of 256 to 16,384 oscillators, "the module" `module_bytes`. Counts taken before the charge of bulk memory instructions ("Bulk copies charged by the words they move" below) count a bulk copy as one instruction: they are marked "before the bulk charge", and compare with each other, never with counts after it (a date cannot tell them apart: several states of the code share 2026-11-11). A number this section does not have is said to be lost, never estimated.

**Measuring again.** Write the other form in a scratch copy of the tree (a worktree), build the module (`pnpm build` in `bindings/audio-wasm`) and run `pnpm benchmarks:check` there: it prints every count, which the baseline's, at the same commit, gives the difference from. Instruction counts move with the exact source form of the plan's per-block code, sometimes by more than the tolerance between forms that compute the same bits, and a change elsewhere can reverse a trade (two below did): **a bless that changes `Plan::process`, the plan's sums or `audio_boxes::BuiltIn` measures again, on its own code, the forms of their entries that one edit of that code can still write, and updates them, naming the code they ran on; an entry whose forms the code can no longer be written in keeps its counts, marked with the code they were measured on.** Entries name a state of the code by the bless or entry it follows, never by a commit (a rewritten history would change it).

### Sums of more than two terms

- **One reduction core, a block at a time** (`reduce` in `audio-core`'s math layer, generic over a sample and a block; 2026-11-10, before the bulk charge). The order of decision 28 was first applied frame by frame, through the sample helper `ordered_sum`, walking the terms again for each of the 64 frames: mixing 2 cables 454,848, 3 cables 557,248, 16 cables 2,027,712, 17 cables 2,142,400 and two output boxes 1,528,000 (binary64). ### The image hash fed by chunks

**The image hash feeds SHA-256 4 KiB at a time** (`visual-hash`, `ImageHasher`; 2026-11-16). One call per value (4 bytes) cost 1505 instructions a pixel to render and hash; laying 1024 values out on the stack and feeding them at once costs 1378 (-8.5%), the same bytes in the same order, so the same hash (the corpus and the known-answer vectors unchanged). The rest is SHA-256's own work; a faster hash would be a new scheme, `image-hash/2`, decided apart.

### The square placed in 32 bits

**The square's edges are 32-bit integers** (`visual-boxes`, `Square::placement`; 2026-11-16). Every edge is at most 16 384 × 4096 = 2²⁶ subpixels, so 32 bits hold it by construction, the GPU's shading language (no wider integers) included. Computing the placement in 32 bits instead of 64 costs 8.4% fewer instructions to render the square (87.04 against 95.05 a pixel at 1280×720), the same images (the corpus unchanged).

## Construction of the engine processor

The engine processor compiles the module, instantiates it, parses the patch and builds its plan on the audio thread, once, before it renders (`engine-design.md`, decision 15; a known deviation of CLAUDE.md's real-time constraint). The end-to-end test "constructs the engine processor within its bound, every time" times it `runs` times per browser engine (Chromium, Firefox, WebKit, at desktop and iPhone sizes), each time from creating an engine node (copying the module and the patch into its options included) to its processor's `ready` message, on the bench page's "Time construction" button, with the sine-440 patch. It prints the times it measured.

**What is asserted:** every time is at most the bound of its browser engine, `ceil(measured_max_ms × margin)` (`constructionBoundMs` in `benchmarks/suite.ts`), from `benchmark-thresholds.json`.

**Derivation.** Wall time on a shared machine is noisy, and browsers coarsen their timers (the bench page reads tenths of a millisecond in Chromium and whole milliseconds in Firefox and WebKit). `measured_max_ms` is the slowest of the constructions measured as `measured_on` says; `margin` covers a slower CI runner, a loaded machine and timer granularity. Such a bound catches what changes the construction by an order of magnitude (an eager compilation of a much larger module, a plan built in quadratic time, a copy of the module per block); it cannot catch a regression of a few percent, which is what the instruction counts of plan building are for.

**Where the values come from.** CI runs these bounds, but the measured values come from the maintainer's Mac, never from the runner; the margin is what must cover the x86_64 Linux runner, whose WebKit is WebKitGTK. A bound a CI run fails is measured again on the runner and recorded (`measured_on` names where), in a reviewed commit: never by widening the margin to pass.

**Measuring again.** Run `pnpm test:e2e` in `bindings/audio-wasm` several times on an idle machine; each run prints the times per browser engine. Record the slowest per engine in `measured_max_ms`, and where, when and how many in `measured_on`.

## Rendering each box

The end-to-end test "renders every box benchmark in both precisions within its bound, every time, and prints the cost ratio" times, on the bench page's own thread (the module and the browser engine compiling it are those of the worklet), for every setting of `BOX_BENCHMARKS` and both precisions given as binary32, `blocks` blocks (of the engine block, `engine_block_size`, rendered in Web Audio's 128-frame quanta) `runs` times after one warm-up, each in a fresh engine, with and without the box, in Chromium, Firefox and WebKit (desktop and iPhone sizes). It prints every time and the binary32/binary64 cost ratio of the box, from the difference of the medians with and without it: the real ratio decision 10 speaks of, which the instruction counts cannot see (memory, vector width, the cost of each instruction on each browser engine's compiler).

**What is asserted:** every time of the patch holding the box is at most `ceil(measured_max_ms × margin)` of its browser engine, from the `boxes` entry of `benchmark-thresholds.json`. The whole render is bounded, not the difference: a difference of two noisy times can be near zero or negative (an unconnected `dac~`), and the whole render bounds the box's cost from above.

**Derivation.** As for the construction above: `measured_max_ms` is the slowest render measured as `measured_on` says, `margin` covers a slower CI runner, a loaded machine and timer granularity (whole milliseconds in Firefox and WebKit, so `blocks` makes every render last tens of milliseconds). It catches what changes a box's cost by an order of magnitude; the ratio it prints is a measurement, not a threshold, and differences of a few percent are for the instruction counts.

**Where the values come from** and **measuring again**: as for the construction above; CI runs these bounds, and the values come from the maintainer's Mac.

## Adding a benchmark

For a new box type (its registration in `audio-boxes`' `REGISTRY` requires one: a test of `audio-boxes` refuses a registry and a baseline that name different box types):

1. Add its settings to `BOX_BENCHMARKS` (`bindings/audio-wasm/benchmarks/suite.ts`): a `setting` in words, a sample rate, a `patch` holding the box, and `without`, the same patch without it. Choose settings that change its cost (rates, parameters that change its work, inlets fed or not), including the extremes of its parameters; give a box with inlets a source in both patches, so that only the box itself differs.
2. Update the literal list of settings in `test/benchmarks/suite.test.ts`.
3. If the box type keeps a state, measure it both held inline in `audio_boxes::BuiltIn` and on the heap, keep the faster per block, and record both in "Measured design choices" above.
4. Run `cargo xtask bless-benchmarks`, and commit the new baseline with the box, saying that a box was added.

For a heavier patch or a new whole-patch setting: add it to `PATCH_BENCHMARKS` and to the literal list of settings in `test/benchmarks/suite.test.ts`, then bless.

For a new kind of benchmark (an engine component, a topology): add it to `benchmarks/suite.ts` and to the shape of the baseline (`parseBaseline`, `formatBaseline`), with its tests, then bless. For a new scaling claim, state it as a law like the n log n law, with a unit test that it refuses a cost that breaks it.

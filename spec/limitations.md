# Limitations and trade-offs

What the project does not prove, or proves only in part, and the trade-offs it accepted, in one place. Each entry says what is limited, why, what it costs, and where it is decided or tracked; the decision or the item it names is the source, this page only gathers them. An entry leaves this page when the roadmap step it names removes it.

## Bit-identical renders

- **A browser that flushes subnormals on its audio thread.** Firefox on x86_64 runs its audio thread, and the engine's WebAssembly on it, with subnormal operands and results flushed to zero, which no page can read or change; Chromium and WebKit keep IEEE arithmetic, and on aarch64 all three do (measured; [`engine-design.md`](engine-design.md), decision 11). Where the engine flushes, no bit changes, but for the values a binary64 render given as binary32 rounds up to ±2^-126, which aarch64's flush-to-zero with AH clear gives as a zero of their sign instead (decision 11; no browser measured on aarch64 flushes); elsewhere, a live render in that browser equals the native one only as long as no subnormal arises outside the engine's flush points (none arises in the limiter's control path, which keeps no stage value, share or applied reduction below `2^-100`, its Hann sums, derived from those, proven zero or normal, and computes no subnormal value: [`measurements.md`](measurements.md), "The true-peak limiter", step 7): true of every case the browser tests play live, not proven for every patch. The difference is far below anything audible. The engine reports the arithmetic it observes when it starts. Accepted: avoiding it would cost every user latency or speed, for one browser on one architecture.
- **The bits of a NaN.** A sum or a product whose result is NaN gives a NaN whose payload and sign may differ between targets and builds ([`engine-design.md`](engine-design.md), decision 28; #24 step 2 decides how sums treat NaN).

## Output stage

- **True peak above the ceiling.** Every sample the protected stage gives is at or below the ceiling, proven; its true peak (between samples) can exceed it by the detector's under-read, bounded only for an in-band sine whose period fits the window the limiter holds its needs over ([`engine-design.md`](engine-design.md), decision 12; [`measurements.md`](measurements.md), "The true-peak limiter"). For other signals the overshoot is not established yet: on noise, measured against a 16-times oversampled reference, it was found up to 2.1, 1.0 and 0.4 dB with the standard, precise and mastering detectors, and up to 0.23, 0.14 and 0.05 dB for noise below 0.4 of the rate, figures of one search, not bounds (#24 step 118).
- **Below the window.** No true-peak bound is derived for a sine whose period is longer than that window (below `rate/(L + 2)` for a lookahead of `L` frames, about 570 to 665 Hz at the default 1.5 ms lookahead, the precondition of [`measurements.md`](measurements.md), "The true-peak limiter"; about 290 to 330 Hz once #24 step 112 relaxes it to half a period), where the gain moves within each period; the playground's tests allow a measured shortfall instead (#24 step 112).
- **In the bass.** The release is meant neither to pump nor to distort, but pumping is measured nowhere, and a sine 6 dB over the ceiling was found with 3.7% THD+N at 50 Hz with the default settings; a hold separate from the lookahead is decided against it, and the adaptivity's default and the fast release's divisor are derived after it, not yet (#24 step 114). That step comes before the mastering application (#39) and before any use of the limiter as a final true-peak stage (decided 2026-11-17).
- **Below the ceiling by the detector's over-read.** A detector reading a peak high limits a sine below the ceiling, by its largest gain `G`: up to 1.044 in band for the precise detector, the default, about 0.37 dB (#24 step 132).
- **The mastering detector live.** Whether a live plan may use the mastering detector, the dearest, waits for the stage's measured cost (#24 step 113).
- **A lookahead set while the limiter's input needs a reduction takes effect at its next rest; while its input keeps needing one, it waits.** A lookahead set live is held pending while its input needs a reduction, in a switchable stage switched to raw too, whose limiter runs on unheard, the last one set counting, and taken at the limiter's rest, a frame by which a count certifies its whole control state that of a limiter at rest at any lookahead, so that from then on it renders bit for bit what a limiter always at the new lookahead renders, with no click (decision 12; [`measurements.md`](measurements.md), "The true-peak limiter", step 6). The count comes `K` frames, about 71 release time constants, after its last frame needing a reduction (about 7.1 s at the default release of 100 ms, 0.71 s at 10 ms, 71 s at 1,000 ms), counted again from a release or an adaptivity set meanwhile (but one set at rest, which counts nothing), never while its input needs one, however long: a lookahead set on program material over the ceiling more often than that, a pause of about 7.1 s without an over at the default release, stays pending for the whole program. The count certifies the rest, it does not find its first frame: every state is zero some time before it, the switch coming 14.6% later after one frame 0.1 dB over the ceiling (6.19 s against 7.10 s at the default settings), 2.5% later after a second 20 dB over, and the gain is back to 1, the input given bit for bit, seconds before that (2.88 s after that 0.1 dB over), so an interface showing "pending" shows it while nothing is reduced (step 6, *When*, measured). A limiter whose input never needed a reduction, or one at rest, takes a lookahead on its next frame. An interface can show it pending, then applied (decision 12: `lookaheadPending`, `onLookaheadApplied`). Changing the lookahead under limiting belongs to the musical limiter box (#38 step 12), designed for it, its model first.
- **A binary32 render one step low in a release tail.** The gain of a frame is rounded toward zero in the sample type, so that the ceiling holds with no slack: while the reduction lies in `(2^-54, 2^-25]`, about twenty release time constants of a tail, a binary32 gain is `1 - 2^-24` where rounding to the nearest would give 1, lowering each limited sample by one binary32 step (about `-5·10^-7` dB), so that a binary32 null test fails over that stretch where it could pass; a binary64 render is not transparent there either (its gain `1 - r` is below 1 for every `r` above `2^-54`), and both return to their input bit for bit on the same frame ([`engine-design.md`](engine-design.md), decision 12). Deriving per format the reduction below which the gain may round to the nearest and still keep every sample at or below the ceiling is #24 step 158.
- **Louder is quieter far over the ceiling.** The margin that keeps every sample at or below the ceiling lowers a limited output of level `p` by `p·E` (`E = 64·M·2^-53`, `M` the maximum lookahead in frames): a tenth of the ceiling at a tenth of `c/E`, and silence from about `c/E`, `6.5·10^10` at -1 dBTP, a maximum lookahead of 5 ms and 384 kHz but `3.1·10^13` at a maximum of 0.5 ms and 8 kHz, whatever the lookahead in force ([`measurements.md`](measurements.md), "The true-peak limiter"). Only a runaway signal comes near it.
- **Its cost.** What the limiter costs while it protects, each detector, and the 128-frame module the playground ships, are not measured by the benchmarks yet (#24 step 113); nor whether a block that takes a lookahead, whose frame computes the new window's phasor (594,594 instructions more at 384 kHz, [`benchmarks.md`](benchmarks.md), "A live lookahead taken at the limiter's rest"), fits a render quantum at 384 kHz in a browser, though a slider dragged on a limiter at rest puts one in every block that carries a command.

## Visual library

- **Point sampling, no motion blur.** Each image shows one instant, so fast motion strobes and can alias in time ([`visual-design.md`](visual-design.md), decision 2); whether boxes integrate over time is decided by #35 step 2.
- **A box filter only.** A pixel is the exact area a shape covers: the standard for vector shapes, but it leaves some aliasing on fine detail, which other filters reduce (#35 step 7).
- **Exact, not ideal.** The square is proven equal to its exact coverage at 1/4096 of a pixel, not to the ideal, unrounded square. Derived from where each edge can fall, in subpixel units (the side is rounded down by at most 15/16; the top edge errs within [−1/2, 15/32], the bottom within [−31/32, 0], the left within (−1, 15/16), the right within (−31/16, 0]): a pixel's value differs from the ideal by less than 93/32 of 1/4096 (about 2.906/4096, the supremum), and by less than 31/16 of 1/4096 (about 1.94/4096) near black, a pixel the square barely covers. Through the sRGB transfer, near black, that is below 1.6 codes at 8 bits, 6.3 at 10 and 25.1 at 12. The derivation is not yet checked by a test: #35 step 7 measures each image against the ideal shape, and whether the difference shows is a perceptual question it answers.
- **An 8-bit display encoding, without dithering.** Images are linear-light floats, encoded for display as 8-bit sRGB with straight alpha, exactly, the same bytes on every target ([`visual-design.md`](visual-design.md), section 9); with no dithering, a smooth gradient bands at 8 bits, and a straight-alpha encoding cannot be shown as it is on a WebGPU canvas, which takes premultiplied alpha (decided when images get transparent). Deterministic dithering and wider encodings come with the color pipeline and the output stage (#35 steps 6 and 10).
- **Square pixels assumed.** An image has no pixel aspect ratio: the square is square on square pixels only (#35 step 2).
- **Images follow the audio clock, not the sound.** The page shows the image of the frame the audio clock reads (`AudioContext.currentTime`), ahead of what is heard by the output latency (about 10 to 40 ms on built-in speakers, up to about 250 ms over Bluetooth) and by the output stage's lookahead; and the clock is as precise as the browser reports it (Firefox rounds it to 1 ms at 128 kHz and above: at most one image off, near a boundary). #35 step 3 carries the clock to the page with the output latency.
- **Exactness, not perception, measured.** The square's measurements are bit equalities with an exact reference ([`measurements.md`](measurements.md), Images); perceptual measurements (aliasing of moving edges, flicker, banding) come with #35 step 7, and the visual library's benchmarks count only its CPU reference in WebAssembly (`spec/benchmarks.md`, "Visual library"): the GPU's time is checked only on a GPU whose baseline the repository holds, the maintainer's Mac until CI has a GPU runner (CI's software GPU only shows it); one benchmark per visual box comes with #35 step 12.
- **The visual library's own module in Node only.** Its module, `visual-wasm`, is tested in Node; in browsers the product loads the page module, which links it (`web-page`, [`engine-design.md`](engine-design.md), decision 33), and the playground's end-to-end tests run it in Chromium, Firefox and WebKit, the GPU's drawing required in Chromium alone.
- **Little-endian hosts and regular case files assumed.** The visual module's wrapper reads image values in the host's byte order, right on every little-endian JavaScript host and wrong on a big-endian one (roadmap #24 step 103); `visual-cli` reading a case path that is not a regular file (a FIFO) waits on it instead of refusing it (#24 step 104).
- **No algorithm versions.** A visual reference is changed only through `visual-cli bless`, in a commit that says why; nothing yet refuses a changed bit at an unchanged version ([`visual-design.md`](visual-design.md), section 9; #35 step 2).

## Real time

- **Constructing the engine processor** compiles the module, instantiates it and builds the plan on the audio thread, once, before it renders (measured; to be bounded by #12 step 30).
- **The tap processor** copies and posts every render quantum while the playground's oscilloscope runs (until #12 step 21).
- **Allocation in the browser** is measured in V8 only; SpiderMonkey and JavaScriptCore are not measured yet (#12 step 21). The known deviations of the measured path are listed with the allocation test (`bindings/audio-wasm`, `pnpm test:allocation`).

## Offline rendering

- **A known length on a 32-bit target.** A render of a known length (`Renderer::lasting`) holds what is left of its samples as one value, so that it can render it at once: at most `isize::MAX` bytes, 2^31 - 1 on a 32-bit target such as WebAssembly, 2^28 - 1 frames of stereo binary32 (about 1 h 33 min at 48 kHz; `render.rs`'s `fits`, tested at both widths), where a 64-bit target holds far more; a longer render there is refused when it is built, though rendering it in parts would work (#24 step 156). No 32-bit host renders a known length today.

## What CI runs on

- **One CI platform.** CI runs on x86_64 Linux. On aarch64 (macOS on Apple silicon), native conformance and the native floating-point mode are proven only by the pre-push check of the maintainer's Mac, until a macOS job (#20 step 1).
- **A flushing host, per architecture.** The limiter's host differential (`differs_on_no_host_through_a_release_tail`, [`measurements.md`](measurements.md), "The true-peak limiter", step 7) runs the flushing mode of the processor that runs it: x86_64's flush-to-zero and denormals-are-zero in CI, aarch64's FZ and FIZ only on the maintainer's Mac (#20 step 1); aarch64's alternate handling (AH), which an Apple M2 does not hold, runs nowhere. That the control path computes alike on every host rests on step 7's derivation there.
- **Browsers are Playwright's builds.** "WebKit" is Playwright's WebKit, not Safari, and "mobile WebKit" is the same engine at a phone's size, not iOS Safari; real phones are tested by #18 step 5.
- **No sound card.** In CI, live playback is proven to reach an audio output, never a device.

## Proofs

- **The default check proves the changes only.** It mutates the changed code; only the full check (`cargo xtask check --full`, CI) proves the rest. A green default check does not imply a green full check.
- **Branch coverage reads each generic function's best instantiation.** llvm-cov's summary counts a generic function by its best instantiation, never their union: a path taken by one instantiation only (one precision, one caller's type) counts as covered when that instantiation takes it, so the paths of the others go unseen (a branch on a constant of the instantiation is written as a run-time test of that constant, `CLAUDE.md`; #24 step 87).
- **Review only.** What no tool can check is reviewed instead, and each case says so where it is stated: the files a doc test loads, the test data paths computed at run time, sums written inside box code, and the provenance of npm packages, which is not checked yet.
